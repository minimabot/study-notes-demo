@topic vpc/endpoints-privatelink/overview

프라이빗 서브넷의 인스턴스가 S3나 SQS 같은 AWS 서비스를 부르려면 보통 NAT 게이트웨이와 인터넷 게이트웨이를 거친다. 트래픽이 AWS 네트워크를 떠나지는 않지만, NAT 비용이 들고 인터넷으로 나가는 경로를 열어 두어야 한다. **VPC 엔드포인트(VPC endpoint)** 는 이 경로 없이 VPC에서 서비스로 바로 가는 입구다.

**AWS PrivateLink** 는 VPC를 서비스와 리소스에 사설로 잇는 기술이다. 인터넷 게이트웨이, NAT 장치, 퍼블릭 IP, VPN, Direct Connect 없이 프라이빗 서브넷에서 서비스에 닿는다. 그 서비스가 내 VPC 안에 있는 것처럼 보인다. 엔드포인트 유형은 다음과 같다.

| 유형 | 하는 일 |
|---|---|
| 게이트웨이 엔드포인트(Gateway endpoint) | S3·DynamoDB 전용. 라우팅 테이블 경로로 보낸다. **PrivateLink를 쓰지 않는다** |
| 인터페이스 엔드포인트(Interface endpoint) | 서브넷에 네트워크 인터페이스를 두고 DNS로 보낸다. AWS 서비스, 다른 계정의 엔드포인트 서비스, 파트너 서비스에 쓴다 |
| Gateway Load Balancer 엔드포인트 | 라우팅 테이블로 트래픽을 보안 어플라이언스 무리에 돌린다 |
| 리소스·서비스 네트워크 엔드포인트 | 공유받은 리소스(DB 등)나 서비스 네트워크에 닿는다. 이 장에서는 다루지 않는다 |

시험에서 가장 자주 비교되는 것은 앞의 둘이다.

| 항목 | 게이트웨이 엔드포인트 | 인터페이스 엔드포인트 |
|---|---|---|
| 대상 | S3, DynamoDB | PrivateLink를 지원하는 많은 AWS 서비스(S3·DynamoDB 포함) |
| 동작 | 라우팅 테이블에 접두사 목록 경로 추가 | 서브넷에 네트워크 인터페이스(프라이빗 IP) + DNS |
| 요금 | 추가 요금 없음 | 가용 영역별 시간당 요금 + 처리한 데이터 양 |
| 온프레미스·다른 VPC에서 | 쓸 수 없음 | 쓸 수 있음 |
| 보안 그룹 | 엔드포인트에 없음 | 엔드포인트 네트워크 인터페이스에 붙임 |

@topic vpc/endpoints-privatelink/gateway

게이트웨이 엔드포인트를 만들 때 연결할 라우팅 테이블을 고른다. 그러면 각 표에 경로가 자동으로 들어간다. 목적지는 AWS가 관리하는 서비스 **접두사 목록(prefix list)**(`pl-...`), 타깃은 엔드포인트(`vpce-...`)다.

- 이 경로는 볼 수는 있지만 고치거나 지울 수 없다. 라우팅 테이블 연결을 끊거나 엔드포인트를 지우면 사라진다.
- 연결된 라우팅 테이블을 쓰는 서브넷의 인스턴스는 자동으로 엔드포인트를 쓴다. 다른 서브넷은 계속 퍼블릭 서비스 엔드포인트로 간다.
- 표 하나에 S3 경로와 DynamoDB 경로를 함께 둘 수 있다. 같은 서비스 경로를 한 표에 둘 넣을 수는 없다.
- 가장 구체적인 경로가 이긴다. 0.0.0.0/0이 인터넷 게이트웨이로 가더라도, 같은 리전 S3로 가는 트래픽은 엔드포인트 경로를 탄다.

**같은 리전 전용이다.** 접두사 목록은 리전별이다. 다른 리전의 S3 버킷으로 가는 트래픽은 엔드포인트를 타지 않고 다른 경로(인터넷 게이트웨이 등)로 간다. 그래서 버킷과 같은 리전에 엔드포인트를 만든다.

**VPC 밖으로 넓힐 수 없다.** VPN, VPC 피어링, 전송 게이트웨이, Direct Connect 너머의 리소스는 이 VPC의 게이트웨이 엔드포인트를 쓸 수 없다. 온프레미스나 다른 VPC에서 사설로 S3에 닿아야 하면 인터페이스 엔드포인트를 쓴다.

**보안 설정.** 인스턴스는 서비스의 퍼블릭 엔드포인트 주소로 접속한다. 그래서 인스턴스 보안 그룹의 아웃바운드 규칙이 서비스로 가는 트래픽을 허용해야 한다. 접두사 목록 ID를 대상으로 TCP 443을 열면 된다. 네트워크 ACL은 접두사 목록을 참조할 수 없으므로, 접두사 목록에 든 IP 대역을 규칙에 적는다.

**요금과 할당량.** 게이트웨이 엔드포인트에는 추가 요금이 없다. NAT 게이트웨이를 거치던 S3·DynamoDB 트래픽을 엔드포인트로 돌리면 NAT 데이터 처리 비용이 준다. 리전당 기본 {{fact:vpc.endpoint.gateway-per-region}}(늘릴 수 있음), VPC당 {{fact:vpc.endpoint.gateway-per-vpc}}까지 만든다.

@topic vpc/endpoints-privatelink/interface

인터페이스 엔드포인트를 만들 때 서브넷을 고른다. **가용 영역마다 서브넷은 하나만** 고를 수 있다. 고른 서브넷마다 **엔드포인트 네트워크 인터페이스(endpoint network interface)** 가 생기고 서브넷의 프라이빗 IP를 받는다. 이 인터페이스는 요청자 관리형(requester-managed)이라 계정에서 보이지만 직접 다룰 수 없다. 인터페이스가 유지되는 동안 그 IP도 유지된다. 서브넷을 빼면 그 서브넷의 인터페이스가 지워지고, 서브넷을 더하면 새로 생긴다. 이미 인터페이스가 있는 서브넷에 IP를 새로 지정하면 인터페이스가 새것으로 바뀌어 IP가 달라질 수 있고, 그동안 그 서브넷과 엔드포인트의 연결이 잠시 끊긴다.

**보안 그룹.** 엔드포인트 네트워크 인터페이스에 보안 그룹을 붙인다. 지정하지 않으면 VPC 기본 보안 그룹이 붙는다. 이 보안 그룹은 VPC 리소스에서 오는 트래픽을 인바운드로 허용해야 한다. AWS API는 HTTPS이므로 보통 TCP 443을 연다. 서브넷 네트워크 ACL도 이 트래픽을 막지 않아야 한다.

**프라이빗 DNS(Private DNS).** 켜면 AWS가 숨겨진 프라이빗 호스팅 영역을 만들어, 서비스의 기본 DNS 이름(예: `sqs.<리전>.amazonaws.com`)이 엔드포인트의 프라이빗 IP로 풀리게 한다. 그래서 SDK와 CLI 코드를 고치지 않아도 엔드포인트를 탄다. 조건이 있다.

- VPC의 DNS 호스트 이름(`enableDnsHostnames`)과 DNS 확인(`enableDnsSupport`)이 모두 켜져 있어야 한다.
- 켠 뒤 몇 분이 지나야 프라이빗 IP가 쓰인다.
- 프라이빗 DNS를 끄면 엔드포인트 고유의 리전 DNS 이름이나 가용 영역별 DNS 이름을 코드에 직접 써야 한다. 가용 영역별 이름을 쓰면 트래픽을 같은 가용 영역 안에 둘 수 있다.

**가용성.** 리전 DNS 이름은 정상인 엔드포인트 네트워크 인터페이스를 번갈아 돌려준다. 한 가용 영역에만 만들면 그 가용 영역이 손상될 때 다른 가용 영역의 리소스도 서비스에 닿지 못한다. AWS는 가용 영역을 둘 이상 켜라고 권장한다.

**요금과 한도.** 엔드포인트가 있는 가용 영역마다 시간당 요금이 붙고, 처리한 데이터 양에 따라 요금이 더 붙는다. 단가는 리전마다 다르다. 대역폭은 가용 영역당 {{fact:vpc.endpoint.bw.default}}로 시작해 {{fact:vpc.endpoint.bw.max}}된다. MTU는 {{fact:vpc.endpoint.mtu}}다. VPC당 인터페이스 엔드포인트와 Gateway Load Balancer 엔드포인트를 합쳐 기본 {{fact:vpc.endpoint.interface-per-vpc}}까지 만든다.

**S3에 두 엔드포인트를 함께 쓰기.** 온프레미스에서도 사설로 S3를 써야 하면 인터페이스 엔드포인트가 필요하다. 이때 S3 인터페이스 엔드포인트에 "인바운드 엔드포인트에만 프라이빗 DNS 사용(private DNS only for inbound endpoint)"을 켜면, 온프레미스 요청은 인터페이스 엔드포인트로, VPC 안 요청은 무료인 게이트웨이 엔드포인트로 간다. 이 옵션은 같은 VPC에 S3 게이트웨이 엔드포인트가 있어야 쓸 수 있다.

@topic vpc/endpoints-privatelink/policies

**엔드포인트 정책(endpoint policy)** 은 VPC 엔드포인트에 붙이는 IAM 리소스 기반 정책이다. 이 엔드포인트를 지나는 요청 중 어떤 주체가 어떤 작업을 어떤 리소스에 할 수 있는지 정한다.

- 붙이지 않으면 기본 정책이 붙는다. 모든 주체에게 모든 작업·리소스를 허용한다.
- 엔드포인트 정책은 IAM 자격 증명 정책이나 버킷 정책 같은 리소스 정책을 대신하지 않는다. 요청은 모든 정책을 통과해야 한다.
- 엔드포인트 하나에 정책 하나를 붙이고, 언제든 바꿀 수 있다. 바꾼 뒤 반영까지 몇 분 걸릴 수 있다. 크기는 {{fact:vpc.endpoint.policy-chars}}까지다.
- 엔드포인트 정책을 지원하지 않는 서비스도 있다. 그때는 전체 접근이 허용된다.
- 게이트웨이 엔드포인트 정책에서는 `Principal`을 `*`로 두어야 한다. 특정 주체로 좁히려면 `aws:PrincipalArn` 조건 키를 쓴다.

엔드포인트 정책은 "이 문으로 무엇이 나갈 수 있나"를 정한다. 반대로 "이 리소스는 어느 문을 거친 요청만 받나"는 리소스 쪽 정책에서 정한다. 예를 들어 S3 버킷 정책이나 SQS 큐 정책에 `aws:sourceVpce`·`aws:SourceVpc` 조건을 넣어, 특정 엔드포인트를 거치지 않은 요청을 거부한다. 두 가지를 함께 써야 데이터가 정해진 경로로만 오간다. SQS 큐 쪽 설정과 주의점은 {{ch:sqs/security}}에서 다룬다.

@topic vpc/endpoints-privatelink/endpoint-services

PrivateLink로 내 서비스를 다른 VPC나 계정에 내보일 수도 있다. 서비스를 가진 쪽을 **서비스 공급자(service provider)**, 쓰는 쪽을 **서비스 소비자(service consumer)** 라 한다.

1. 공급자가 서비스 앞에 Network Load Balancer를 두고, 이를 지정해 **엔드포인트 서비스(endpoint service)** 를 만든다.
2. 공급자는 연결을 허용할 AWS 주체(계정, 사용자, 역할)를 권한에 넣는다. 기본값에서는 아무도 연결할 수 없다.
3. 소비자가 서비스 이름을 지정해 인터페이스 엔드포인트를 만든다. 공급자는 연결 요청을 수락하거나 거절한다(자동 수락도 설정할 수 있다).
4. 연결은 소비자가 시작한다. 소비자는 공급자 VPC 전체가 아니라 그 서비스에만 닿는다.

공급자 쪽은 Network Load Balancer를 가용 영역 둘 이상에 켜고 각 가용 영역에 대상을 두라는 것이 AWS 권장이다. 소비자는 서비스가 켜진 가용 영역에만 엔드포인트를 만들 수 있다.

**Gateway Load Balancer 엔드포인트.** 공급자가 Gateway Load Balancer로 엔드포인트 서비스를 만들면, 소비자는 Gateway Load Balancer 엔드포인트를 만들고 라우팅 테이블에서 이 엔드포인트를 타깃으로 지정해 트래픽을 방화벽 같은 어플라이언스로 보낸다. 엔드포인트 하나는 가용 영역 하나에만 두며, 서브넷은 나중에 바꿀 수 없다. 응답 트래픽만 돌려줄 뿐 서비스 쪽에서 소비자 VPC로 먼저 연결하지는 못한다.

**세 가지 연결 방법 비교.**

| 방법 | 잇는 범위 | 맞는 경우 |
|---|---|---|
| VPC 피어링 | 두 VPC 네트워크 전체 | VPC 몇 개를 서로 잇는다 |
| 전송 게이트웨이 | 많은 VPC와 온프레미스, 라우팅 테이블로 분리 | 대규모·하이브리드 허브 |
| PrivateLink | 특정 서비스 하나(소비자 → 공급자 방향) | 서비스만 내보이고 네트워크는 열지 않는다 |

자세한 내용은 {{ch:vpc/peering}}, {{ch:vpc/transit-gateway}}에서 다룬다.
