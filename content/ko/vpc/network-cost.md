@topic vpc/network-cost/components

VPC 자체와 서브넷, 라우팅 테이블, 인터넷 게이트웨이, 보안 그룹, 네트워크 ACL에는 요금이 없다. 요금은 **트래픽을 처리하거나 주소를 쥐고 있는 구성 요소**에 붙는다. 대부분 "켜 둔 시간"과 "처리한 GB" 두 축으로 매긴다.

서울 리전을 기준으로 하고 미국 동부(버지니아 북부)를 참고로 붙인다.

| 항목 | 서울 (ap-northeast-2) | us-east-1 (참고) |
|---|---|---|
| NAT 게이트웨이 시간 | {{fact:vpc.price.natgw-hour.apne2}} | {{fact:vpc.price.natgw-hour.use1}} |
| NAT 게이트웨이 처리 | {{fact:vpc.price.natgw-gb.apne2}} | {{fact:vpc.price.natgw-gb.use1}} |
| 인터페이스 엔드포인트 시간 | {{fact:vpc.price.interface-endpoint-hour.apne2}} | {{fact:vpc.price.interface-endpoint-hour.use1}} |
| 인터페이스 엔드포인트 처리 | {{fact:vpc.price.interface-endpoint-gb}} | 서울과 같다 |
| 전송 게이트웨이 연결 시간 | {{fact:vpc.price.tgw-attachment-hour.apne2}} | {{fact:vpc.price.tgw-attachment-hour.use1}} |
| 전송 게이트웨이 처리 | {{fact:vpc.price.tgw-gb}} | 서울과 같다 |
| 퍼블릭 IPv4 주소 | {{fact:vpc.price.public-ipv4-hour}} | 서울과 같다 |

요금은 리전마다 다르고 자주 바뀐다. 이 장의 값은 {{fact:vpc.price.offer-version}} 기준이다. 실제 단가는 요금 페이지나 AWS Pricing Calculator에서 다시 확인한다.

항목별로 알아 둘 점은 다음과 같다.

- **NAT 게이트웨이.** 사용 가능한 상태로 있는 시간마다, 그리고 처리한 데이터 GB마다 낸다. 트래픽이 없어도 시간 요금은 붙는다. 처리 요금은 목적지가 인터넷이든 같은 리전의 AWS 서비스든 똑같이 붙는다. 영역마다 하나씩 두면 시간 요금도 영역 수만큼 늘어난다({{ch:vpc/nat}}).
- **퍼블릭 IPv4 주소.** 인스턴스에 자동으로 붙은 주소, 탄력적 IP, NAT 게이트웨이·로드 밸런서에 붙은 주소 모두 시간 단위로 낸다. 리소스에 붙지 않고 계정에만 잡혀 있는 유휴 주소도 같은 단가로 낸다({{ch:vpc/internet-access}}).
- **게이트웨이 엔드포인트(S3, DynamoDB).** 시간 요금도 처리 요금도 없다.
- **인터페이스 엔드포인트.** 엔드포인트 네트워크 인터페이스를 둔 가용 영역마다 시간 요금이 붙고, 처리한 GB만큼 더 낸다. 처리 단가는 월 사용량이 아주 커지면 낮아진다({{ch:vpc/endpoints-privatelink}}).
- **전송 게이트웨이.** 붙인 연결(attachment)마다 시간 요금, 처리한 GB마다 처리 요금을 낸다. 처리 요금은 기본적으로 트래픽을 보낸 쪽 연결의 소유 계정에 붙는다({{ch:vpc/transit-gateway}}).
- **VPC 피어링.** 연결 자체와 시간 요금이 없다. 같은 가용 영역 안의 피어링 트래픽은 무료이고, 영역을 넘거나 리전을 넘으면 데이터 전송 요금이 붙는다({{ch:vpc/peering}}).

청구서와 사용량 보고서에는 이 항목이 사용 유형 코드로 나온다. 예를 들어 서울 리전의 인터페이스 엔드포인트 시간은 `APN2-VpcEndpoint-Hours`, 전송 게이트웨이 처리량은 `APN2-TransitGateway-Bytes`, 유휴 퍼블릭 IPv4는 `APN2-PublicIPv4:IdleAddress`다. Cost Explorer에서 이 코드로 거르면 어느 항목이 비용을 끌어올리는지 빨리 찾는다.

@topic vpc/network-cost/data-transfer

구성 요소 요금과 따로, 데이터가 **어디서 어디로 가는지**에 따라 전송 요금이 붙는다. 같은 바이트라도 경로에 따라 공짜일 수도, 두세 번 요금이 붙을 수도 있다.

| 경로 | 전송 요금 |
|---|---|
| 같은 가용 영역 안, 프라이빗 IP | 없다 |
| 같은 리전, 다른 가용 영역 | {{fact:vpc.price.inter-az-gb}} |
| 같은 리전의 EC2 → S3·DynamoDB 등 | 없다 (경로의 NAT 처리 요금은 따로) |
| 다른 리전으로 (서울에서) | {{fact:vpc.price.inter-region-gb.apne2}} |
| 인터넷으로 (서울) | {{fact:vpc.price.internet-out-gb.apne2}} |
| 인터넷으로 (us-east-1, 참고) | {{fact:vpc.price.internet-out-gb.use1}} |
| 인터넷에서 들어오는 방향 | 없다 |

- **영역 간 전송은 양쪽에 붙는다.** 한 영역의 인스턴스가 다른 영역의 인스턴스로 보내면 나가는 쪽과 들어오는 쪽에 각각 GB당 요금이 붙는다. 서버 사이에 대화가 많은 계층(예: 애플리케이션 서버와 캐시)을 영역 여러 곳에 흩어 두면 이 요금이 쌓인다.
- **퍼블릭 IPv4로 같은 리전 안을 오가도** 영역 간과 같은 단가가 붙는다. 같은 VPC 안이라면 프라이빗 IP로 통신하게 한다.
- **인터넷 송신**은 모든 서비스와 리전을 합쳐 {{fact:vpc.price.internet-out.free}}의 무료 제공량이 있고, 그 뒤로는 양이 많을수록 단가가 낮아지는 구간제다. 위 표는 첫 구간 단가다.
- **비용이 겹치는 경로.** 프라이빗 서브넷의 인스턴스가 다른 영역의 NAT 게이트웨이를 거쳐 인터넷으로 나가면 영역 간 전송 + NAT 처리 + 인터넷 송신이 모두 붙는다. 같은 영역의 NAT로 보내면 영역 간 몫이 빠진다.

시험에서는 "같은 데이터를 어떤 경로로 보내야 가장 싼가"를 묻는 형태가 많다. 기준은 단순하다. 같은 영역 안 > 같은 리전 > 다른 리전 > 인터넷 순으로 싸고, NAT·전송 게이트웨이·인터페이스 엔드포인트처럼 **처리 요금이 붙는 장치를 몇 번 지나는지**를 센다.

@topic vpc/network-cost/s3-path

프라이빗 서브넷에서 같은 리전의 S3로 데이터를 보내는 길은 셋이다. 가장 흔한 절감 포인트라서 숫자로 비교해 둔다.

| 경로 | 붙는 요금 |
|---|---|
| (a) NAT 게이트웨이 경유 | NAT 시간 + NAT 처리 GB (+ 다른 영역의 NAT를 쓰면 영역 간 전송) |
| (b) S3 게이트웨이 엔드포인트 | 없다 |
| (c) S3 인터페이스 엔드포인트 | 영역마다 엔드포인트 시간 + 처리 GB |

- **(b)가 기본값이다.** 같은 리전의 VPC 안에서 S3·DynamoDB에 닿는 것이 목적이면 게이트웨이 엔드포인트가 가장 싸다. 콘솔의 "VPC 등" 마법사도 S3 게이트웨이 엔드포인트를 기본으로 켠다. 라우팅 테이블에 접두사 목록 경로가 들어가므로, 엔드포인트를 연결한 라우팅 테이블의 서브넷에서만 효과가 있다.
- **(c)가 필요한 경우.** 게이트웨이 엔드포인트는 그 VPC 안에서만 쓸 수 있다. 온프레미스(Direct Connect·VPN)나 피어링·전송 게이트웨이로 이어진 다른 VPC에서 S3에 사설 경로로 닿아야 하면 인터페이스 엔드포인트를 쓴다.
- **(a)는 S3 트래픽에는 피한다.** NAT 처리 단가가 인터페이스 엔드포인트 처리 단가보다 몇 배 높다. NAT가 인터넷용으로 어차피 있더라도, S3로 가는 GB만큼 처리 요금을 계속 낸다.

아래 계산기로 월 전송량과 영역 수를 바꿔 본다. "인터넷용으로 NAT가 어차피 필요하다"를 켜면 NAT 고정비를 빼고 GB 요금 차이만 비교한다.

@topic vpc/network-cost/checklist

네트워크 비용을 줄일 때는 다음 순서로 점검한다.

1. **S3·DynamoDB 트래픽을 게이트웨이 엔드포인트로 돌린다.** NAT 게이트웨이의 `BytesOutToDestination` 지표와 VPC 흐름 로그로 목적지를 확인한다. 대부분 S3·DynamoDB면 게이트웨이 엔드포인트만으로 NAT 처리 요금이 크게 준다.
2. **다른 AWS 서비스는 인터페이스 엔드포인트를 검토한다.** ECR, CloudWatch Logs, STS처럼 트래픽이 많은 서비스는 NAT 처리 단가와 엔드포인트 시간·처리 요금을 비교한다. 트래픽이 적으면 엔드포인트 시간 요금이 더 클 수 있다.
3. **인터페이스 엔드포인트를 모은다.** VPC마다 같은 서비스의 엔드포인트를 영역 여러 곳에 두면 시간 요금이 VPC 수 × 영역 수 × 서비스 수로 늘어난다. 전송 게이트웨이로 이어진 공유 서비스 VPC 한 곳에 엔드포인트를 두고 Route 53 프라이빗 호스팅 영역으로 이름을 풀게 하는 방법이 있다. 대신 전송 게이트웨이 처리 요금이 더해지므로 트래픽 양을 놓고 비교한다.
4. **대화가 많은 트래픽은 같은 영역에 둔다.** 영역 간 전송은 양쪽에 붙는다. 프라이빗 서브넷은 같은 영역의 NAT 게이트웨이를 쓰게 라우팅한다. 다만 가용성을 위해 영역 여러 곳에 두는 것 자체를 포기하지는 않는다. 비용과 가용성의 균형이다.
5. **NAT 게이트웨이 수를 환경에 맞춘다.** 운영 환경은 영역마다 하나가 권장 구성이다. 개발·시험 환경은 하나를 공유하거나, 쓰지 않을 때 지우는 방법으로 시간 요금을 줄인다.
6. **퍼블릭 IPv4를 줄인다.** 인터넷에서 직접 받을 필요가 없는 인스턴스는 퍼블릭 IP 자동 할당을 끈다. 쓰지 않는 탄력적 IP는 해제한다. 들어오는 트래픽은 로드 밸런서로 받고, IPv6를 쓸 수 있으면 IPv6 경로를 함께 검토한다.
7. **피어링과 전송 게이트웨이를 트래픽 양으로 고른다.** 피어링은 시간·처리 요금이 없어 트래픽이 많은 소수의 VPC 쌍에 싸다. VPC가 많으면 전송 게이트웨이가 관리 면에서 낫지만 연결 시간과 처리 GB가 붙는다.
8. **리전 간·인터넷 송신을 줄인다.** 다른 리전으로 복제하는 데이터는 꼭 필요한 것만 보낸다. 인터넷으로 내보내는 정적 콘텐츠는 CloudFront 같은 캐시를 앞에 두는 것을 검토한다.
