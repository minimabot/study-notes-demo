@topic vpc/overview/what-is

**Amazon VPC(Virtual Private Cloud)** 는 내 AWS 계정 안에 따로 떼어 둔 가상 네트워크다. 다른 가상 네트워크와 논리적으로 격리되어 있고, 주소 범위·서브넷·라우팅·게이트웨이를 내가 정한다. 데이터 센터에서 운영하던 네트워크를 AWS 위에 다시 만드는 것과 비슷하다.

범위를 먼저 잡아 두면 뒤의 내용이 쉽다.

| 단위 | 걸치는 범위 |
|---|---|
| VPC | 한 리전(Region) 안의 모든 가용 영역(Availability Zone, AZ) |
| 서브넷(Subnet) | 가용 영역 하나. 여러 가용 영역에 걸칠 수 없다 |

그래서 고가용성은 "VPC를 여러 개 만드는 것"이 아니라 "한 VPC 안에서 가용 영역마다 서브넷을 두고 리소스를 나눠 놓는 것"에서 시작한다. 가용 영역 하나가 장애를 겪어도 다른 가용 영역의 서브넷에 있는 리소스는 살아 있다.

VPC 자체에는 추가 요금이 없다. NAT 게이트웨이, IPAM, 트래픽 미러링 같은 일부 구성 요소와 퍼블릭 IPv4 주소에는 요금이 붙는다.

@topic vpc/overview/building-blocks

VPC를 이루는 부품은 다음과 같다. 각각은 뒤의 장에서 자세히 다룬다.

| 구성 요소 | 하는 일 |
|---|---|
| CIDR 블록 | VPC가 쓰는 IP 주소 범위. {{ch:vpc/ip-addressing}} |
| 서브넷 | VPC 주소 범위의 일부. 리소스는 서브넷 안에 만든다. {{ch:vpc/subnets-routing}} |
| 라우팅 테이블(Route table) | 서브넷에서 나가는 트래픽을 어디로 보낼지 정하는 규칙 모음 |
| 인터넷 게이트웨이(Internet gateway) | VPC와 인터넷을 잇는다. {{ch:vpc/internet-access}} |
| NAT 장치 | 프라이빗 서브넷에서 밖으로 나가는 연결만 허용한다. {{ch:vpc/nat}} |
| 보안 그룹·네트워크 ACL | 리소스 단위와 서브넷 단위의 트래픽 필터. {{ch:vpc/security-groups-nacl}} |
| VPC 엔드포인트 | 인터넷 게이트웨이나 NAT 없이 AWS 서비스에 사설로 연결한다. {{ch:vpc/endpoints-privatelink}} |
| 피어링·Transit Gateway | VPC끼리 잇는다. {{ch:vpc/peering}}, {{ch:vpc/transit-gateway}} |
| Site-to-Site VPN | 사내 데이터 센터와 잇는다. {{ch:vpc/hybrid-vpn}} |

VPC를 만들면 몇 가지는 저절로 따라온다. **기본 DHCP 옵션 세트**, **기본 네트워크 ACL**, **기본 보안 그룹**, **기본 라우팅 테이블(Main route table)** 이다. 인터넷 게이트웨이, NAT 게이트웨이, 사용자 지정 라우팅 테이블 등은 필요할 때 직접 만든다.

한국어 문서에서는 Main route table과 Default VPC를 모두 "기본"으로 옮긴다. 이 책에서는 헷갈리지 않게 처음 나올 때 영어를 함께 적는다.

@topic vpc/overview/default-vpc

{{fact:vpc.default-vpc.since}} 이후에 만든 계정은 리전마다 **기본 VPC(Default VPC)** 를 하나씩 받는다. 바로 EC2 인스턴스를 띄워 인터넷과 통신할 수 있게 미리 꾸며 둔 VPC다. AWS가 만들어 두는 것은 다음과 같다.

- IPv4 CIDR 블록 {{fact:vpc.default-vpc.cidr}}
- 가용 영역마다 {{fact:vpc.default-vpc.subnet-prefix}} 크기의 **기본 서브넷(Default subnet)**. 기본 서브넷은 퍼블릭 서브넷이다
- VPC에 연결된 인터넷 게이트웨이
- 기본 라우팅 테이블에 모든 트래픽(`0.0.0.0/0`)을 인터넷 게이트웨이로 보내는 경로
- 기본 보안 그룹, 기본 네트워크 ACL, 계정의 기본 DHCP 옵션 세트
- 퍼블릭 IP를 가진 인스턴스에 퍼블릭 DNS 호스트 이름을 주고, Amazon 제공 DNS로 이름을 풀어 주는 DNS 설정

기본 서브넷에 띄운 인스턴스는 프라이빗 IPv4 주소와 퍼블릭 IPv4 주소를 함께 받는다. 그래서 따로 설정하지 않아도 인터넷에 닿는다. 서브넷을 지정하지 않고 인스턴스를 띄우면 AWS가 기본 서브넷 하나를 골라 넣는다.

반대로 내가 만든 VPC(**기본이 아닌 VPC, Nondefault VPC**)는 기본 라우팅 테이블에 로컬 경로만 있다. 인터넷 게이트웨이도 직접 만들어 붙이기 전에는 없다(콘솔의 "VPC 등" 마법사에서 고르면 함께 만들어 준다). 여기 만든 서브넷의 인스턴스는 기본적으로 퍼블릭 IPv4 주소를 받지 않는다.

기본 VPC는 빠르게 시작하거나 블로그 같은 공개 서버를 띄울 때 알맞다. 일반 VPC처럼 서브넷·라우팅 테이블·CIDR 블록을 더하고 고칠 수 있다. 다만 모든 서브넷이 인터넷에 열려 있는 구조이므로, 운영 워크로드는 보통 계층을 나눈 VPC를 따로 설계한다.

알아 둘 점이 하나 있다. 기본 VPC의 구성 요소는 AWS가 대신 만들기 때문에 IAM 정책의 거부가 적용되지 않는다. 예를 들어 `CreateInternetGateway`를 막아 두어도 `CreateDefaultVpc`를 호출하면 인터넷 게이트웨이가 생긴다. 막으려면 두 작업을 함께 거부해야 한다.

@topic vpc/overview/planning

AWS 문서가 제시하는 계획 순서를 간추리면 다음과 같다.

1. **IP 주소 범위를 정한다.** 계정과 VPC 전체에 몇 개의 주소가 필요한지 따진다. 사내 네트워크, 그리고 나중에 연결할 다른 VPC와 범위가 겹치지 않아야 한다. 겹치면 피어링 같은 연결을 만들 수 없다. 자세한 계산은 {{ch:vpc/ip-addressing}}에서 다룬다.
2. **가용 영역을 고른다.** 운영 환경은 {{fact:vpc.plan.prod-min-azs}}의 가용 영역에 리소스를 고르게 둔다. 개발·테스트 환경은 비용을 아끼려고 한 곳만 쓸 수도 있다.
3. **연결 요구에 따라 서브넷을 나눈다.** 인터넷에서 요청을 받는 웹 서버, VPC 안에서만 요청을 받는 서버, VPN으로만 요청을 받는 서버를 각각 다른 서브넷에 두고, 이것을 가용 영역마다 반복한다.
4. **인터넷 연결을 정한다.** 인터넷 게이트웨이를 붙이는 것만으로는 아무것도 열리지 않는다. 서브넷 라우팅 테이블에 인터넷 게이트웨이로 가는 경로, 인스턴스의 퍼블릭 IP, 포트를 허용하는 보안 그룹이 모두 있어야 한다. 프라이빗 서브넷이 업데이트를 받으려면 가용 영역마다 퍼블릭 NAT 게이트웨이를 두고 라우팅 테이블을 고친다.

AWS는 리소스를 보호하려면 프라이빗 서브넷을 쓰라고 권장한다. 인터넷에서 직접 받아야 하는 것(로드 밸런서 등)만 퍼블릭 서브넷에 두고, 애플리케이션과 데이터베이스는 프라이빗 서브넷에 두는 계층 구조가 흔하다.
