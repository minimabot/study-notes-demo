@topic vpc/design-patterns/dev-test

이 장은 VPC를 실제로 짤 때 자주 쓰는 모양을 모아 본다. 각 구성 요소의 동작은 앞 장에서 다뤘으므로, 여기서는 **무엇을 어디에 두는지**와 **왜 그렇게 두는지**만 본다. 그림은 휴대폰에서도 보이도록 좁게 그렸다.

**개발·시험용 VPC.** 운영용이 아니므로 가용 영역 하나에 퍼블릭 서브넷 하나만 둔다. 비용과 복잡도를 낮추는 것이 목적이다.

```
VPC 10.0.0.0/16
└─ 영역 A
   └─ 퍼블릭 서브넷
      └─ EC2 (퍼블릭 IPv4)
라우팅: 0.0.0.0/0 → 인터넷 게이트웨이
```

- **라우팅.** 퍼블릭 서브넷 라우팅 테이블에 local 경로와 인터넷 게이트웨이로 가는 기본 경로가 있다. 이중 스택이면 `::/0`도 인터넷 게이트웨이로 보낸다.
- **보안 그룹.** 애플리케이션이 받는 포트만 연다. SSH·RDP는 내 네트워크의 주소 범위에서만 받는다. 아예 열지 않고 Session Manager로 접속하는 방법도 있다.
- **넣지 않는 것.** NAT 게이트웨이는 두지 않는다. 시간 요금이 붙고, 퍼블릭 서브넷의 인스턴스는 인터넷 게이트웨이로 바로 나가므로 필요 없다.
- **한계.** 영역 하나가 멈추면 환경 전체가 멈춘다. 시험 환경이라 받아들이는 위험이다. 이 구성을 그대로 운영에 올리지 않는다.

연결이 안 되면 Reachability Analyzer로 출발지와 목적지 사이 경로를 분석한다. 라우팅 테이블이나 보안 그룹 중 어디가 막는지 알려 준다. 다 쓰면 인스턴스를 먼저 종료하고 VPC를 지운다.

@topic vpc/design-patterns/web-db

**웹·DB 2계층, 가용 영역 두 곳.** 운영 환경의 기본 모양이다. 영역 두 곳에 퍼블릭·프라이빗 서브넷을 하나씩 둔다.

```
        인터넷
          │
   [로드 밸런서]  ← 두 영역의 퍼블릭 서브넷
     │        │
  영역 A    영역 B
  웹 서버    웹 서버   (퍼블릭 서브넷)
     │        │
  DB 서버    DB 서버   (프라이빗 서브넷)
     └─ S3 게이트웨이 엔드포인트
```

| 계층 | 서브넷과 경로 |
|---|---|
| 로드 밸런서·웹 | 퍼블릭. `0.0.0.0/0 → 인터넷 게이트웨이` |
| DB | 프라이빗. local 경로와 S3 접두사 목록 → 게이트웨이 엔드포인트. 인터넷 경로 없음 |

**보안 그룹 사슬.** 계층마다 보안 그룹을 따로 만들고, 앞 계층의 **보안 그룹 ID**를 출발지로 쓴다.

- 로드 밸런서: 리스너 포트를 인터넷(`0.0.0.0/0`)에서 받는다. 대상의 리스너 포트와 상태 확인 포트로 나가는 것을 허용한다.
- 웹 서버: HTTP·HTTPS를 로드 밸런서 보안 그룹에서만 받는다.
- DB 서버: DB 포트(MySQL, SQL Server 등)를 웹 서버 보안 그룹에서만 받는다.

IP 주소 대신 보안 그룹을 참조하면 Auto Scaling으로 서버가 늘고 줄어도 규칙을 고칠 필요가 없다({{ch:vpc/security-groups-nacl}}).

**S3 게이트웨이 엔드포인트.** 콘솔 마법사는 이 구성에서 S3 게이트웨이 엔드포인트를 기본으로 켠다. 요금이 없으므로 당장 S3를 안 써도 켜 두어도 된다. DB 서버가 백업을 S3에 올릴 때 인터넷 경로 없이 닿는다.

더 안전하게 하려면 웹 서버도 프라이빗 서브넷으로 옮긴다. 다음 절의 모양이다.

@topic vpc/design-patterns/private-nat

**서버를 모두 프라이빗 서브넷에.** 퍼블릭 서브넷에는 로드 밸런서 노드와 NAT 게이트웨이만 둔다. 서버는 Auto Scaling 그룹으로 두 영역의 프라이빗 서브넷에 띄운다.

```
           인터넷
             │
   인터넷 게이트웨이
     │              │
  영역 A 퍼블릭    영역 B 퍼블릭
  ALB 노드, NAT-A  ALB 노드, NAT-B
     │              │
  영역 A 프라이빗  영역 B 프라이빗
  서버 → NAT-A     서버 → NAT-B
```

- **영역마다 NAT 게이트웨이.** 프라이빗 서브넷 라우팅 테이블을 영역마다 따로 만들고, 같은 영역의 NAT 게이트웨이로 기본 경로를 보낸다. 한 영역이 멈춰도 다른 영역의 출구는 살아 있다. 영역 간 전송 요금도 생기지 않는다({{ch:vpc/nat}}).
- **IPv6.** 이중 스택이면 프라이빗 서브넷의 `::/0`은 송신 전용 인터넷 게이트웨이로 보낸다. IPv6에는 NAT가 필요 없다({{ch:vpc/internet-access}}).
- **S3.** 프라이빗 라우팅 테이블에 S3 게이트웨이 엔드포인트를 연결한다. 이걸 빼면 S3 트래픽이 NAT를 지나며 처리 요금이 붙는다({{ch:vpc/network-cost}}).
- **보안 그룹.** 서버는 로드 밸런서 보안 그룹에서 오는 리스너 포트와 상태 확인 포트만 받는다.
- **정리 순서.** Auto Scaling 그룹 → 인스턴스 → NAT 게이트웨이 → 로드 밸런서를 지운 뒤에 VPC를 지운다. 의존 관계가 남아 있으면 VPC가 지워지지 않는다.

이 모양은 운영 서버의 기본값으로 삼기 좋다. 비용은 NAT 게이트웨이 시간 요금(영역 수만큼)과 처리 요금이 더해진다. 서버가 인터넷에 나갈 일이 거의 없고 AWS 서비스만 부른다면 다음의 엔드포인트 중심 모양을 검토한다.

@topic vpc/design-patterns/hub-spoke

VPC가 여러 개가 되면 서로를 어떻게 이을지가 설계의 중심이 된다. 몇 개뿐이면 피어링으로 직접 잇고({{ch:vpc/peering}}), 많아지면 **전송 게이트웨이를 허브로 두는 허브-스포크(hub-and-spoke)** 모양을 쓴다({{ch:vpc/transit-gateway}}).

| 모양 | 전송 게이트웨이 라우팅 |
|---|---|
| 중앙 라우터 | 모든 연결이 기본 라우팅 테이블에 연결·전파. 모두가 서로 통신 |
| 격리 VPC | VPC 연결끼리는 경로가 없고 VPN(온프레미스)만 공유 |
| 격리 + 공유 서비스 | 업무 VPC는 공유 서비스 VPC와 온프레미스에만 닿고 서로는 못 닿는다 |

**중앙 집중식 송신(centralized egress).** 인터넷으로 나가는 길을 VPC마다 두지 않고 한 VPC에 모은다.

```
VPC A (프라이빗만) ─┐
VPC B (프라이빗만) ─┼─ 전송 게이트웨이
                    │
     송신 VPC C ────┘
     연결용 프라이빗 서브넷
       → NAT 게이트웨이 (퍼블릭)
       → 인터넷 게이트웨이
```

- VPC A, B의 프라이빗 라우팅 테이블은 `0.0.0.0/0`을 전송 게이트웨이로 보낸다. 전송 게이트웨이 라우팅 테이블의 기본 경로는 VPC C 연결을 가리킨다.
- **VPC C의 전송 게이트웨이 연결은 프라이빗 서브넷에 만든다.** 퍼블릭 서브넷에 만들면 트래픽이 NAT를 건너뛰고 인터넷 게이트웨이로 가는데, 인스턴스에 퍼블릭 IP가 없어 버려진다. 연결용 서브넷은 NAT 게이트웨이가 있는 퍼블릭 서브넷과 같은 영역에 둔다.
- 장점: NAT 게이트웨이 수가 VPC 수만큼 늘지 않는다. 송신 지점이 하나라 통제와 로그가 쉽다.
- 비용: 전송 게이트웨이 연결 시간 요금과 처리 요금이 더해진다. NAT 처리 요금은 그대로다. VPC가 적거나 트래픽이 아주 많으면 VPC마다 NAT를 두는 쪽이 쌀 수 있으므로 계산해 본다.

**중앙 집중식 검사(inspection).** 송신 VPC나 별도 검사 VPC에 방화벽 장비나 AWS Network Firewall을 두고, VPC 사이 트래픽과 인터넷 트래픽을 모두 그곳으로 돌린다. 상태 저장 장비가 요청과 응답을 같은 장비에서 보려면 장비가 있는 VPC 연결에 **어플라이언스 모드**를 켠다. 켜지 않으면 전송 게이트웨이가 트래픽을 출발 영역에 붙잡아 두므로 응답이 다른 영역의 장비로 가서 버려질 수 있다. 검사 서비스의 자세한 구성은 {{ch:vpc/network-protection}}에서 다룬다.

@topic vpc/design-patterns/endpoint-centric

**엔드포인트 중심 사설 접근.** 서버가 인터넷에는 나갈 일이 없고 AWS 서비스만 부른다면, NAT 게이트웨이와 인터넷 경로를 아예 두지 않는다.

```
VPC (인터넷 게이트웨이 없음)
└─ 프라이빗 서브넷 (영역 A, B)
   ├─ S3·DynamoDB → 게이트웨이 엔드포인트
   └─ ECR·Logs·STS 등
        → 인터페이스 엔드포인트
```

- **S3·DynamoDB**는 게이트웨이 엔드포인트로 연다. 요금이 없다.
- **그 밖의 서비스**는 인터페이스 엔드포인트를 서비스마다 만든다. 프라이빗 DNS를 켜면 애플리케이션 코드가 기본 서비스 이름을 그대로 써도 엔드포인트로 간다. 엔드포인트 보안 그룹에서 서버의 HTTPS(443)를 허용해야 한다({{ch:vpc/endpoints-privatelink}}).
- **엔드포인트 정책**으로 이 VPC에서 닿을 수 있는 버킷이나 리소스를 좁힌다. 버킷 정책에서 `aws:SourceVpce` 조건으로 이 엔드포인트를 거친 요청만 받게 하면 양쪽에서 막는다.
- **장점.** 인터넷으로 나가는 길이 없으므로 데이터 유출 경로가 줄어든다. NAT 시간·처리 요금도 없다.
- **비용 주의.** 인터페이스 엔드포인트는 서비스 수 × 영역 수만큼 시간 요금이 붙는다. 필요한 서비스가 아주 많고 트래픽이 적으면 NAT 하나보다 비쌀 수 있다. 여러 VPC가 있다면 공유 서비스 VPC 한 곳에 엔드포인트를 모으는 방법도 있지만, 이때는 전송 게이트웨이 처리 요금이 더해진다.
- **확인할 것.** 쓰려는 서비스가 인터페이스 엔드포인트를 지원하는지, 엔드포인트를 만들려는 영역에서 지원하는지 먼저 본다. 운영 체제 패키지 저장소처럼 인터넷에만 있는 대상이 필요하면 이 모양만으로는 안 된다. 미리 이미지(AMI)에 넣어 두거나 S3에 미러를 둔다.
