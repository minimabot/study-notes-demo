@topic vpc/security-groups-nacl/security-groups

**보안 그룹(Security Group)** 은 리소스(정확히는 네트워크 인터페이스)에 붙는 가상 방화벽이다. EC2 인스턴스에 붙이면 그 인스턴스로 들어오고 나가는 트래픽을 정한다. 추가 요금은 없다.

- **허용 규칙만 있다.** 거부 규칙은 쓸 수 없다. 규칙에 맞지 않는 트래픽은 들어오지 못한다.
- **상태 저장(stateful)이다.** 허용된 요청의 응답은 규칙과 상관없이 통과한다. 인바운드에서 443을 허용했다면 그 응답은 아웃바운드 규칙을 보지 않고 나간다. 인스턴스가 먼저 보낸 요청의 응답도 인바운드 규칙과 상관없이 들어온다.
- **새로 만든 보안 그룹** 은 인바운드 규칙이 없고(아무것도 못 들어온다), 아웃바운드는 모두 허용하는 규칙 하나를 갖는다. 아웃바운드 규칙을 모두 지우면 아무것도 나가지 못한다.
- **여러 개를 붙이면 합쳐진다.** 리소스에 보안 그룹을 여럿 붙이면 모든 규칙을 합친 하나의 규칙 집합으로 평가한다. 네트워크 인터페이스 하나에는 기본 {{fact:vpc.quota.sg-per-eni}}를 붙이고, 보안 그룹 하나에는 방향마다 기본 {{fact:vpc.quota.sg-rules}}의 규칙을 둔다.
- **규칙의 구성.** 프로토콜, 포트 범위, 그리고 출발지(인바운드)나 목적지(아웃바운드)다. 출발지·목적지에는 CIDR 대역, 관리형 접두사 목록, **다른 보안 그룹 ID** 를 쓸 수 있다.

**보안 그룹 참조.** 출발지에 보안 그룹 ID를 쓰면 "그 보안 그룹이 붙은 리소스"의 프라이빗 IP 주소에서 오는 트래픽을 허용한다. 예를 들어 DB 보안 그룹의 인바운드 3306 출발지를 앱 서버 보안 그룹으로 잡으면, 앱 서버가 늘거나 줄어도 규칙을 고칠 필요가 없다. 참조된 보안 그룹의 규칙이 복사되는 것은 아니다. 같은 VPC 안이거나, 피어링이나 전송 게이트웨이로 이어진 VPC끼리 인바운드 참조를 할 수 있다.

**기본 보안 그룹(default security group).** VPC마다 이름이 `default`인 보안 그룹이 있다. 지울 수는 없고 규칙은 고칠 수 있다. 인바운드는 같은 보안 그룹이 붙은 리소스끼리만 모두 허용하고, 아웃바운드는 모두 허용한다. 인스턴스를 만들 때 보안 그룹을 고르지 않으면 이것이 붙는다. AWS는 기본 보안 그룹 대신 용도별 보안 그룹을 만들어 쓰라고 권장한다.

**거르지 않는 트래픽.** Amazon DNS(Route 53 Resolver), DHCP, 인스턴스 메타데이터, Amazon Time Sync Service 같은 트래픽은 보안 그룹도 네트워크 ACL도 거르지 않는다. DNS 질의를 걸러야 하면 Route 53 Resolver DNS Firewall을 쓴다.

@topic vpc/security-groups-nacl/nacl

**네트워크 ACL(Network ACL)** 은 서브넷 경계에서 트래픽을 허용하거나 거부한다. 트래픽이 서브넷에 들어오고 나갈 때 평가하고, 같은 서브넷 안에서 오가는 트래픽은 평가하지 않는다. 추가 요금은 없다.

- **허용과 거부를 모두 쓴다.**
- **상태 비저장(stateless)이다.** 들어온 요청을 허용해도 그 응답이 자동으로 나가지 않는다. 응답 방향 규칙을 따로 열어야 한다(다음 절).
- **번호 순서로 평가한다.** 규칙 번호는 1부터 {{fact:vpc.nacl.rule-number.max}}까지다. 가장 낮은 번호부터 보다가 처음 맞는 규칙을 적용하고 거기서 멈춘다. 뒤에 반대 규칙이 있어도 보지 않는다. 그래서 거부 규칙은 넓은 허용 규칙보다 낮은 번호에 둔다. AWS는 나중에 끼워 넣을 수 있게 10이나 100 간격으로 번호를 매기라고 권장한다.
- **마지막은 `*` 규칙이다.** 어느 번호에도 맞지 않으면 거부한다. 이 규칙은 지울 수 없다.
- **연결.** 모든 서브넷은 네트워크 ACL 하나에 연결된다. 따로 연결하지 않으면 기본 네트워크 ACL에 연결된다. 네트워크 ACL 하나는 여러 서브넷에 연결할 수 있다.
- **할당량.** 규칙은 방향마다 기본 {{fact:vpc.quota.nacl-rules}}다.

| 종류 | 기본 규칙 |
|---|---|
| 기본 네트워크 ACL(default) | 들어오고 나가는 트래픽을 모두 허용(규칙 100, IPv6는 101) + `*` 거부 |
| 사용자 지정 네트워크 ACL(custom) | 처음에는 `*` 거부뿐이다. 규칙을 넣기 전에는 모두 막힌다 |

규칙을 바꾸면 연결된 모든 서브넷에 잠시 뒤 적용된다. 규칙을 지우면서 동시에 할당량보다 많은 규칙을 추가하면, 지우는 것만 되고 추가는 되지 않아 연결이 끊길 수 있다.

@topic vpc/security-groups-nacl/ephemeral

클라이언트가 웹 서버의 443 포트로 요청을 보내면, 응답은 서버의 443에서 **클라이언트가 고른 임시 포트(ephemeral port)** 로 돌아간다. 임시 포트 범위는 클라이언트 OS에 따라 다르다.

| 클라이언트 | 임시 포트 범위 |
|---|---|
| 많은 Linux 커널(Amazon Linux 포함) | {{fact:vpc.ephemeral.linux}} |
| Windows Server 2008 이후 | {{fact:vpc.ephemeral.windows}} |
| NAT 게이트웨이, Elastic Load Balancing, Lambda | {{fact:vpc.ephemeral.aws-services}} |

보안 그룹은 상태를 저장하니 응답 포트를 신경 쓸 필요가 없다. 네트워크 ACL은 다르다.

- **서브넷의 서버가 요청을 받는 경우:** 아웃바운드에 클라이언트 임시 포트로 가는 규칙이 있어야 응답이 나간다.
- **서브넷의 인스턴스가 요청을 보내는 경우:** 인바운드에 자기 OS의 임시 포트로 오는 규칙이 있어야 응답이 들어온다.

여러 종류의 클라이언트를 받는 서버라면 문서는 {{fact:vpc.ephemeral.aws-services}}를 열어 두는 방법을 제시한다. 그 범위 안에서 막고 싶은 포트가 있으면 거부 규칙을 더 낮은 번호에 둔다. 아래 실험에서 패킷이 어디서 막히는지 직접 확인해 보자.

| 구분 | 보안 그룹 | 네트워크 ACL |
|---|---|---|
| 적용 위치 | 리소스(네트워크 인터페이스) | 서브넷 |
| 규칙 | 허용만 | 허용과 거부 |
| 평가 | 모든 규칙을 보고 결정 | 낮은 번호부터, 처음 맞는 규칙 |
| 응답 트래픽 | 자동 허용(상태 저장) | 직접 열어야 함(상태 비저장) |
| 적용 대상 | 그 보안 그룹이 붙은 리소스 | 연결된 서브넷의 모든 리소스 |

**둘을 함께 쓴다.** AWS는 보안 그룹과 비슷한 규칙의 네트워크 ACL을 두어 방어를 한 겹 더하라고 권장한다. 문서의 예에서는 누가 실수로 보안 그룹에 SSH를 전체 허용으로 열어도, 네트워크 ACL이 관리용 주소 대역만 허용하고 있어 접근이 막힌다.

**특정 주소를 막아야 할 때.** 보안 그룹에는 거부 규칙이 없다. 웹 트래픽은 받으면서 특정 IP 대역만 막으려면 네트워크 ACL에 그 대역을 거부하는 규칙을 허용 규칙보다 낮은 번호로 넣는다. 보안 그룹만으로 하려면 막을 대역을 뺀 나머지를 모두 허용 규칙으로 나열해야 하므로 현실적이지 않다.

**포트 열기 원칙.** AWS 권장 사항은 이렇다. 22(SSH)·3389(RDP)는 특정 주소 대역에만 열고, 넓은 포트 범위를 열지 않으며, 보안 그룹을 만들고 고치는 권한을 특정 IAM 주체로 제한한다. 연결 문제를 추적할 때는 흐름 로그로 거부된 트래픽을 본다({{ch:vpc/flow-logs-monitoring}}).
