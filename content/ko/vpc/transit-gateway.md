@topic vpc/transit-gateway/concepts

**전송 게이트웨이(Transit Gateway)** 는 VPC와 온프레미스 네트워크를 한곳에서 잇는 리전 단위 네트워크 허브다. 피어링처럼 VPC 쌍마다 연결을 만들지 않는다. 모든 네트워크를 허브 하나에 붙이고, 허브의 라우팅 테이블로 누가 누구와 통신할지 정한다.

허브에 붙이는 것을 **연결(attachment)** 이라 한다. 연결은 패킷의 출발지이자 목적지다. 주요 유형은 다음과 같다.

| 연결 유형 | 쓰임 |
|---|---|
| VPC | VPC 서브넷과 전송 게이트웨이를 잇는다 |
| VPN | Site-to-Site VPN으로 온프레미스와 잇는다 |
| Direct Connect 게이트웨이 | 전송 가상 인터페이스로 Direct Connect 회선을 잇는다 |
| 피어링 | 다른 전송 게이트웨이(다른 리전 포함)와 잇는다 |
| Connect | VPC 안 SD-WAN 같은 서드 파티 어플라이언스와 GRE 터널·BGP로 잇는다 |

**VPC 연결의 동작.** VPC를 붙일 때 가용 영역마다 서브넷을 하나씩 고른다. 전송 게이트웨이는 그 서브넷에 네트워크 인터페이스를 만들고 IP 하나를 쓴다. 가용 영역을 켜면 그 영역의 다른 서브넷으로도 트래픽을 보낼 수 있다. 하지만 연결이 없는 가용 영역의 리소스는 전송 게이트웨이에 닿지 못한다. 그래서 AWS는 여러 가용 영역을 켜라고 권장한다.

AWS 설계 모범 사례는 연결용 서브넷을 따로 두라고 한다. 연결마다 작은 서브넷(예: {{fact:vpc.cidr.ipv4.smallest}})을 쓰면 워크로드용 주소가 남는다. 이 서브넷의 네트워크 ACL은 열어 두고, 필요한 필터링은 워크로드 서브넷에서 한다.

**VPC 쪽 경로는 직접 넣는다.** VPC 연결은 VPC CIDR을 전송 게이트웨이 라우팅 테이블에 전파할 수 있다. 반대 방향은 아니다. VPC 서브넷 라우팅 테이블에는 목적지 CIDR을 전송 게이트웨이(`tgw-...`)로 보내는 정적 경로를 직접 넣어야 한다.

**MTU.** VPC·Direct Connect·Connect·피어링 연결 사이 트래픽은 {{fact:vpc.tgw.mtu}}, VPN 연결은 {{fact:vpc.tgw.mtu.vpn}}다. 피어링에서 옮길 때 같은 리전 피어링의 점보 프레임({{fact:vpc.peering.mtu.intra-region}})과 크기가 달라 비대칭 트래픽의 큰 패킷이 버려질 수 있다. 문서는 두 VPC를 동시에 옮기라고 한다.

@topic vpc/transit-gateway/routing

전송 게이트웨이의 라우팅은 세 가지 개념으로 움직인다.

- **전송 게이트웨이 라우팅 테이블(transit gateway route table).** 목적지 IP에 따라 다음 홉(연결)을 정한다. 전송 게이트웨이를 만들면 기본 라우팅 테이블이 생기고, 더 만들 수 있다.
- **연결(association).** 연결(attachment) 하나는 라우팅 테이블 **하나** 와 연결된다. 그 연결에서 **들어온** 패킷은 연결된 라우팅 테이블을 보고 나간다. 라우팅 테이블 하나에는 연결이 여럿 묶일 수 있다.
- **전파(propagation).** 연결(attachment)은 자기 경로를 라우팅 테이블 **여러 개** 에 전파할 수 있다. VPC 연결은 VPC CIDR을, BGP를 쓰는 VPN·Direct Connect 게이트웨이 연결은 온프레미스에서 배운 경로를 전파한다. 전파된 경로를 골라 걸러 낼 수는 없다.

정리하면 association은 "이 연결의 트래픽은 어느 표를 보는가", propagation은 "이 연결로 가는 길을 어느 표에 적는가"다. 기본 설정에서는 새 연결이 기본 라우팅 테이블에 자동으로 연결·전파된다. 이 둘은 전송 게이트웨이를 만들 때 끌 수 있다.

**경로 종류와 우선순위.** 경로에는 직접 넣은 정적(static) 경로와 전파(propagated) 경로가 있다. 블랙홀(blackhole) 경로를 넣어 특정 목적지 트래픽을 버릴 수도 있다. 평가는 가장 구체적인 경로가 먼저다. 목적지가 같으면 정적 경로가 전파 경로보다 앞선다. 전파 경로끼리는 VPC, Direct Connect 게이트웨이, Connect, VPN 순으로 앞선다. 그래서 같은 온프레미스 대역을 Direct Connect와 VPN으로 함께 광고하면 Direct Connect 경로가 쓰이고 VPN은 예비가 된다.

**피어링 연결은 정적 경로만.** 전송 게이트웨이끼리 피어링하면 동적 경로를 주고받지 않는다. 상대 쪽 CIDR을 피어링 연결로 보내는 정적 경로를 넣어야 한다.

**분리(segmentation).** 라우팅 테이블을 나누면 전송 게이트웨이 하나 안에 서로 격리된 네트워크를 둘 수 있다. 문서는 이것을 기존 네트워크의 VRF에 빗댄다. 개발과 운영을 나누는 예는 다음과 같다.

| 라우팅 테이블 | 연결(association)된 것 | 전파(propagation)받는 것 |
|---|---|---|
| 개발용 | 개발 VPC들 | 개발 VPC, 공용 서비스 VPC, 온프레미스 |
| 운영용 | 운영 VPC들 | 운영 VPC, 공용 서비스 VPC, 온프레미스 |
| 공용·온프레미스용 | 공용 서비스 VPC, VPN·Direct Connect 게이트웨이 | 개발 VPC, 운영 VPC, 공용 서비스 VPC |

개발 표에는 운영 VPC 경로가 없으므로 개발에서 운영으로 가는 패킷은 전송 게이트웨이에서 버려진다. 반대도 같다. 개발 VPC끼리도 막고 싶다면 개발용 표에 개발 VPC를 전파하지 않는다. 다만 라우팅 테이블 수는 설계에 꼭 필요한 만큼만 두라는 것이 AWS 권장이다.

@topic vpc/transit-gateway/appliance-mode

검사용 VPC에 방화벽 같은 **상태 저장(stateful) 어플라이언스** 를 가용 영역마다 두고, VPC 사이 트래픽을 그곳으로 돌리는 구성이 있다. 여기서 문제가 생긴다.

전송 게이트웨이는 기본적으로 트래픽을 출발한 가용 영역 안에 두려 한다. 요청이 가용 영역 1에서 출발해 검사 VPC의 가용 영역 1 어플라이언스를 지났는데, 응답은 목적지가 있는 가용 영역 2에서 출발해 가용 영역 2 어플라이언스로 갈 수 있다. 그 어플라이언스는 원래 요청을 본 적이 없으므로 응답을 버린다.

**어플라이언스 모드(appliance mode)** 를 어플라이언스가 있는 VPC의 연결에 켜면, 전송 게이트웨이는 한 흐름(출발지–목적지)이 살아 있는 동안 그 VPC 연결에서 같은 가용 영역을 쓴다. 요청과 응답이 같은 어플라이언스를 지난다.

- VPC 연결에서만 켤 수 있다. 흐름의 반대편은 VPC, VPN, Connect 등 어떤 연결이어도 된다.
- 연결을 만들 때나 나중에(`ApplianceModeSupport=enable`) 켠다. 나중에 켜면 기존 흐름이 다른 가용 영역으로 다시 나뉠 수 있다.
- 어플라이언스 쪽 VPC 연결에 서브넷이 있는 가용 영역으로만 보낸다.

검사 장비를 여러 대 두고 부하를 나누는 Gateway Load Balancer는 {{ch:vpc/endpoints-privatelink}}에서 짧게 다룬다.

@topic vpc/transit-gateway/sharing

전송 게이트웨이는 계정을 넘어 쓸 수 있다. 네트워크 계정이 **AWS Resource Access Manager(AWS RAM)** 로 전송 게이트웨이를 다른 계정과 공유하면, 그 계정은 자기 VPC를 공유받은 전송 게이트웨이에 붙인다.

- AWS Organizations에서 조직 내 공유를 켰다면 조직 안 계정은 초대 수락 없이 바로 쓴다. 그렇지 않으면 RAM 콘솔에서 초대를 수락해야 한다.
- 다른 계정이 만든 연결은 **공유 연결 자동 수락(Auto accept shared attachments)** 을 켜지 않았다면 소유자가 수락해야 붙는다.
- 공유 뒤에 만들어진 연결은 어느 계정의 사용자든 삭제할 수 있다.
- 라우팅 테이블은 VPC가 아니라 전송 게이트웨이 쪽에 있다. 그래서 전송 게이트웨이를 가진 네트워크 계정에서 association·propagation을 정하는 구성이 되고, 분리 정책을 한곳에서 관리하기 쉽다.
- 가용 영역 이름(예: `us-east-1a`)은 계정마다 실제 위치가 다를 수 있다. 계정을 넘어 가용 영역을 맞출 때는 가용 영역 ID(예: `use1-az1`)를 쓴다.

**보안 그룹 참조.** 같은 전송 게이트웨이에 붙은 VPC 사이에서 보안 그룹을 참조할 수 있다. 전송 게이트웨이와 VPC 연결 양쪽에서 켜야 하고, 인바운드 규칙에서만 쓸 수 있다. 전송 게이트웨이 피어링을 넘어서는 쓸 수 없다.

@topic vpc/transit-gateway/quotas-pricing

**요금 구조.** 전송 게이트웨이에는 두 가지 요금이 붙는다. 단가는 리전마다 다르다.

| 요금 | 기준 |
|---|---|
| 연결 요금 | 연결(attachment)마다 시간당 |
| 데이터 처리 요금 | 전송 게이트웨이가 처리한 트래픽 양 |

데이터 처리 요금은 기본적으로 출발지 연결을 소유한 계정에 붙는다. 피어링은 연결 요금과 처리 요금이 없으므로, 트래픽이 아주 많은 소수의 VPC 쌍은 피어링이 더 쌀 수 있다. 대신 관리가 늘어난다({{ch:vpc/peering}}). 연결이 없는 가용 영역에서 온 트래픽을 전송 게이트웨이가 다른 가용 영역으로 넘기는 데에는 별도 전송 게이트웨이 요금이 없다.

**주요 할당량.** 별도 표기가 없으면 리전 단위다.

| 항목 | 기본값 |
|---|---|
| 계정당 전송 게이트웨이 | {{fact:vpc.tgw.per-account}} |
| 전송 게이트웨이당 연결 | {{fact:vpc.tgw.attachments}} |
| 전송 게이트웨이당 라우팅 테이블 | {{fact:vpc.tgw.route-tables}} |
| 전송 게이트웨이 전체 경로 합계 | {{fact:vpc.tgw.total-routes}} |
| VPC 하나에 붙는 전송 게이트웨이 | {{fact:vpc.tgw.per-vpc}} |
| 전송 게이트웨이당 피어링 연결 | {{fact:vpc.tgw.peering-attachments}} |
| VPC 연결 대역폭 | {{fact:vpc.tgw.bw.vpc-attachment}} |
| VPC 연결 패킷 처리량 | {{fact:vpc.tgw.pps.vpc-attachment}} |
| Connect 피어(GRE 터널) 대역폭 | {{fact:vpc.tgw.bw.connect-peer}}, 연결당 피어 {{fact:vpc.tgw.connect-peers}} |

같은 VPC에 VPC 연결을 둘 이상 만들 수는 없다. VPN 대역폭은 BGP(동적 라우팅) VPN 터널 여러 개를 등가 다중 경로(ECMP)로 묶어 늘린다. 정적 라우팅 VPN에서는 ECMP를 쓸 수 없다.

**고가용성.** 전송 게이트웨이는 설계상 고가용성이므로 가용성을 위해 더 만들 필요가 없다. 재해 복구를 위해서는 리전마다 하나씩 두고, 여러 전송 게이트웨이를 쓰면 각각 다른 ASN을 주라는 것이 AWS 권장이다.
