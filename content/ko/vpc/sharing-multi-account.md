@topic vpc/sharing-multi-account/basics

계정을 팀·서비스마다 나누면 청구와 권한은 깔끔해진다. 그런데 계정마다 VPC를 따로 만들면 VPC 수, 주소 계획, 연결이 함께 늘어난다. **VPC 공유(VPC sharing)** 는 이 문제를 줄인다. 한 계정이 VPC를 소유하고 그 안의 서브넷을 같은 조직의 다른 계정과 공유한다. 다른 계정은 공유받은 서브넷에 EC2 인스턴스, RDS 데이터베이스, Lambda 함수 같은 자기 리소스를 띄운다.

| 역할 | 뜻 |
|---|---|
| 소유자(Owner) | VPC와 서브넷을 가진 계정. 보통 중앙 네트워크 계정 |
| 참여자(Participant) | 공유받은 서브넷에 자기 리소스를 만드는 계정 |

같은 VPC 안이므로 참여자 리소스끼리는 VPC의 로컬 경로로 바로 통신한다. 그래서 AWS는 **서로 많이 통신하고 신뢰 경계가 같은 애플리케이션** 에 맞는 방식으로 설명한다. 참여자는 다른 참여자나 소유자의 리소스를 보거나 고치거나 지울 수 없다.

**준비 조건.**

- 소유자와 참여자 계정이 모두 같은 AWS Organizations 조직에 있어야 한다.
- 조직의 관리 계정에서 AWS RAM의 조직 내 리소스 공유를 켠다.
- AWS Resource Access Manager(AWS RAM)에서 **리소스 공유(resource share)** 를 만들고 서브넷을 넣는다. 대상은 계정이나 조직 단위(OU)다.

**공유할 수 없는 것.** 기본 VPC의 서브넷은 공유할 수 없다. 공유는 서브넷 단위이고, VPC 자체를 통째로 넘기지는 않는다.

**할당량.** VPC 하나가 서브넷을 공유할 수 있는 참여자 계정 수는 기본 {{fact:vpc.quota.shared-participants}}, 계정 하나가 공유받을 수 있는 서브넷 수는 기본 {{fact:vpc.quota.subnets-shared-per-account}}다. 둘 다 늘릴 수 있다. 일반 VPC 할당량도 그대로 적용된다({{ch:vpc/limits}}).

@topic vpc/sharing-multi-account/responsibilities

공유 VPC의 핵심은 **네트워크는 소유자가, 애플리케이션은 참여자가** 맡는다는 분담이다.

| 리소스 | 소유자 | 참여자 |
|---|---|---|
| VPC·서브넷 속성 | 만들고 바꾼다 | 조회만 |
| 라우팅 테이블 | 만들고 바꾼다 | 조회만 |
| 네트워크 ACL | 만들고 바꾼다 | 조회만 |
| 인터넷 게이트웨이 | 만들고 붙인다 | 조회만 |
| NAT 게이트웨이 | 만들고 지운다 | 만들 수도, 조회할 수도 없다 |
| 전송 게이트웨이 연결 | 소유자만 붙인다 | 붙일 수 없다 |
| VPC 피어링, 게이트웨이·인터페이스 엔드포인트 | 소유자 책임으로 분류된다 | 피어링은 만들거나 수락할 수 없다 |
| 네트워크 인터페이스 | 참여자 것은 조회만 | 자기가 만든 것만 관리 |
| 보안 그룹 | 참여자 것은 조회만 | 자기 것을 만들고 관리 |
| 흐름 로그 | 서브넷·VPC와 남의 인터페이스에도 만든다 | 자기 인터페이스에만 만든다 |

- 참여자는 VPC의 **기본 보안 그룹** 으로 인스턴스를 띄울 수 없다. 기본 보안 그룹은 소유자 것이기 때문이다. 자기 보안 그룹을 만들거나, 소유자가 공유한 보안 그룹을 쓴다.
- 참여자는 보안 그룹 규칙에서 다른 계정의 보안 그룹을 `계정번호/보안그룹ID` 형식으로 참조할 수 있다.
- 참여자가 만든 리소스는 **참여자 계정의 할당량** 에 잡힌다.
- 소유자는 참여자 흐름 로그를 조회하거나 지울 수 없다. 반대로 참여자는 서브넷 단위 흐름 로그를 만들 수 없다.
- VPC와 그 안 리소스의 태그는 참여자에게 공유되지 않는다.

**요금 분담.**

| 누가 | 무엇을 낸다 |
|---|---|
| 참여자 | 자기 애플리케이션 리소스(EC2, RDS 등). 가용 영역 간 전송, VPC 피어링·인터넷 게이트웨이·Direct Connect 게이트웨이를 지나는 데이터 전송 |
| 소유자 | NAT 게이트웨이, 가상 프라이빗 게이트웨이, 전송 게이트웨이, PrivateLink·VPC 엔드포인트의 시간·데이터 처리·전송 요금. 공유 VPC에서 쓰는 퍼블릭 IPv4 주소 |

같은 가용 영역 안의 데이터 전송은 어느 계정 리소스끼리든 무료다.

@topic vpc/sharing-multi-account/az-sg-unshare

**가용 영역 ID.** AWS는 계정마다 가용 영역 이름을 따로 매핑한다. 내 계정의 `us-east-1a`와 다른 계정의 `us-east-1a`는 실제로 다른 위치일 수 있다. 계정을 넘어 리소스 위치를 맞출 때는 모든 계정에서 같은 위치를 가리키는 **가용 영역 ID(AZ ID)**(예: `use1-az1`)를 쓴다. 공유 서브넷도 콘솔에서 서브넷마다 AZ ID를 보여 준다. 전송 게이트웨이를 계정 간에 공유할 때도 같은 원리가 적용된다.

**보안 그룹 공유(Shared security groups).** 소유자가 자기 VPC의 보안 그룹을 AWS RAM으로 같은 리전의 조직 내 계정과 공유할 수 있다. 소유자가 규칙을 고치면 그 그룹을 쓰는 참여자 리소스에 바로 반영된다. 공통 규칙(예: 관리용 접근)을 중앙에서 쥘 때 쓴다. {{fact:vpc.shared-sg.since}}에 추가된 기능이다.

- 공유하는 계정이 VPC와 보안 그룹을 모두 소유해야 한다.
- 기본 보안 그룹, 기본 VPC의 보안 그룹은 공유할 수 없다.
- 참여자는 공유 VPC에 보안 그룹을 만들 수는 있지만 그것을 다시 공유할 수는 없다.
- 네트워크 인터페이스에 공유받은 그룹을 함께 붙이면, 인터페이스당 보안 그룹 수 할당량은 소유자와 참여자 할당량 중 작은 값이 적용된다.

**공유를 끊을 때.** 소유자는 언제든 공유를 끊을 수 있다. 끊어도 참여자의 기존 리소스는 계속 돈다. 참여자는 새 리소스를 만들 수 없을 뿐, 기존 리소스를 고치고 지울 수는 있다. 참여자 리소스가 남아 있으면 소유자는 그 서브넷이나 VPC를 지울 수 없다.

**BPA.** 소유자가 켠 VPC 퍼블릭 액세스 차단은 참여자 트래픽에도 걸리고, 참여자는 그 설정을 바꿀 수 없다({{ch:vpc/network-protection}}).

@topic vpc/sharing-multi-account/patterns

여러 계정의 네트워크를 묶는 큰 방식은 둘이고, 함께 쓰기도 한다.

**1) 공유 VPC.** 네트워크 계정이 VPC를 만들고 서브넷을 앱 계정들과 공유한다. 라우팅, 네트워크 ACL, NAT 게이트웨이, 엔드포인트, 전송 게이트웨이 연결은 모두 네트워크 계정이 쥔다. VPC 수가 줄고 주소 계획이 단순해진다. 대신 같은 VPC 안의 참여자끼리는 로컬 경로로 열려 있으므로, 계정 사이의 분리는 보안 그룹(과 네트워크 ACL)으로 한다.

**2) 전송 게이트웨이 허브.** 각 앱 계정이 자기 VPC를 갖고, 네트워크 계정이 만든 전송 게이트웨이를 AWS RAM으로 공유받아 VPC를 붙인다. 전송 게이트웨이의 라우팅 테이블은 네트워크 계정에 있으므로, 어느 VPC가 어디와 통신할지는 네트워크 계정이 정한다. 공유 연결 자동 수락, association·propagation 같은 세부 동작은 {{ch:vpc/transit-gateway}}에서 다룬다.

| 기준 | 공유 VPC | 전송 게이트웨이 허브 |
|---|---|---|
| VPC 수 | 적다(환경별 몇 개) | 앱 계정마다 하나 이상 |
| 계정 간 분리 | 보안 그룹·네트워크 ACL | 전송 게이트웨이 라우팅 테이블로 경로 자체를 나눈다 |
| 앱 계정의 네트워크 권한 | 거의 없다(애플리케이션만) | 자기 VPC 안은 직접 관리 |
| 중앙 통제 지점 | 소유자 VPC의 라우팅·게이트웨이 | 전송 게이트웨이 라우팅 테이블, 공유 서비스 VPC |
| 요금 | VPC 안 통신은 전송 게이트웨이 요금이 없다 | 연결 시간 요금과 처리 데이터 요금이 붙는다 |

**함께 쓰기.** 실제로는 환경(운영·개발)이나 신뢰 경계별로 공유 VPC를 몇 개 두고, 그 VPC들과 온프레미스, 공유 서비스 VPC, 중앙 송신·검사 VPC를 전송 게이트웨이로 잇는 구성이 흔하다. 문서도 공유 VPC를 PrivateLink, 전송 게이트웨이, VPC 피어링과 엮어 토폴로지를 단순하게 만들 수 있다고 설명한다. 서비스 하나만 다른 계정에 내놓으면 되는 경우는 PrivateLink가 맞다({{ch:vpc/endpoints-privatelink}}).

고르는 기준을 정리하면 이렇다.

- 팀들이 서로 많이 통신하고 신뢰 경계가 같으며, 네트워크 운영을 중앙 팀이 전부 맡는다 → 공유 VPC.
- 팀마다 VPC를 따로 운영해야 하거나, 환경·조직 사이 경로를 엄격히 나눠야 하거나, 온프레미스·여러 VPC를 허브로 묶어야 한다 → 전송 게이트웨이 허브.
- 주소가 겹치지 않게 계획하는 일은 어느 쪽이든 필요하다({{ch:vpc/ip-addressing}}).
