@topic vpc/peering/basics

**VPC 피어링 연결(VPC peering connection)** 은 두 VPC를 잇는 네트워크 연결이다. 연결하면 두 VPC의 인스턴스가 프라이빗 IPv4 주소나 IPv6 주소로 서로 통신한다. 같은 네트워크 안에 있는 것처럼 보인다.

- 내 VPC끼리도, 다른 AWS 계정의 VPC와도 만들 수 있다.
- 두 VPC가 다른 리전에 있어도 된다. 이것을 **리전 간 VPC 피어링(inter-Region VPC peering)** 이라 한다.
- 게이트웨이도 VPN 연결도 아니다. VPC의 기존 인프라를 쓰고 별도 하드웨어가 없다. 그래서 단일 장애 지점이나 대역폭 병목이 없다.

만드는 순서는 다음과 같다.

1. **요청.** 요청자 VPC(requester VPC)의 소유자가 수락자 VPC(accepter VPC)의 소유자에게 연결을 요청한다. 두 VPC의 CIDR 블록은 겹치면 안 된다.
2. **수락.** 수락자 VPC 소유자가 요청을 받아들이면 연결이 활성화된다.
3. **경로 추가.** 양쪽 소유자가 **각자** 자기 VPC 라우팅 테이블에 상대 VPC의 IP 범위로 가는 경로를 넣는다. 대상은 피어링 연결(`pcx-...`)이다. 경로는 자동으로 생기지 않는다.
4. **보안 그룹 수정.** 필요하면 인스턴스 보안 그룹 규칙이 상대 VPC 트래픽을 막지 않게 고친다.
5. **DNS(선택).** 기본값에서는 상대 인스턴스의 퍼블릭 DNS 호스트 이름이 퍼블릭 IP로 풀린다. 연결에서 DNS 확인(DNS resolution)을 켜면 프라이빗 IP로 풀린다.

연결 상태는 요청 후 `pending-acceptance`가 되고, 수락하면 `provisioning`을 거쳐 `active`가 된다. 아무도 응답하지 않은 요청은 {{fact:vpc.peering.request-expiry}} 뒤 `expired`가 된다. `active` 상태에서는 어느 쪽 소유자든 연결을 삭제할 수 있지만 거절은 할 수 없다.

@topic vpc/peering/limits

피어링은 일대일 관계다. 이 성질 때문에 지원하지 않는 구성이 여럿 있고, 시험에 자주 나오는 부분이다.

**전이적 피어링(transitive peering)은 없다.** A–B, A–C가 피어링되어 있어도 B와 C는 A를 거쳐 통신할 수 없다. B와 C 사이에도 피어링이 필요하다. 직접 피어링하지 않은 VPC와는 아무 관계가 없다.

**CIDR이 겹치면 만들 수 없다.** IPv4든 IPv6든 같거나 겹치는 CIDR이 있으면 안 된다. VPC에 IPv4 CIDR 블록이 여럿 있을 때 그중 하나라도 겹치면 만들 수 없다. 겹치지 않는 블록만 쓰거나 IPv6만 쓸 생각이어도 마찬가지다. 그래서 CIDR 계획은 피어링을 만들기 전에 끝내 두어야 한다.

**에지 간 라우팅(edge to edge routing)은 없다.** 상대 VPC의 게이트웨이나 사설 연결을 빌려 쓸 수 없다. VPC A와 B가 피어링되어 있을 때 B의 리소스는 다음을 쓸 수 없다.

| A에 있는 것 | B에서 빌려 쓰기 |
|---|---|
| 인터넷 게이트웨이 | 불가 |
| NAT 장치 | 불가 |
| 회사망으로 가는 VPN 연결 | 불가 |
| 회사망으로 가는 Direct Connect 연결 | 불가 |
| S3 게이트웨이 엔드포인트 | 불가 |

그 밖의 제약도 있다.

- 두 VPC 사이에는 피어링 연결을 동시에 {{fact:vpc.peering.per-vpc-pair}}만 둘 수 있다.
- 상대 VPC의 Amazon DNS 서버에 연결하거나 질의할 수 없다.
- 피어링 연결에 단 태그는 만든 계정·리전에만 적용된다.
- 유니캐스트 역방향 경로 전달(unicast reverse path forwarding)은 지원하지 않는다.
- 공유 VPC에서는 VPC 소유자만 피어링 연결을 다룰 수 있다. 참여자 계정은 만들거나 수락할 수 없다.

이런 제약이 걸리면 전송 게이트웨이 연결로 대신할 수 있다고 문서가 안내한다. {{ch:vpc/transit-gateway}}에서 다룬다.

@topic vpc/peering/cross

**계정 간 피어링.** 요청자가 상대 계정 ID와 VPC ID를 지정해 요청하고, 상대 계정이 수락한다. 양쪽이 각자 라우팅 테이블을 고치는 것은 같다.

**보안 그룹 참조.** 같은 리전의 피어링이면 보안 그룹 규칙의 소스·대상에 상대 VPC의 보안 그룹을 쓸 수 있다.

| 상대 VPC | 규칙에 쓰는 값 |
|---|---|
| 같은 계정, 같은 리전 | 상대 보안 그룹 ID |
| 다른 계정, 같은 리전 | `계정ID/보안그룹ID` 형식 |
| 다른 리전 | 상대 VPC의 CIDR 블록 (보안 그룹 참조 불가) |

보안 그룹을 참조하려면 피어링 연결이 `active` 상태여야 한다. 콘솔은 상대 VPC의 보안 그룹을 목록에 보여 주지 않으니 ID를 직접 넣는다.

**리전 간 피어링.** 트래픽은 프라이빗 IP 공간에 머물고, AWS 시설을 떠나기 전에 암호화되며, AWS 글로벌 백본만 지난다. 공용 인터넷을 지나지 않는다. 같은 리전과 다른 점은 다음과 같다.

- MTU가 작다. 같은 리전은 {{fact:vpc.peering.mtu.intra-region}}(점보 프레임), 리전 간은 {{fact:vpc.peering.mtu.inter-region}}다.
- 상대 VPC의 프라이빗 DNS 호스트 이름을 프라이빗 IP로 풀려면, CIDR이 RFC 1918 사설 범위 안에 있어도 피어링 연결에서 DNS 확인을 켜야 한다.
- 위 표처럼 보안 그룹 참조를 쓸 수 없다.

@topic vpc/peering/cost-quotas

**요금.** 피어링 연결을 만드는 데는 요금이 없다. 같은 가용 영역 안에 머무는 피어링 트래픽은 계정이 달라도 무료다. 가용 영역을 넘거나 리전을 넘는 트래픽에는 데이터 전송 요금이 붙는다. 시간당 요금이나 처리량 요금이 없다는 점이 전송 게이트웨이와 다르다.

**할당량.**

| 항목 | 기본값 |
|---|---|
| VPC당 활성 피어링 연결 | {{fact:vpc.peering.active-per-vpc}} |
| 대기 중인 피어링 요청 | {{fact:vpc.peering.pending-requests}} |
| 수락하지 않은 요청의 만료 | {{fact:vpc.peering.request-expiry}} (조정 불가) |

**언제 피어링을 고르나.** VPC 몇 개를 서로 잇고, 트래픽이 많고, 비용을 아끼고 싶을 때 맞다. 반대로 VPC가 많아지면 모든 쌍을 잇는 완전 메시(full mesh)가 필요하다. VPC가 n개면 필요한 연결 수는 n(n−1)/2로 늘고, 각 VPC 라우팅 테이블에 경로를 일일이 넣어야 한다. 온프레미스 연결도 VPC마다 따로 두어야 한다(에지 간 라우팅 불가). 이때는 허브 하나에 모두 붙이는 {{ch:vpc/transit-gateway}}가 관리하기 쉽다. 서비스 하나만 다른 VPC에 내보이고 싶다면 네트워크 전체를 잇지 않는 {{ch:vpc/endpoints-privatelink}}도 후보다.
