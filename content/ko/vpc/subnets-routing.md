@topic vpc/subnets-routing/subnet-types

서브넷을 만들 때 정하는 것은 셋이다. 어느 VPC에 둘지, 어느 가용 영역에 둘지, 그리고 VPC 범위 안의 어느 CIDR 블록을 쓸지다. 가용 영역을 고르지 않으면 AWS가 하나를 고른다. 주소 크기 계산은 {{ch:vpc/ip-addressing}}에서 다뤘다.

주소 체계에 따라 서브넷은 **IPv4 전용**, **듀얼 스택**, **IPv6 전용** 으로 나뉜다. IPv6 전용 서브넷에 띄우는 인스턴스는 Nitro 기반이어야 한다.

**서브넷 유형은 라우팅이 정한다.** 서브넷에 "퍼블릭" 같은 스위치가 따로 있는 것이 아니다. 서브넷에 연결된 라우팅 테이블에 어떤 경로가 있느냐로 이름이 붙는다.

| 유형 | 라우팅 테이블의 모양 |
|---|---|
| 퍼블릭 서브넷(Public subnet) | 인터넷 게이트웨이로 가는 직접 경로가 있다 |
| 프라이빗 서브넷(Private subnet) | 인터넷 게이트웨이로 가는 직접 경로가 없다. 인터넷에 나가려면 NAT 장치가 필요하다 |
| VPN 전용 서브넷(VPN-only subnet) | 가상 프라이빗 게이트웨이를 거쳐 Site-to-Site VPN으로 가는 경로가 있고, 인터넷 게이트웨이 경로는 없다 |
| 격리된 서브넷(Isolated subnet) | VPC 밖으로 가는 경로가 없다. 같은 VPC 안에서만 통신한다 |

AWS는 리소스를 보호하려면 프라이빗 서브넷을 쓰라고 권장한다. 인터넷 쪽 요청은 퍼블릭 서브넷의 로드 밸런서가 받고, 애플리케이션은 프라이빗 서브넷, 데이터베이스는 더 좁은 경로만 가진 서브넷에 두는 식으로 계층을 나눈다. 이것을 가용 영역마다 반복한다.

서브넷마다 네트워크 ACL도 반드시 하나 연결된다. 만들면 VPC의 기본 네트워크 ACL에 연결되고, 기본 네트워크 ACL은 모든 트래픽을 허용한다. 자세한 내용은 {{ch:vpc/security-groups-nacl}}에서 다룬다.

@topic vpc/subnets-routing/public-ip

퍼블릭 서브넷이라도 인스턴스에 퍼블릭 IPv4 주소가 없으면 인터넷과 직접 통신하지 못한다. 이를 정하는 것이 서브넷의 **퍼블릭 IPv4 주소 자동 할당(Auto-assign public IPv4 address)** 속성이다.

| 서브넷 | 기본값 |
|---|---|
| 기본 서브넷(기본 VPC 안) | 켜짐 |
| 기본이 아닌 서브넷 | 꺼짐. 단 EC2 인스턴스 시작 마법사가 만든 서브넷은 켜짐 |

- 속성은 서브넷을 만든 뒤 콘솔의 **서브넷 설정 편집** 이나 `modify-subnet-attribute`로 바꾼다.
- 인스턴스를 띄울 때 이 속성을 덮어쓸 수 있다.
- 자동으로 받은 퍼블릭 IP는 Amazon 풀에서 빌린 것이라 계정에 남지 않는다. 떼면 풀로 돌아간다. 계속 같은 주소가 필요하면 탄력적 IP 주소(Elastic IP address)를 쓴다.
- 퍼블릭 IPv4 주소는 실행 중인 인스턴스에 붙은 것까지 모두 요금이 붙는다.
- IPv6 주소 자동 할당 속성도 따로 있다. 서브넷에 IPv6 CIDR 블록이 있어야 켤 수 있다.

인터넷 게이트웨이와 퍼블릭 IP, 보안 그룹까지 맞춰야 하는 이유는 {{ch:vpc/internet-access}}에서 다룬다.

@topic vpc/subnets-routing/route-tables

**라우팅 테이블** 은 경로(Route)의 모음이다. 경로마다 **대상(Destination)** 과 **대상(Target)** 이 있다. 한국어 문서는 둘을 같은 말로 옮기므로, 이 책에서는 Destination을 "목적지 범위", Target을 "보낼 곳"으로 풀어 쓴다. 목적지 범위는 CIDR 블록이나 접두사 목록이고, 보낼 곳은 인터넷 게이트웨이, NAT 게이트웨이, 피어링 연결, 네트워크 인터페이스 같은 것이다.

| 개념 | 뜻 |
|---|---|
| 기본 라우팅 테이블(Main route table) | VPC와 함께 생긴다. 다른 테이블에 명시적으로 연결되지 않은 모든 서브넷이 이 테이블을 쓴다. 지울 수 없다 |
| 사용자 지정 라우팅 테이블(Custom route table) | 직접 만든 테이블. 연결된 서브넷이 없을 때만 지울 수 있다 |
| 로컬 경로(Local route) | 모든 테이블에 자동으로 있는 VPC 내부 통신 경로. VPC의 CIDR 블록마다 하나씩 있다 |
| 연결(Association) | 테이블과 서브넷(또는 게이트웨이)의 묶음 |

**연결 규칙.** 서브넷은 한 번에 라우팅 테이블 하나에만 연결된다. 한 테이블은 여러 서브넷이 함께 쓸 수 있다. 서브넷을 새로 만들면 처음에는 기본 라우팅 테이블에 **암시적으로** 연결된다. VPC당 라우팅 테이블 수는 {{fact:vpc.quota.route-tables-per-vpc}}, 테이블 하나의 정적 경로 수는 {{fact:vpc.quota.routes-per-table}}가 기본 할당량이다.

**기본 라우팅 테이블을 건드리지 않는 이유.** 기본 라우팅 테이블에 `0.0.0.0/0 → 인터넷 게이트웨이`를 넣으면, 앞으로 아무 연결 없이 만드는 서브넷이 모두 퍼블릭 서브넷이 된다. 그래서 AWS는 기본 라우팅 테이블을 처음 상태(로컬 경로만)로 두고, 새 서브넷마다 사용자 지정 테이블을 명시적으로 연결하라고 권장한다. 기본 라우팅 테이블 자체를 바꿔야 한다면 사용자 지정 테이블을 서브넷 하나에 먼저 연결해 시험한 뒤, 그 테이블을 기본으로 지정한다. 기본 테이블을 바꾸면 명시적 연결이 없는 서브넷 모두의 라우팅이 함께 바뀐다.

**로컬 경로.** VPC 안의 통신은 로컬 경로가 맡는다. 로컬 경로보다 더 구체적인 경로를 넣을 수 있는데, 목적지 범위는 VPC 안 서브넷 하나의 CIDR 전체여야 하고 보낼 곳은 NAT 게이트웨이, 네트워크 인터페이스, Gateway Load Balancer 엔드포인트 중 하나여야 한다. 서브넷 사이 트래픽을 검사 장비로 돌릴 때 쓴다.

**IPv4와 IPv6는 따로.** `0.0.0.0/0`은 IPv6 주소를 포함하지 않는다. IPv6 기본 경로는 `::/0`을 따로 넣는다.

@topic vpc/subnets-routing/priority

트래픽은 목적지 IP 주소와 맞는 경로 가운데 **가장 구체적인 경로** 를 따라간다. 이것을 **가장 긴 접두사 일치(Longest prefix match)** 라고 한다. 테이블의 적힌 순서는 상관없다.

| 목적지 범위 | 보낼 곳 |
|---|---|
| 10.0.0.0/16 | local |
| 172.31.0.0/16 | 피어링 연결 |
| 0.0.0.0/0 | 인터넷 게이트웨이 |

이 테이블에서 `172.31.5.9`는 `0.0.0.0/0`과도 맞고 `172.31.0.0/16`과도 맞는다. 더 긴 `/16`이 이기므로 피어링 연결로 간다. `10.0.3.4`는 로컬 경로를 따르고, 나머지는 모두 인터넷 게이트웨이로 간다. 아무 경로와도 맞지 않으면 패킷은 버려진다.

접두사 길이가 **같은** 경로가 겹칠 때만 다음 순서를 따진다.

1. 정적 경로(인터넷 게이트웨이, NAT 게이트웨이, 네트워크 인터페이스, 게이트웨이 VPC 엔드포인트, Transit Gateway, 피어링 연결 등)
2. 접두사 목록을 참조하는 경로
3. 전파된 경로(Propagated route): Direct Connect BGP 경로 → VPN 정적 경로 → VPN BGP 경로 순

예를 들어 `172.31.0.0/24`가 가상 프라이빗 게이트웨이에서 전파되고, 같은 범위의 정적 경로가 인터넷 게이트웨이를 가리키면 정적 경로가 이긴다. 서로 다른 접두사 목록이 겹치는 범위를 다른 곳으로 보내면 AWS가 하나를 임의로 고르고, 그 뒤로는 계속 그것을 쓴다. 이런 모호함은 만들지 않는 것이 좋다.

**경로 전파(Route propagation).** VPC에 가상 프라이빗 게이트웨이를 붙이고 테이블에서 전파를 켜면 VPN 경로가 자동으로 들어온다. 전파 경로 수에는 {{fact:vpc.quota.propagated-routes}}라는 한도가 있다. VPN 라우팅은 {{ch:vpc/hybrid-vpn}}에서 다룬다.

@topic vpc/subnets-routing/gateway-route-tables

라우팅 테이블은 서브넷뿐 아니라 **인터넷 게이트웨이** 나 **가상 프라이빗 게이트웨이** 에도 연결할 수 있다. 이것을 **게이트웨이 라우팅 테이블(Gateway route table)** 이라 하고, 이 연결을 **엣지 연결(Edge association)** 이라 한다. 서브넷 라우팅 테이블이 "나가는" 트래픽을 다룬다면, 게이트웨이 라우팅 테이블은 게이트웨이로 "들어오는" 트래픽이 VPC 안에서 어디로 갈지 정한다. 들어오는 트래픽을 방화벽 같은 검사 장비로 먼저 보낼 때 쓴다.

제약이 많다.

- 보낼 곳은 `local`, Gateway Load Balancer 엔드포인트, 검사 장비의 네트워크 인터페이스만 된다.
- 목적지 범위는 VPC의 CIDR 블록 전체(로컬 경로의 보낼 곳을 바꾸는 것)나 VPC 안 서브넷 하나의 CIDR 전체만 된다. VPC 밖 범위와 접두사 목록은 안 된다.
- 전파를 켠 테이블이나, 다른 종류의 경로가 있는 테이블은 게이트웨이에 연결할 수 없다. 게이트웨이 라우팅 테이블을 기본 라우팅 테이블로 지정할 수도 없다.
- 돌아가는 트래픽도 같은 장비를 거쳐야 한다. 비대칭 라우팅은 지원하지 않는다.
- Transit Gateway를 거치는 트래픽처럼 VPC 밖의 흐름은 가로챌 수 없다.

검사 구조와 Gateway Load Balancer는 {{ch:vpc/network-protection}}에서 다룬다.
