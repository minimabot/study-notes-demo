@topic vpc/nat/overview

프라이빗 서브넷의 인스턴스도 OS 업데이트나 외부 API 호출 때문에 밖으로 나가야 할 때가 많다. 이때 **NAT 장치** 를 쓴다. NAT 장치는 인스턴스의 출발지 IPv4 주소를 자기 주소로 바꿔 내보내고, 응답이 오면 원래 주소로 되돌려 준다. 실제로는 주소와 포트를 함께 바꾼다(PAT). 기본 동작에서는 연결이 VPC 안쪽에서 시작해야 하고, 밖에서 먼저 거는 연결은 받지 않는다. NAT 게이트웨이는 이 동작을 바꿀 수 없고, NAT 인스턴스는 포트 포워딩을 직접 구성하면 예외를 만들 수 있다(아래 비교 표).

NAT 장치는 두 가지다. AWS가 관리하는 **NAT 게이트웨이(NAT gateway)** 와 EC2 인스턴스에 직접 꾸리는 **NAT 인스턴스(NAT instance)** 다. AWS는 가용성·대역폭·관리 부담 면에서 NAT 게이트웨이를 권장한다.

NAT 게이트웨이를 만들 때 연결 유형을 고른다.

| 유형 | 쓰임 |
|---|---|
| 퍼블릭(Public, 기본값) | 퍼블릭 서브넷에 만들고 탄력적 IP 주소를 붙인다. 프라이빗 서브넷 → NAT 게이트웨이 → 인터넷 게이트웨이 경로로 인터넷에 나간다 |
| 프라이빗(Private) | 탄력적 IP를 붙일 수 없다. 전송 게이트웨이나 가상 프라이빗 게이트웨이를 거쳐 다른 VPC·온프레미스로만 나간다. 인터넷 게이트웨이로 보내면 버려진다 |

두 유형 모두 먼저 인스턴스의 프라이빗 주소를 NAT 게이트웨이의 프라이빗 주소로 바꾼다. 퍼블릭 NAT 게이트웨이의 경우 그다음 인터넷 게이트웨이가 이를 탄력적 IP로 바꾼다. 그래서 퍼블릭 NAT 게이트웨이를 전송 게이트웨이 쪽으로 쓰면 상대방에게는 탄력적 IP가 아니라 NAT 게이트웨이의 프라이빗 주소가 보인다.

알아 둘 성질은 다음과 같다.

- TCP, UDP, ICMP를 지원한다.
- **보안 그룹을 붙일 수 없다.** 뒤쪽 인스턴스의 보안 그룹과 NAT 게이트웨이 서브넷의 네트워크 ACL로 거른다. NAT 게이트웨이는 포트 {{fact:vpc.ephemeral.aws-services}}를 쓰므로, 그 서브넷의 네트워크 ACL은 이 범위를 열어 두어야 한다({{ch:vpc/security-groups-nacl}}).
- **경로 제약.** VPC 피어링을 건너온 트래픽을 NAT 게이트웨이로 내보낼 수 없다. 가상 프라이빗 게이트웨이로 들어온 VPN·Direct Connect 트래픽도 마찬가지이고, 전송 게이트웨이를 쓰면 된다.
- **IPv6 워크로드.** IPv6 전용 인스턴스가 IPv4 대상과 통신해야 하면 NAT 게이트웨이의 NAT64와 Route 53 Resolver의 DNS64를 함께 쓴다. IPv6 대상으로 나가기만 하면 되면 송신 전용 인터넷 게이트웨이가 맞다({{ch:vpc/internet-access}}).

@topic vpc/nat/ha-cost

**영역 NAT 게이트웨이는 가용 영역(AZ) 하나에 속한다.** (리전 NAT 게이트웨이는 뒤에서 따로 다룬다.) 그 영역 안에서는 중복으로 구현돼 있지만, 영역 자체가 멈추면 함께 멈춘다. 그래서 영역 B·C의 서브넷이 영역 A의 NAT 게이트웨이를 출구로 삼으면, A 하나의 장애가 세 영역 모두의 인터넷 송신을 끊는 단일 장애점이 된다.

AWS가 권장하는 구성은 **영역마다 NAT 게이트웨이를 하나씩 두고, 각 영역의 프라이빗 서브넷은 같은 영역의 NAT 게이트웨이로 가게** 라우팅하는 것이다. 라우팅 테이블이 영역마다 하나씩 필요하다.

| 구성 | 가용성 | 비용 |
|---|---|---|
| NAT 게이트웨이 하나를 모든 영역이 공유 | 그 영역이 멈추면 전체가 밖으로 못 나간다 | 시간 요금이 하나뿐. 다른 영역에서 오는 트래픽에는 영역 간 전송 요금이 붙는다 |
| 영역마다 하나씩 | 한 영역 장애가 다른 영역에 번지지 않는다 | 시간 요금이 영역 수만큼. 영역 간 전송은 생기지 않는다 |

**요금 차원.** NAT 게이트웨이는 사용 가능한 시간마다, 그리고 처리한 데이터 GB마다 요금이 붙는다. 단가는 리전마다 다르므로 요금 페이지에서 확인한다. 문서가 제시하는 절감 방법은 두 가지다.

1. 영역 간 트래픽이 많으면 리소스를 NAT 게이트웨이와 같은 영역에 두거나, 리소스가 있는 영역마다 NAT 게이트웨이를 둔다.
2. NAT 게이트웨이를 지나는 트래픽 대부분이 S3·DynamoDB처럼 VPC 엔드포인트를 지원하는 AWS 서비스로 간다면 게이트웨이 엔드포인트나 인터페이스 엔드포인트를 만든다. 엔드포인트로 가는 트래픽은 NAT 게이트웨이 데이터 처리 요금이 붙지 않는다({{ch:vpc/endpoints-privatelink}}).

가용 영역당 만들 수 있는 NAT 게이트웨이 수의 기본 할당량은 {{fact:vpc.quota.natgw-per-az}}다.

@topic vpc/nat/limits-monitoring

이 절의 처리량과 상한은 영역 NAT 게이트웨이 기준이다. NAT 게이트웨이는 크기를 고르지 않는다. 처리량은 스스로 늘어나지만 상한이 있다.

| 항목 | 기본 → 최대 |
|---|---|
| 대역폭 | {{fact:vpc.natgw.bandwidth.base}} → {{fact:vpc.natgw.bandwidth.max}} |
| 패킷 | {{fact:vpc.natgw.pps.base}} → {{fact:vpc.natgw.pps.max}}. 넘으면 패킷을 버린다 |

영역 NAT 게이트웨이 하나로 이보다 더 필요하면 리소스를 여러 서브넷으로 나누고 서브넷마다 NAT 게이트웨이를 따로 둔다.

**연결 수.** IPv4 주소 하나는 고유 목적지(목적지 IP·포트·프로토콜의 조합) 하나에 동시에 {{fact:vpc.natgw.conn-per-ip}}의 연결을 맺는다. 같은 외부 API 하나로 연결이 몰리면 이 한도에 먼저 닿는다. 보조 IPv4 주소를 붙이면 한도가 주소 수만큼 늘어나며, 영역 NAT 게이트웨이 하나에 {{fact:vpc.natgw.ips.max}}까지 붙일 수 있다(리전 NAT는 아래 절). 퍼블릭 NAT 게이트웨이에 붙이는 탄력적 IP는 기본 {{fact:vpc.natgw.eip.default}}로 제한되고, 할당량 조정으로 늘린다.

**유휴 시간 초과.** 연결이 {{fact:vpc.natgw.idle-timeout}} 이상 아무 트래픽 없이 있으면 끊긴다. NAT 게이트웨이는 이어서 보내는 쪽에 RST 패킷을 돌려준다. 오래 열어 두는 연결이라면 인스턴스에서 TCP keepalive를 이보다 짧게 둔다.

**CloudWatch 지표.** NAT 게이트웨이 지표는 {{fact:vpc.natgw.metric-interval}} 간격으로 들어온다. 자주 보는 지표는 다음과 같다.

| 지표 | 읽는 법 |
|---|---|
| `ErrorPortAllocation` | 출발지 포트를 못 잡은 횟수. 0보다 크면 한 목적지로 동시 연결이 너무 많다 |
| `PacketsDropCount` | 버린 패킷 수. 전체 패킷 대비 비율로 본다 |
| `IdleTimeoutCount` | 유휴 상태로 넘어간 연결 수. 늘면 끊기는 연결이 생긴다 |
| `ActiveConnectionCount` | 지금 열린 TCP 연결 수 |
| `BytesOutToDestination` 등 | 방향별 바이트·패킷 수. 처리 데이터 요금을 가늠할 때도 쓴다 |

@topic vpc/nat/regional

**리전 NAT 게이트웨이(Regional NAT gateway)** 는 문서에 최근 추가된 방식이다. 시험 범위인지는 확인되지 않았다. 앞에서 설명한 기존 방식은 이와 구분해 **영역 NAT 게이트웨이(zonal NAT gateway)** 라고 부른다.

- **영역을 따라 늘고 준다.** 어떤 영역에 네트워크 인터페이스가 생기면 그 영역으로 확장하고, 워크로드가 없어지면 그 영역에서 빠진다. 새 영역으로 확장하는 데 {{fact:vpc.natgw.regional.expand-time}}이 걸릴 수 있고, 그동안 그 영역의 트래픽은 다른 영역에서 처리된다.
- **퍼블릭 서브넷이 필요 없다.** 자기 라우팅 테이블을 갖는 독립 리소스이고, 인터넷 게이트웨이 경로가 미리 들어 있다. 모든 영역의 프라이빗 서브넷이 같은 NAT 게이트웨이 ID 하나를 가리키면 된다.
- **주소 한도가 크다.** 영역마다 {{fact:vpc.natgw.regional.ips-per-az}}의 IP 주소를 쓸 수 있다.
- **자동 모드와 수동 모드.** 자동 모드(권장)는 AWS가 IP 주소와 영역 확장을 관리한다. 수동 모드에서는 둘 다 직접 관리한다.
- **제약.** 프라이빗 NAT는 지원하지 않는다. 다른 VPC·온프레미스로 가는 프라이빗 NAT가 필요하면 영역 NAT 게이트웨이를 쓴다.

CloudWatch 지표는 영역 NAT 게이트웨이가 `NatGatewayId` 차원만 쓰는 데 비해, 리전 NAT 게이트웨이는 `NatGatewayId`와 `AvailabilityZone`을 함께 쓴다.

@topic vpc/nat/nat-instance

NAT 인스턴스는 NAT를 하도록 꾸린 EC2 인스턴스다. 퍼블릭 서브넷에 두고 퍼블릭 IP나 탄력적 IP를 준다. 프라이빗 서브넷 라우팅 테이블은 `0.0.0.0/0` → NAT 인스턴스로 잡는다.

**소스/대상 확인(source/destination check)을 꺼야 한다.** EC2 인스턴스는 기본으로 자기가 출발지나 목적지인 트래픽만 주고받는다. NAT 인스턴스는 남의 트래픽을 대신 전달하므로 이 확인을 꺼야 동작한다. 보조 네트워크 인터페이스가 있으면 그 인터페이스도 끈다.

예전에 쓰던 NAT AMI는 지원이 끝난 Amazon Linux AMI 2018.03 기반이다. AWS는 NAT 게이트웨이로 옮기라고 권장하고, 꼭 NAT 인스턴스가 필요하면 최신 Amazon Linux로 NAT AMI를 직접 만들라고 안내한다.

| 항목 | NAT 게이트웨이(영역) | NAT 인스턴스 |
|---|---|---|
| 가용성 | 영역 안에서 중복 구현. 영역마다 두면 영역 독립 | 장애 조치를 스크립트로 직접 |
| 대역폭 | 최대 {{fact:vpc.natgw.bandwidth.max}}까지 자동 | 인스턴스 유형에 따라 |
| 관리 | AWS가 관리 | OS 패치·소프트웨어 업데이트 직접 |
| 요금 | 개수 × 시간 + 처리 데이터량 | 개수 × 시간 + 인스턴스 유형·크기 |
| 보안 그룹 | 붙일 수 없다 | 붙인다 |
| 포트 포워딩·배스천 | 지원하지 않는다 | 직접 구성하면 가능 |
| 시간 초과 시 | RST 패킷을 보낸다 | FIN 패킷을 보낸다 |
| IP 조각 | UDP만 전달. TCP·ICMP 조각은 버린다 | UDP·TCP·ICMP 조각을 재조립 |

비용만 보면 작은 NAT 인스턴스가 싸 보일 수 있다. 대신 장애 조치, 패치, 처리량 한계를 직접 떠안는다. NAT 인스턴스에서 NAT 게이트웨이로 옮길 때는 같은 서브넷에 NAT 게이트웨이를 만들고 경로 대상을 바꾼다. 같은 탄력적 IP를 쓰려면 먼저 NAT 인스턴스에서 떼어 낸다. 경로를 바꾸는 순간 기존 연결은 끊긴다.
