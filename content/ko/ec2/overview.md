@topic ec2/overview/what-is

**Amazon EC2(Amazon Elastic Compute Cloud)** 는 AWS 클라우드에서 가상 서버를 빌려 쓰는 서비스다. 가상 서버 하나를 **인스턴스(instance)** 라고 부른다. 필요한 만큼 띄우고, 부하가 줄면 줄이거나 끈다. 하드웨어를 미리 사 둘 필요가 없다.

인스턴스를 띄울 때 정하는 것:

| 구성 요소 | 하는 일 |
|---|---|
| AMI(Amazon Machine Image) | OS와 기본 소프트웨어를 담은 템플릿. 인스턴스는 AMI에서 시작한다({{ch:ec2/amis}}) |
| 인스턴스 유형(instance type) | CPU·메모리·스토리지·네트워크 성능의 조합. 어떤 호스트 하드웨어를 쓸지 정한다({{ch:ec2/instance-types}}) |
| 스토리지 | Amazon EBS 볼륨, 인스턴스 스토어 볼륨 |
| 네트워크 | 인스턴스를 넣을 VPC와 서브넷, 보안 그룹 |
| 키 페어(key pair) | 로그인 자격 증명. AWS는 공개 키를, 사용자는 프라이빗 키를 보관한다 |

**스토리지 두 종류.**

- **Amazon EBS 볼륨**: 인스턴스와 따로 존재하는 영구 스토리지다. 인스턴스를 중지해도 데이터가 남는다({{ch:ec2/ebs}}).
- **인스턴스 스토어(instance store) 볼륨**: 호스트에 붙은 임시 스토리지다. 인스턴스를 중지하거나 최대 절전 모드로 두거나 종료하면 데이터가 지워진다. 캐시나 임시 파일처럼 잃어도 되는 데이터에만 쓴다({{ch:ec2/instance-store-efs}}).

**네트워크와 접근.** 인스턴스는 VPC의 서브넷 안에서 실행되고, 서브넷은 가용 영역 하나에 속한다({{ch:vpc/subnets-routing}}). **보안 그룹(security group)** 은 인스턴스 앞에 두는 가상 방화벽이다. 어떤 프로토콜·포트·출발지 IP 범위에서 들어올 수 있는지, 어디로 나갈 수 있는지 정한다({{ch:vpc/security-groups-nacl}}). 인스턴스 안의 애플리케이션이 다른 AWS 서비스를 부를 때는 액세스 키를 넣어 두지 말고 인스턴스에 IAM 역할을 붙인다({{ch:iam/roles}}).

**과금.** 기본 방식인 온디맨드 인스턴스는 실행(`running`) 상태인 동안 초 단위로 과금하고, 최소 과금 시간은 {{fact:ec2.ondemand.billing.min}}이다. 약정 할인, 스팟, 전용 하드웨어 같은 다른 구매 방식은 {{ch:ec2/purchasing-options}}에서 다룬다.

관리 도구로는 EC2 콘솔, AWS CLI, CloudFormation, AWS SDK, AWS Tools for PowerShell, Query API가 있다.

@topic ec2/overview/regions-azs

- **리전(Region)**: 서로 떨어진 지리적 영역이다. 리전끼리는 격리되어 있어 리소스가 리전 사이에 자동으로 복제되지 않는다. 콘솔에서도 지금 고른 리전의 리소스만 보인다. 사용자와 가까운 곳, 법적 요구를 만족하는 곳을 고른다.
- **가용 영역(Availability Zone)**: 한 리전 안의 서로 격리된 여러 위치다. 코드는 리전 코드 뒤에 글자를 붙인 꼴이다(예: `ap-northeast-2a`).
- 가용 영역 코드는 계정마다 따로 실제 위치에 매핑된다. 같은 코드라도 계정이 다르면 다른 위치일 수 있다.
- 서브넷이 없는 가용 영역에는 인스턴스를 띄울 수 없다.

**여러 가용 영역에 나눠 둔다.** 모든 인스턴스를 한 위치에 두면 그 위치의 장애로 모두 멈춘다. 인스턴스를 여러 가용 영역에 나눠 두고, 한 곳의 인스턴스가 실패하면 다른 가용 영역의 인스턴스가 요청을 받도록 설계한다. 로드 밸런서와 Auto Scaling 그룹이 이 일을 맡는다({{ch:ec2/load-balancing}}, {{ch:ec2/auto-scaling}}).

처음 인스턴스를 띄울 때는 가용 영역을 직접 고르지 말고 AWS가 시스템 상태와 가용 용량을 보고 고르게 두라고 문서는 권한다. 새 인스턴스를 기존 인스턴스와 가깝게 두거나 떨어뜨려야 할 때만 직접 지정한다.

리전 밖으로 넓히는 위치도 있다.

| 위치 | 뜻 |
|---|---|
| 로컬 영역(Local Zones) | 사용자와 가까운 곳에 둔 리전의 확장. 지연 시간이 짧다 |
| Wavelength 영역 | 통신사 5G 네트워크 가장자리에 둔 컴퓨팅·스토리지 |
| AWS Outposts | 사내 데이터센터 등에 설치하는 AWS 인프라 |

로컬 영역과 Wavelength 영역은 먼저 켜고(옵트인) 그 안에 서브넷을 만들어야 쓸 수 있다.

@topic ec2/overview/shared-responsibility

보안은 AWS와 고객이 나눠 맡는다. 이를 **공동 책임 모델(shared responsibility model)** 이라고 한다.

| 누가 | 맡는 일 |
|---|---|
| AWS (클라우드 **의** 보안) | AWS 서비스를 실행하는 인프라 보호: 데이터센터, 하드웨어, 네트워크 등 |
| 고객 (클라우드 **안의** 보안) | VPC·보안 그룹으로 네트워크 접근 제어, 인스턴스 접속 자격 증명 관리, 게스트 OS와 그 위 소프트웨어의 업데이트·보안 패치, 인스턴스에 붙인 IAM 역할과 권한 |

EC2는 인스턴스 안의 OS를 고객이 관리한다. 그래서 OS 패치를 AWS가 대신 해 주는 Lambda 같은 서비스보다 고객 몫이 크다. 여러 인스턴스의 패치와 운영 작업은 AWS Systems Manager로 묶어 처리할 수 있다.

@topic ec2/overview/choosing-compute

EC2, Lambda, 컨테이너 중 무엇을 쓸지는 "어디까지 직접 관리할 것인가"로 정리할 수 있다. EC2는 OS, 인스턴스 유형, 스토리지, 네트워크를 모두 직접 고르고 관리한다. 특정 OS·커널 설정, 오래 도는 프로세스, GPU 같은 특수 하드웨어, 서버에 묶인 소프트웨어 라이선스가 필요하면 EC2가 맞다. Lambda는 서버를 관리하지 않고 이벤트마다 코드를 실행하며, 실행한 만큼 낸다. 대신 실행 시간 상한 같은 제약이 있다({{ch:lambda/overview}}). 컨테이너는 Amazon ECS나 Amazon EKS로 돌리고, 그 아래 용량은 직접 관리하는 EC2 인스턴스 클러스터로 두거나 서버를 관리하지 않는 AWS Fargate에 맡긴다. 비용은 부하 모양에 따라 달라진다. 늘 일정하게 바쁜 서버는 EC2에 약정 할인을 붙이는 쪽을, 드문드문 짧게 도는 작업은 Lambda를 먼저 따져 본다. 간단한 웹사이트를 예측 가능한 월 요금으로 돌리려면 Amazon Lightsail도 있다.
