@topic ec2/instance-types/naming

**인스턴스 유형(instance type)** 은 인스턴스가 쓸 호스트 하드웨어를 정한다. 이름은 **인스턴스 패밀리(instance family)** 와 **크기(size)** 로 이뤄진다. `c7gn.xlarge`를 나눠 보면 다음과 같다.

| 부분 | 뜻 |
|---|---|
| `c` | 시리즈(series). 여기서는 컴퓨팅 최적화 |
| `7` | 세대(generation) |
| `gn` | 옵션. `g`는 AWS Graviton 프로세서, `n`은 네트워크·EBS 최적화 |
| `xlarge` | 점 뒤의 크기. `metal`이면 베어 메탈 |

자주 보는 시리즈 글자:

- `M` 범용, `T` 버스터블 성능, `Mac` macOS
- `C` 컴퓨팅 최적화
- `R` 메모리 최적화, `X` 메모리 집약, `U` 고메모리
- `I`·`D` 스토리지 최적화(`D`는 고밀도 스토리지)
- `P`·`G` GPU 가속, `Inf` AWS Inferentia, `Trn` AWS Trainium, `F` FPGA
- `Hpc` 고성능 컴퓨팅

자주 보는 옵션 글자:

- 프로세서: `a` AMD, `g` AWS Graviton, `i` Intel
- `d` 인스턴스 스토어 볼륨이 붙어 있다
- `n` 네트워크·EBS 최적화, `b` 블록 스토리지 최적화
- `e` 추가 메모리(메모리 최적화)나 추가 스토리지(스토리지 최적화)
- `z` 높은 CPU 클럭, `flex` Flex 인스턴스

같은 패밀리 안에서 크기를 바꾸면 자원을 늘리거나 줄일 수 있다. 예를 들어 `m7g.large`와 `m7g.2xlarge`는 같은 패밀리의 다른 크기다.

@topic ec2/instance-types/families

인스턴스 유형은 용도에 따라 범주로 묶인다.

| 범주 | 맞는 일 |
|---|---|
| 범용(General purpose: M, T, Mac) | 컴퓨팅·메모리·네트워크가 고르게 필요한 일. 웹 서버, 개발·테스트 환경 등 |
| 컴퓨팅 최적화(Compute optimized: C) | CPU 성능이 중요한 일 |
| 메모리 최적화(Memory optimized: R, X, U, z1d) | 큰 데이터를 메모리에 올려 처리하는 일 |
| 스토리지 최적화(Storage optimized: I, D, H) | 로컬 스토리지에 읽기·쓰기를 많이 하는 일 |
| 가속화된 컴퓨팅(Accelerated computing: P, G, Inf, Trn, F 등) | GPU, ML 전용 칩, FPGA가 필요한 일. ML 학습·추론, 그래픽 |
| 고성능 컴퓨팅(HPC: Hpc) | 대규모 HPC 작업 |

**호스트 자원 나눠 쓰기.** CPU, 메모리, 인스턴스 스토어는 인스턴스마다 전용으로 할당된다. 네트워크와 디스크 하위 시스템은 같은 호스트의 인스턴스들이 나눠 쓴다. 모두가 최대로 쓰려 하면 똑같이 나누고, 남는 자원이 있으면 더 가져다 쓸 수 있다. I/O 성능이 높은 유형은 공유 자원 몫이 크고 성능 편차도 작다.

**CPU 성능 방식.**

- 고정 성능(fixed performance): 언제든 CPU를 끝까지 쓰고 그대로 유지한다. 동영상 인코딩, 트래픽이 많은 웹사이트, HPC처럼 늘 높은 CPU가 필요할 때 쓴다.
- 버스터블 성능(T): 기준 성능까지 쓰고, 필요할 때 그 위로 올라간다. 다음 절에서 다룬다.
- Flex(`C7i-flex`, `M7i-flex` 등): 기준 CPU 성능을 보장하고 필요하면 그 위로 올라가는, 범용 워크로드용 저비용 선택지다. 기준을 넘는 높은 사용률이 오래 이어지면 최대 버스트 성능이 서서히 낮아질 수 있다.

**현재 세대를 쓴다.** 문서는 새 인스턴스에 현재 세대 유형을 쓰라고 권한다. 이전 세대(M4, C4 등)는 그 유형에 맞춰 둔 기존 사용자를 위해 남아 있다.

@topic ec2/instance-types/burstable

T 패밀리(T8i, T4g, T3a, T3, 이전 세대 T2)는 **성능 버스트 가능 인스턴스(burstable performance instances)** 다. 많은 범용 워크로드는 평소 CPU를 조금만 쓰다가 가끔 치솟는다. T 인스턴스는 평소 **기준 사용률(baseline utilization)** 까지 쓰고, 필요할 때 그 위로 버스트한다. 버스트할 수 있는 양은 **CPU 크레딧(CPU credit)** 으로 관리한다.

- CPU 크레딧 하나는 {{fact:ec2.t.credit.def}}이다.
- 기준보다 적게 쓰면 크레딧이 쌓이고(적립), 기준보다 많이 쓰면 쌓인 크레딧을 쓴다. 계산은 밀리초 단위로 이뤄진다.
- 기준 사용률 = (시간당 얻는 크레딧 ÷ vCPU 수) ÷ 한 시간의 분 수. 예를 들어 t3.large는 {{fact:ec2.t3.large.vcpu}}에 {{fact:ec2.t3.large.earn}}를 얻어 기준이 {{fact:ec2.t3.large.baseline}}다.
- 쌓을 수 있는 한도는 {{fact:ec2.t.accrual.window}} 동안 얻는 양과 같다. 한도에 닿으면 새로 얻은 크레딧은 버려진다.
- 실행 중인 인스턴스의 크레딧은 만료되지 않는다. 인스턴스를 중지하면 T3·T3a·T4g·T8i는 쌓인 크레딧이 {{fact:ec2.t.credit.persist}} 동안 남고, T2는 바로 사라진다.

**크레딧을 다 쓰면 어떻게 되나: 두 모드.**

| 모드 | 동작 |
|---|---|
| 표준(standard) | 쌓인 크레딧만큼만 버스트한다. 다 쓰면 기준 사용률로 서서히 내려오고, 다시 쌓일 때까지 버스트하지 못한다 |
| 무제한(unlimited) | 쌓인 크레딧을 다 쓰면 잉여 크레딧(surplus credit)을 써서 계속 버스트한다. {{fact:ec2.t.unlimited.window}} 평균이 기준 이하면 추가 요금이 없고, 넘으면 넘은 만큼 vCPU-시간당 정해진 추가 요금을 낸다 |

- T3·T3a·T4g·T8i는 무제한이 기본이고, T2는 표준이 기본이다.
- 모드는 실행 중이든 중지 상태든 언제든 바꿀 수 있다. 계정의 리전별·패밀리별 기본 모드도 정할 수 있다.
- 시작 크레딧(launch credits)은 표준 모드 T2에만 있다. 다른 T 유형은 무제한 기본이라 시작하자마자 버스트할 수 있다.
- 전용 호스트에서 띄운 T3는 표준 모드만 지원한다.
- 쓴 잉여 크레딧이 청구되는 때: 하루에 얻을 수 있는 최대치를 넘었을 때, 인스턴스를 중지·종료할 때, 무제한에서 표준으로 바꿀 때.

**무제한 T와 고정 성능 중 무엇이 싼가.** 평균 CPU 사용률이 계속 높으면 무제한 T가 같은 크기의 M보다 비싸진다. 문서 예시로 t3.large는 평균 사용률 {{fact:ec2.t3.large.breakeven}}에서 m5.large와 비용이 같다(us-east-1 Linux 가격 기준이며 가격은 리전마다 다르다). T3가 CPU를 늘 최대로 버스트하면 같은 크기 M5의 {{fact:ec2.t3.full-burst.ratio}} 정도를 낸다. 평균이 이 손익분기점보다 높게 이어지면 고정 성능 유형으로 바꾼다.

**모니터링(CloudWatch 지표).**

| 지표 | 뜻 |
|---|---|
| `CPUCreditBalance` | 쌓여 있는 크레딧 |
| `CPUCreditUsage` | 쓴 크레딧 |
| `CPUSurplusCreditBalance` | 무제한 모드에서 쓴 잉여 크레딧 |
| `CPUSurplusCreditsCharged` | 갚지 못해 청구된 잉여 크레딧 |

표준 모드에서 `CPUCreditBalance`가 바닥이면 성능이 기준으로 묶인다. 무제한 모드에서 `CPUSurplusCreditsCharged`가 계속 생기면 추가 요금이 나가고 있다는 뜻이다.

@topic ec2/instance-types/nitro-graviton

**하이퍼바이저.** EC2는 Xen과 Nitro 두 하이퍼바이저를 쓴다. 현재 세대 유형 대부분은 **AWS Nitro System** 위에서 돈다. Nitro System은 AWS가 만든 하드웨어·소프트웨어 묶음이다.

- Nitro 카드: 로컬 NVMe 스토리지, 네트워크, 관리, 모니터링, 보안을 맡는다.
- Nitro 보안 칩: 메인보드에 들어 있다.
- Nitro 하이퍼바이저: 메모리와 CPU 할당만 맡는 가벼운 하이퍼바이저다. 대부분의 워크로드에서 베어 메탈과 구분하기 어려운 성능을 낸다.

`metal` 크기는 가상화 계층 없이 호스트 하드웨어를 직접 쓴다. 가상화 환경에서 쓸 수 없는 저수준 하드웨어 기능이 필요하거나, 라이선스·지원 조건상 가상화되지 않은 환경이 필요할 때 쓴다.

유형을 바꿀 때 알아 둘 Nitro의 차이: EBS 볼륨이 NVMe 블록 장치로 보이고, ENA(Elastic Network Adapter) 드라이버가 필요하다.

**AMI 가상화 유형.** 현재 세대 유형은 HVM(하드웨어 가상 머신)만 지원한다. 문서는 최고 성능을 위해 HVM AMI를 권하고, 향상된 네트워킹도 HVM AMI가 있어야 쓸 수 있다.

**프로세서.**

| 프로세서 | 특징 |
|---|---|
| Intel, AMD(`a`) | x86. 문서는 AMD 기반 유형을 비용과 성능을 함께 최적화하는 선택지로 소개한다 |
| AWS Graviton(`g`) | AWS가 설계한 Arm 프로세서. EC2 워크로드에 가장 좋은 가격 대비 성능을 내도록 설계됐다. 예: `m7g`, `c7g`, `t4g` |
| AWS Trainium, AWS Inferentia | ML 학습(Trainium)과 추론(Inferentia)용 전용 칩 |

**Graviton으로 옮길 때.** AMI는 프로세서 아키텍처별로 만들어진다. x86 인스턴스의 유형을 Arm 유형으로 그냥 바꿀 수는 없다. Arm용 AMI로 새 인스턴스를 띄우고, 애플리케이션과 의존 라이브러리가 Arm에서 제대로 도는지 시험한 뒤 옮긴다.

@topic ec2/instance-types/right-sizing

**고르는 방법.** 문서는 후보 유형으로 직접 인스턴스를 띄워 자기 애플리케이션으로 벤치마크하라고 권한다. 초 단위로 과금되니 여러 유형을 시험하는 비용이 작고, 고른 뒤에도 나중에 유형을 바꿀 수 있다. 콘솔의 인스턴스 유형 찾기 기능으로 리전, vCPU, 메모리 같은 조건에 맞는 유형을 걸러 볼 수도 있다.

**AWS Compute Optimizer.** 옵트인하면 기존 인스턴스의 사양과 사용률 지표를 분석해 더 맞는 유형을 추천한다(최대 세 가지 선택지). 결과는 다음처럼 분류된다.

| 분류 | 뜻 |
|---|---|
| 과소 프로비저닝(Under-provisioned) | CPU·메모리·네트워크 중 하나라도 워크로드 요구에 못 미친다. 성능이 나빠질 수 있다 |
| 과다 프로비저닝(Over-provisioned) | 줄여도 되는 사양이 하나 이상 있고 모자란 사양은 없다. 비용이 새고 있다 |
| 최적화(Optimized) | 모든 사양이 요구에 맞고 남지도 않는다. 새 세대를 추천할 수 있다 |
| 없음(None) | 추천이 없다. 옵트인 직후, 실행 기간이 짧을 때, 지원하지 않는 유형일 때 |

추천을 따르기 전에 볼 것:

- 추천은 최근 {{fact:ec2.co.lookback}} 기록을 바탕으로 하며 앞으로의 사용을 예측하지 않는다. 앞으로의 요구도 따진다.
- 평균만 보지 말고 피크를 본다. CloudWatch에서 평균·최대·백분위수를 함께 확인한다.
- 버스터블 유형을 추천받았다면 새 유형의 vCPU로도 버스트를 이어 갈 수 있는지 본다.
- 예약 인스턴스를 갖고 있으면 유형 변경이 예약 인스턴스 사용률·적용 범위에 미치는 영향을 먼저 본다({{ch:ec2/purchasing-options}}).
- 성능 위험 등급을 확인하고, 바꾸기 전후로 부하 시험을 한다.

**유형 바꾸기(크기 조정).** 수직 확장(scale up/down)은 유형을 바꾸는 것이고, 수평 확장은 인스턴스 수를 늘리는 것이다({{ch:ec2/auto-scaling}}). 유형을 바꾸면 그때부터 새 유형 요금을 낸다. 스토리지만 늘리려면 유형을 바꾸지 말고 EBS 볼륨을 붙인다.

| 루트 볼륨 | 새 유형과 호환 | 방법 |
|---|---|---|
| EBS | 호환된다 | 인스턴스를 중지하고 유형을 바꾼 뒤 시작한다 |
| EBS | 호환되지 않는다 | 새 인스턴스를 띄워 옮긴다(마이그레이션) |
| 인스턴스 스토어 | 해당 없음 | 새 인스턴스를 띄워 옮긴다 |

- 중지해야 하므로 중단 시간을 계획한다. 중지·시작하면 새 하드웨어로 옮겨지고, 탄력적 IP가 아닌 퍼블릭 IPv4 주소는 바뀐다.
- 호환성을 가르는 것: 가상화 유형(PV AMI는 HVM 전용 유형으로 못 바꾼다), 프로세서 아키텍처(Arm과 x86 사이 불가), 네트워크 어댑터·ENA 드라이버, NVMe 드라이버(Linux는 `/etc/fstab`에 장치 이름 대신 UUID나 레이블을 쓴다), 이미 붙은 EBS 볼륨 수, NitroTPM.
- 스팟 인스턴스는 유형을 바꿀 수 없다.
- Auto Scaling 그룹에 속한 인스턴스를 중지하면 그룹이 비정상으로 보고 교체할 수 있다. 바꾸는 동안 그룹의 조정 프로세스를 일시 중지한다.
