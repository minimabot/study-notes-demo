@topic ec2/auto-scaling/groups

**Amazon EC2 Auto Scaling 그룹(Auto Scaling group)** 은 EC2 인스턴스를 하나의 논리적 묶음으로 다룬다. 하는 일은 두 가지다. 인스턴스 수를 정한 만큼 **유지** 하는 것, 그리고 수요에 맞춰 수를 **바꾸는** 것이다.

| 값 | 뜻 |
|---|---|
| 원하는 용량(desired capacity) | 지금 있어야 할 인스턴스 수. 직접 바꾸거나 조정 정책이 바꾼다 |
| 최소 용량(minimum) | 원하는 용량이 이 아래로 내려가지 않는다 |
| 최대 용량(maximum) | 원하는 용량이 이 위로 올라가지 않는다 |

- 그룹은 원하는 용량만큼 인스턴스를 띄운 뒤, 주기적인 상태 확인으로 그 수를 지킨다. 인스턴스가 비정상이 되면 종료하고 새로 띄운다. 스팟 중단이나 사람이 직접 종료한 경우도 같다.
- 조정 정책은 원하는 용량을 최소~최대 사이에서 바꾸고, 그에 맞춰 인스턴스를 띄우거나 종료한다.

**시작 템플릿(launch template).** 그룹이 띄울 인스턴스의 AMI, 유형, 키 페어, 보안 그룹, 사용자 데이터 등을 담는다({{ch:ec2/launch-user-data}}). 예전 방식인 시작 구성(launch configuration)보다 시작 템플릿을 쓴다. 여러 인스턴스 유형과 온디맨드·스팟을 섞는 것도 시작 템플릿에서만 된다.

**여러 가용 영역에 고르게.** 그룹에 여러 가용 영역의 서브넷을 주면 원하는 용량을 영역에 나눠 띄우고, 확장·축소 때도 균형을 맞춘다. 한 영역이 고장 나면 남은 영역에 새 인스턴스를 띄운다. 영역 하나에서 시작이 실패할 때의 동작은 **가용 영역 분산 전략** 으로 정한다.
- 균형 최선(balanced best effort): 실패한 영역 대신 다른 정상 영역에 띄운다. 영역 중복이 중요하고 잠시 불균형해도 되는 앱용.
- 균형만(balanced only): 실패한 영역에 계속 시도한다. 쿼럼 기반 작업처럼 영역마다 같은 수가 꼭 필요할 때.

**로드 밸런서와 붙이기.** 그룹에 ALB·NLB 대상 그룹을 붙이면, 그룹이 띄우는 인스턴스를 대상 그룹에 알아서 등록하고 종료할 인스턴스는 등록 취소한다({{ch:ec2/load-balancing}}). 여러 가용 영역의 그룹과 로드 밸런서를 함께 쓰는 것이 EC2 고가용성의 기본 구성이다.

@topic ec2/auto-scaling/health

**상태 확인 종류.** 그룹은 `InService` 인스턴스가 정상인지 다음으로 판단한다.

| 종류 | 확인하는 것 | 기본 |
|---|---|---|
| EC2 상태 확인 | 인스턴스가 `running`인지, 인스턴스·시스템 상태 검사가 `impaired`인지, 예정된 이벤트가 있는지 | 늘 켜짐 |
| ELB 상태 확인 | 로드 밸런서가 인스턴스를 정상으로 보는지. 앱이 요청을 받을 수 있는지 | 꺼짐. 그룹에서 켜야 한다 |

- 그 밖에 VPC Lattice, Amazon EBS, 사용자 지정 상태 확인(`SetInstanceHealth` API로 직접 알림)도 쓸 수 있다.
- **ELB 상태 확인은 기본으로 무시된다.** 로드 밸런서를 붙였다고 ELB 결과로 교체하지 않는다. 앱 프로세스가 죽어도 인스턴스는 `running`이라 EC2 상태 확인으로는 못 잡는다. 그래서 웹 앱이면 ELB 상태 확인을 켠다.
- EC2 상태 검사가 잠깐 실패하면 AWS가 고칠 시간을 몇 분 준다. 반면 `running`이 아닌 상태(`stopping`, `stopped`, `shutting-down`, `terminated`)가 되면 바로 비정상으로 보고 교체한다. 그룹 안 인스턴스를 직접 중지하면 교체되는 이유다({{ch:ec2/instance-lifecycle}}).
- 비정상 인스턴스는 휴지 기간을 기다리지 않고 교체한다. 연결 드레이닝이 켜져 있으면 처리 중인 요청을 기다린 뒤 종료한다.

**상태 확인 유예 기간(health check grace period).** 새 인스턴스가 `InService`가 된 뒤, 비정상 판정으로 종료하기 전까지 기다리는 최소 시간이다. 앱이 아직 초기화 중이라 ELB 상태 확인에 실패하는 것을 비정상으로 오판하지 않게 한다.
- 콘솔로 만들면 기본 {{fact:ec2.asg.grace.console}}, CLI·SDK로 만들면 기본 {{fact:ec2.asg.grace.api}}이다.
- 너무 길면 진짜 고장을 늦게 잡는다. 시작 수명 주기 후크로 초기화를 끝낸 뒤 `InService`로 보내면 유예 기간을 0으로 둬도 된다.
- 유예 기간 중이라도 `running`이 아니게 되면 바로 교체한다.

새 인스턴스가 띄워지자마자 비정상으로 종료되고 다시 띄워지는 일이 반복되면, 유예 기간이 앱 시작 시간보다 짧지 않은지, 로드 밸런서 상태 확인 경로와 보안 그룹이 맞는지 먼저 본다.

@topic ec2/auto-scaling/policies

조정 방법은 다섯 가지다.

| 방법 | 언제 |
|---|---|
| 대상 추적(target tracking) | 지표를 목표값 근처에 두고 싶을 때. 문서가 가장 먼저 권한다 |
| 단계(step) | 경보가 넘은 정도에 따라 다르게 늘리고 줄이고 싶을 때 |
| 단순(simple) | 경보 하나에 조정 한 번, 그다음 휴지 기간. 문서는 쓰지 말라고 권한다 |
| 예약(scheduled) | 요일·시간처럼 미리 아는 변화 |
| 예측(predictive) | 매일·매주 반복되는 패턴을 미리 맞출 때 |

**대상 추적.** 지표와 목표값을 정하면 Auto Scaling이 CloudWatch 경보를 만들고 관리한다. 온도 조절기처럼 지표를 목표값 근처로 돌린다.
- 미리 정의된 지표: `ASGAverageCPUUtilization`, `ASGAverageNetworkIn`, `ASGAverageNetworkOut`, `ALBRequestCountPerTarget`(대상당 ALB 요청 수).
- 지표는 인스턴스 수에 비례해 늘고 줄어야 한다. 로드 밸런서가 받은 **전체** 요청 수나 지연 시간, SQS 큐의 전체 메시지 수는 맞지 않는다. 큐라면 "인스턴스당 메시지 수" 같은 지표를 만든다.
- 목표값은 예상 밖 증가를 버틸 여유를 두고 되도록 높게 잡는다.
- 정책이 만든 CloudWatch 경보를 직접 고치거나 지우지 않는다.
- 여러 대상 추적 정책을 함께 두면, 하나라도 확장이 필요하면 확장하고, **모두** 축소해도 될 때만 축소한다. 가용성을 먼저 지키기 위해서다.
- 트래픽이 줄 때는 더 **천천히** 축소한다. 인스턴스 수를 계산할 때 소수점이 나오면 넉넉한 쪽으로 반올림한다.
- 지표 값이 목표보다 **낮을 때** 확장하는 정책은 만들 수 없다.
- EC2 지표를 쓰면 세부 모니터링(detailed monitoring)을 켜서 지표가 더 자주 나오게 하라고 문서가 권한다.

**단계·단순 조정.** CloudWatch 경보를 직접 만들고 그 경보에 정책을 붙인다. 단계 조정은 "경보 값이 이 구간이면 몇 대, 저 구간이면 몇 대"처럼 여러 단계를 둔다. 단순 조정은 조정 한 번 뒤 휴지 기간이 끝날 때까지 다음 조정을 하지 않는다.

**예약 조정.** 정한 시각(한 번 또는 cron 반복)에 원하는·최소·최대 용량을 바꾼다. 반복 일정은 기본 UTC이고 시간대를 지정할 수 있다. 예약 조정 뒤에도 동적 조정 정책은 계속 동작한다.

**예측 조정.** 과거 부하에서 일·주 단위 반복 패턴을 찾아 앞으로 필요한 용량을 예측하고 **미리** 늘린다.
- 지표 기록이 최소 {{fact:ec2.asg.predictive.min-history}} 있어야 예측을 시작한다. 최대 {{fact:ec2.asg.predictive.lookback}}의 기록을 분석해 앞으로 {{fact:ec2.asg.predictive.horizon}}을 시간 단위로 예측하고, {{fact:ec2.asg.predictive.refresh}}마다 갱신한다.
- 처음에는 "예측만(forecast only)" 모드로 예측이 맞는지 본 뒤 "예측 및 조정(forecast and scale)"으로 바꾼다.
- 예측 조정은 늘리기만 하고 **줄이지는 않는다.** 줄이려면 동적 조정 정책을 함께 둔다.
- 업무 시간에 몰리고 밤에 비는 앱, 초기화가 오래 걸리는 앱에 맞다.

**휴지 기간과 인스턴스 워밍업.** 둘 다 "방금 한 조정의 효과가 지표에 나타나기 전에 또 조정하지 않게" 하는 장치다.
- **휴지 기간(cooldown)**: 단순 조정에만 적용된다. 기본 {{fact:ec2.asg.cooldown.default}}이다. 대상 추적·단계 조정과 예약 동작은 휴지 기간을 기다리지 않는다.
- **기본 인스턴스 워밍업(default instance warmup)**: 새 인스턴스가 `InService`가 된 뒤 이 시간 동안은 그룹의 집계 지표에 넣지 않는다. 시작 직후 CPU가 잠깐 치솟는 것을 부하로 오해해 더 늘리지 않게 한다. 기본으로 켜져 있지 않으며, 문서는 켜라고 강하게 권한다. 값을 모르면 {{fact:ec2.asg.warmup.start}}부터 시작해 조정한다.
- 워밍업 중인 인스턴스는 다음 확장 계산에서 이미 있는 용량으로 친다. 그래서 같은 부하에 경보가 여러 번 울려도 한 번만 늘린다.
- 확장이 진행 중이면 대상 추적·단계 정책의 **축소는 워밍업이 끝날 때까지 막힌다.** 늘리기는 빠르게, 줄이기는 조심스럽게 하는 이유다.

아래 실험에서 목표 CPU와 워밍업을 바꿔 가며 원하는 용량이 어떻게 따라가는지 본다.

@topic ec2/auto-scaling/lifecycle-warm-refresh

**수명 주기 후크(lifecycle hook).** 인스턴스가 시작되거나 종료될 때 대기 상태(`Pending:Wait`, `Terminating:Wait`)에 두고, 그동안 사용자 작업을 한다.
- 시작 후크: 소프트웨어 설치, 설정 내려받기 등을 끝낸 뒤 `InService`로 보낸다.
- 종료 후크: 로그를 내보내거나 데이터를 옮긴 뒤 종료한다. 문서는 종료 후크에 짧은 제한 시간을 권한다.
- 제한 시간 기본값은 {{fact:ec2.asg.hook.timeout.default}}이고 최대 {{fact:ec2.asg.hook.timeout.max}}까지 정한다. 더 필요하면 하트비트(`RecordLifecycleActionHeartbeat`)로 다시 늘리되, 전역 제한 시간을 넘을 수 없다. 전역 제한은 {{fact:ec2.asg.hook.global}}과 제한 시간의 {{fact:ec2.asg.hook.global.multiplier}} 가운데 작은 값이다.
- 작업을 마치면 `CompleteLifecycleAction`으로 `CONTINUE` 또는 `ABANDON`을 보낸다. 시작 중 `ABANDON`이면 인스턴스를 종료한다. 제한 시간이 지나면 정해 둔 기본 결과를 따른다.
- 알림은 EventBridge, SNS, SQS로 받아 Lambda나 스크립트가 처리한다. 인스턴스 안에서는 IMDS로 대상 수명 주기 상태를 읽을 수 있다.

**웜 풀(warm pool).** 미리 초기화해 둔 인스턴스 묶음을 그룹 옆에 둔다. 확장할 때 처음부터 띄우지 않고 웜 풀에서 꺼내 빨리 서비스에 넣는다. 첫 부팅이 아주 오래 걸리는 앱용이다.
- 웜 풀 인스턴스 상태: `Stopped`(가장 싸다. EBS 볼륨과 탄력적 IP 요금만 낸다), `Hibernated`(메모리를 보존), `Running`(권장하지 않음).
- 기본 크기는 최대 용량과 원하는 용량의 차이다. 따로 정할 수도 있다.
- 시작 후크와 함께 써서 초기화가 끝난 뒤에 중지되도록 한다. 루트가 인스턴스 스토어인 인스턴스는 중지·최대 절전을 못 하므로 웜 풀에서 그 상태로 둘 수 없다.
- 부팅 지연이 문제가 아니면 비용만 늘리므로 만들지 않는다.

**인스턴스 새로 고침(instance refresh).** 새 AMI나 새 시작 템플릿 버전으로 그룹의 인스턴스를 일괄 교체한다.
- 최소 정상 비율(기본 {{fact:ec2.asg.refresh.min-healthy}})과 최대 정상 비율(기본 {{fact:ec2.asg.refresh.max-healthy}})로 한 번에 몇 대를 바꿀지 정한다. 최소 정상 비율을 {{raw:100%}}로 두면 새 인스턴스를 먼저 띄운 뒤 옛 인스턴스를 끝내 원하는 용량이 줄지 않는다. 최소와 최대를 모두 {{raw:100%}}로 두면 한 대씩 이렇게 바꾼다.
- 체크포인트(일정 비율 교체 뒤 멈춤), 굽기 시간(bake time), 일치 건너뛰기(skip matching, 이미 새 설정인 인스턴스는 건너뜀), CloudWatch 경보에 따른 자동 롤백을 쓸 수 있다.
- 새 인스턴스의 워밍업은 기본 인스턴스 워밍업, 없으면 상태 확인 유예 기간을 쓴다.
- 새 AMI를 미리 굽는 과정은 {{ch:ec2/amis}}.

@topic ec2/auto-scaling/mixed-termination

**혼합 인스턴스 그룹(mixed instances group).** 한 그룹에서 여러 인스턴스 유형과 온디맨드·스팟을 함께 쓴다. 시작 템플릿이 필요하다.
- **온디맨드 기본 용량(On-Demand base capacity)**: 처음 몇 대까지는 온디맨드로 채운다.
- **기본 용량을 넘는 부분의 온디맨드 비율(On-Demand percentage above base)**: 나머지를 온디맨드와 스팟으로 어떤 비율로 나눌지 정한다.
- 인스턴스 유형을 직접 여러 개 적거나, vCPU·메모리 같은 속성으로 고르게 한다(속성 기반 선택). 유형이 많을수록 스팟 용량 풀이 많아져 중단이 줄어든다.
- 스팟 할당 전략은 `price-capacity-optimized`가 권장값이다. 전략별 차이와 중단 대응은 {{ch:ec2/spot}}에서 다룬다.
- **용량 재조정(Capacity Rebalancing)**: 스팟 인스턴스에 리밸런싱 권고가 오면 대체 인스턴스를 먼저 띄우고, 새 인스턴스가 상태 확인을 통과한 뒤 위험한 인스턴스를 끝낸다. 끄면 실제로 중단되어 상태 확인에 실패한 뒤에야 교체한다.
- 예약 인스턴스나 Savings Plans는 그룹의 온디맨드 인스턴스 요금에 그대로 적용된다({{ch:ec2/purchasing-options}}).

**종료 정책(termination policy).** 축소할 때 어느 인스턴스를 먼저 끝낼지 정한다.
- 무엇보다 **가용 영역 균형** 이 먼저다. 인스턴스가 가장 많은(그리고 보호되지 않은 인스턴스가 있는) 영역에서 고른다.
- 기본 정책은 그 영역 안에서 **옛 설정** 을 쓰는 인스턴스부터 끝낸다. 시작 구성으로 띄운 것, 다른 시작 템플릿으로 띄운 것, 현재 템플릿의 가장 오래된 버전으로 띄운 것 순이다. 그다음은 다음 과금 시간에 가장 가까운 인스턴스, 그래도 같으면 무작위다.
- 혼합 인스턴스 그룹은 먼저 온디맨드·스팟 비율과 할당 전략에 맞게 끝낼 쪽을 고른다.
- 다른 정책: `OldestInstance`, `NewestInstance`, `OldestLaunchTemplate`, `ClosestToNextInstanceHour`, `AllocationStrategy`. Lambda로 직접 만든 사용자 지정 종료 정책도 쓸 수 있다.
- 비정상 인스턴스는 종료 정책을 거치지 않고 교체된다.

**축소 보호(instance scale-in protection).** 특정 인스턴스를 축소 대상에서 뺀다. 긴 작업을 처리 중인 인스턴스 등에 쓴다. 기본은 꺼져 있다. 상태 확인에 따른 교체, 스팟 중단, 사람이 콘솔·CLI로 직접 종료하는 것은 막지 못한다. 실수로 종료하는 것은 EC2 종료 방지로 막는다({{ch:ec2/instance-lifecycle}}).

@topic ec2/auto-scaling/new-features

2025년 이후 추가된 기능이다. 시험 범위인지 알 수 없다.

- **루트 볼륨 교체 전략(replace root volume).** 인스턴스 새로 고침에서 인스턴스를 끝내지 않고 루트 EBS 볼륨만 새 AMI로 바꾼다. 네트워크 인터페이스, 루트가 아닌 EBS 볼륨, 인스턴스 스토어 데이터가 남는다. 혼합 인스턴스 정책에 `ImageId` 재정의가 있어야 하는 등 조건이 있다.
- **인스턴스 수명 주기 정책(instance lifecycle policy).** 종료 수명 주기 후크가 제한 시간을 넘기거나 버려졌을 때 어떻게 할지 정한다. 기본적으로 종료 후크는 최선 노력이라, 후크가 실패하면 그대로 종료한다.
- **가용 영역 분산 전략 "예약 후 균형(reservations then balanced)".** 그룹에 연결한 용량 예약(Capacity Reservation)을 먼저 채우고 남은 용량을 영역에 고르게 나눈다. 축소할 때는 예약 밖 인스턴스부터 끝낸다.
