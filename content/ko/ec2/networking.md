@topic ec2/networking/eni

**탄력적 네트워크 인터페이스(ENI, Elastic Network Interface)** 는 VPC 안의 가상 네트워크 카드다. 콘솔과 API에서는 그냥 "네트워크 인터페이스"라고 부른다. 서브넷과 IP 주소 설계 자체는 {{ch:vpc/ip-addressing}}에서 다룬다.

네트워크 인터페이스가 가지는 속성:

| 속성 | 내용 |
|---|---|
| 프라이빗 IPv4 | 기본(primary) 주소 하나 + 보조(secondary) 주소 여러 개. 모두 서브넷 범위에서 받는다 |
| IPv6 | 서브넷에 IPv6 범위가 있으면 하나 이상 |
| 탄력적 IP | 프라이빗 IPv4 주소마다 하나씩 연결할 수 있다 |
| 보안 그룹 | 인터페이스 단위로 붙는다({{ch:vpc/security-groups-nacl}}) |
| MAC 주소, 소스/대상 확인 플래그, 설명 | 인터페이스를 옮기면 함께 따라간다 |

**기본과 보조 인터페이스.**
- 인스턴스마다 **기본 네트워크 인터페이스(primary network interface)** 가 하나 있고, 떼어 낼 수 없다.
- **보조 네트워크 인터페이스** 는 만들어 붙이고 뗄 수 있다. 붙일 수 있는 개수는 인스턴스 유형마다 다르다.
- 붙이는 시점: 실행 중(hot attach), 중지 중(warm attach), 시작할 때(cold attach). Amazon Linux와 Windows Server가 아닌 OS는 hot/warm 연결 뒤 인터페이스와 라우팅을 직접 올려야 할 수 있다.

**가용 영역 규칙.** 네트워크 인터페이스는 **같은 가용 영역** 의 인스턴스에만 붙는다. 서브넷은 달라도 되고, 같은 계정의 다른 VPC 인터페이스도 가용 영역만 같으면 붙일 수 있다(다중 홈 인스턴스). 다른 계정의 VPC에 걸친 다중 홈은 안 된다.

**보조 프라이빗 IP.** 기본 프라이빗 IP는 인스턴스에 묶이지만, 보조 프라이빗 IPv4는 다른 인스턴스로 다시 지정할 수 있다. 같은 서브넷의 인터페이스를 여러 개 붙이면 비대칭 라우팅 같은 문제가 생길 수 있으므로, 주소만 더 필요하면 기본 인터페이스에 보조 IP를 더하는 쪽을 문서가 권한다.

**자주 나오는 쓰임새.**
- **관리망 분리.** eth0은 공개 트래픽, eth1은 더 엄격한 보안 그룹이 붙은 관리 서브넷에 둔다.
- **네트워크·보안 어플라이언스.** NAT, 방화벽, 프록시처럼 인터페이스마다 다른 보안 그룹과 주소가 필요한 경우. 라우팅·NAT·방화벽 역할을 하면 **소스/대상 확인(source/destination check)** 을 꺼야 한다(기본은 켜짐).
- **저비용 장애 조치.** 인스턴스가 고장 나면 인터페이스(또는 보조 IP)를 대기 인스턴스로 옮긴다. 프라이빗 IP, 탄력적 IP, MAC 주소가 함께 옮겨 가므로 라우팅 테이블이나 DNS를 바꾸지 않아도 된다. 옮기는 동안은 잠깐 끊긴다. 자동화된 고가용성은 Auto Scaling과 로드 밸런서로 만든다({{ch:ec2/auto-scaling}}).

**하지 못하는 것.** 인터페이스를 더 붙여도(NIC 팀 구성 등) 인스턴스의 네트워크 대역폭은 늘지 않는다. 대역폭은 인스턴스 유형이 정한다(아래 절).

- **종료 동작.** 인터페이스마다 인스턴스를 종료할 때 함께 지울지 정한다.
- **요청자 관리형 인터페이스(requester-managed).** 로드 밸런서, Lambda, NAT 게이트웨이 같은 서비스가 계정 안에 만든 인터페이스다. 직접 떼거나 지울 수 없고, 그 리소스를 지우면 함께 지워진다.

@topic ec2/networking/public-ip-eip

**퍼블릭 IPv4 주소.** 서브넷 설정에 따라 인스턴스의 기본 인터페이스에 자동으로 붙는다. 인스턴스를 중지, 최대 절전, 종료하면 놓아주고, 다시 시작하면 새 주소를 받는다. 그래서 주소가 바뀌면 안 되는 서비스에는 맞지 않는다.

**탄력적 IP 주소(Elastic IP address).** 계정에 할당해 두고 놓아줄 때까지 계속 가지는 고정 퍼블릭 IPv4다. 개념과 인터넷 게이트웨이 경로는 {{ch:vpc/internet-access}}에 있다. EC2 쪽에서 알아 둘 점:

- 리전에 묶인다. 다른 리전으로 옮길 수 없다. IPv6용 탄력적 IP는 없다.
- 인스턴스나 네트워크 인터페이스에 연결한다. 이미 퍼블릭 IPv4가 있던 인스턴스에 연결하면 원래 퍼블릭 IPv4는 풀로 돌아가고 다시 쓸 수 없다. 퍼블릭 DNS 이름도 탄력적 IP에 맞게 바뀐다.
- 연결을 끊고 다른 인스턴스에 붙여 장애를 가릴 수 있다. 옮기기 전에 기존 연결을 정리한다.
- 보조 인터페이스나 보조 프라이빗 IP에 탄력적 IP가 연결돼 있으면, 중지 후 시작해도 새 퍼블릭 IPv4를 받지 않는다. 인터페이스가 둘 이상 붙어 있을 때도 마찬가지다.
- 기본 할당량은 리전당 {{fact:vpc.quota.eip-per-region}}이다. 문서는 탄력적 IP를 장애 시 주소를 옮기는 용도로 주로 쓰고, 노드 사이 통신은 DNS 이름으로 하라고 강하게 권한다.

**퍼블릭 IPv4 요금.** 실행 중인 인스턴스에 자동 할당된 주소와 탄력적 IP를 포함한 **모든 퍼블릭 IPv4 주소에 요금이 붙는다.** 탄력적 IP는 붙어 있든 놀고 있든 과금된다. 기준 단가는 {{fact:vpc.price.public-ipv4-hour}}(요금은 바뀔 수 있다). 퍼블릭 주소가 꼭 필요하지 않은 관리 접속은 EC2 Instance Connect 엔드포인트나 Session Manager로 바꿀 수 있다({{ch:ec2/security-access}}).

@topic ec2/networking/bandwidth-ena

**인스턴스 대역폭.** 사양에 적힌 대역폭은 들어오는 쪽과 나가는 쪽에 각각 동시에 적용된다. 대체로 vCPU가 많을수록 크다. 다만 초당 패킷 수, 추적 연결 수 같은 다른 허용량을 넘으면 그만큼 내지 못한다.

| 조건 | 한도 |
|---|---|
| 단일 흐름(5-튜플 TCP/UDP), 클러스터 배치 그룹 밖 | {{fact:ec2.bw.single-flow}} |
| 단일 흐름, 같은 클러스터 배치 그룹 안 | {{fact:ec2.bw.single-flow.cpg}} |
| 단일 흐름, ENA Express를 켠 지원 인스턴스 사이 | {{fact:ec2.bw.single-flow.ena-express}}(인스턴스 전체 한도 이내) |
| 인터넷 게이트웨이를 거치는 다중 흐름, {{fact:ec2.bw.igw.vcpu}} 미만 | {{fact:ec2.bw.igw.small}} |
| 인터넷 게이트웨이를 거치는 다중 흐름, {{fact:ec2.bw.igw.vcpu}} 초과 | 인스턴스 대역폭의 {{fact:ec2.bw.igw.ratio}} |

**버스트 대역폭.** 대체로 {{fact:ec2.bw.burst.vcpu}} 이하 크기는 "최대 ~ Gbps"로 표기된다. 이런 인스턴스는 기준 대역폭(baseline)이 있고, 네트워크 I/O 크레딧으로 잠시 그 위로 올라간다. 버스트는 크기에 따라 보통 {{fact:ec2.bw.burst.min}}~{{fact:ec2.bw.burst.max}} 가능하고, 크레딧이 있어도 최선 노력(best effort)이다. 늘 높은 대역폭이 필요하면 기준 대역폭으로 고른다. 콘솔에는 기준 대역폭이 나오지 않으므로 `describe-instance-types`나 인스턴스 유형 안내서로 확인한다.

**향상된 네트워킹(Enhanced networking).** SR-IOV로 더 높은 대역폭과 초당 패킷 수, 더 낮고 고른 지연을 준다. 추가 요금은 없다.
- **ENA(Elastic Network Adapter)**: 지원 유형에서 최대 {{fact:ec2.ena.max}}. 모든 Nitro 기반 인스턴스가 ENA를 쓴다. AMI에 ENA 드라이버가 있어야 하고 인스턴스에 ENA 지원 속성이 켜져 있어야 한다.
- **ENA Express**: SRD(Scalable Reliable Datagram) 프로토콜로 흐름을 여러 경로에 나눠 보내 단일 흐름 대역폭을 높이고 혼잡할 때 꼬리 지연을 줄인다. 보내는 쪽과 받는 쪽 모두 지원 유형이고 둘 다 켜야 한다. 한산할 때는 중앙값 지연이 조금 늘 수 있다. 가용 영역 사이 지원은 2026년에 추가된 내용이라 시험 범위인지 알 수 없다.
- 오래된 일부 유형은 Intel 82599 VF 인터페이스를 쓴다.

**MTU와 점보 프레임.** MTU는 한 번에 보낼 수 있는 가장 큰 패킷 크기다. 모든 유형이 {{fact:ec2.mtu.std}}를 지원하고, 현재 세대 유형은 **점보 프레임(jumbo frames)** {{fact:ec2.mtu.jumbo}}를 지원한다.

| 경로 | 최대 MTU |
|---|---|
| 인터넷 게이트웨이, VPN, 리전 사이(전송 게이트웨이 없이) | {{fact:ec2.mtu.std}} |
| 리전 간 VPC 피어링 | {{fact:vpc.peering.mtu.inter-region}} |
| 같은 VPC 안, 클러스터 배치 그룹 안 | {{fact:ec2.mtu.jumbo}} |

- 경로의 한도보다 큰 패킷은 쪼개지거나, DF(Don't Fragment) 비트가 있으면 버려진다.
- 클러스터 배치 그룹 안에서는 점보 프레임이 최대 처리량에 도움이 된다고 문서가 권한다. VPC 밖으로 나가는 트래픽에는 조심해서 쓴다. 경로별 MTU를 주거나 MTU가 다른 인터페이스를 따로 둔다.
- **경로 MTU 검색(PMTUD)** 은 ICMP 메시지(IPv4 Type 3 Code 4, IPv6 Packet Too Big)에 기댄다. 보안 그룹이 연결을 추적하지 않거나 네트워크 ACL이 ICMP를 막으면 이 메시지가 오지 않아 큰 패킷이 조용히 버려질 수 있다.

@topic ec2/networking/efa

**Elastic Fabric Adapter(EFA)** 는 HPC와 AI/ML의 인스턴스 사이 통신을 빠르게 하는 네트워크 장치다. 결합이 강한(tightly coupled) MPI 작업, 분산 학습의 NCCL 집합 통신처럼 노드끼리 자주 주고받는 일에 쓴다.

- **OS 우회(OS-bypass).** 앱이 MPI나 NCCL을 거쳐 Libfabric API를 부르면, 커널 TCP/IP 스택을 건너뛰고 EFA 장치와 직접 통신한다. 그래서 지연이 낮고 고르다. 전송은 SRD 프로토콜이 맡는다.
- **인터페이스 종류.**

| 종류 | IP 통신 | 기본 인터페이스로 쓰기 |
|---|---|---|
| ENA | 된다 | 된다 |
| EFA(EFA with ENA) | 된다(ENA 장치 포함) | 된다 |
| EFA 전용(EFA-only) | 안 된다 | 안 된다 |

- 모든 EFA 인터페이스는 인스턴스의 네트워크 인터페이스 개수 한도에 들어간다. 네트워크 카드마다 EFA는 하나만 둔다.
- 지원 인스턴스 유형이 정해져 있다(주로 큰 크기의 HPC·가속 컴퓨팅 유형).
- EFA는 보통 클러스터 배치 그룹과 함께 쓴다. 노드끼리 가까이 있어야 낮은 지연을 얻기 때문이다.

ENA와의 차이: ENA는 일반 IP 네트워킹을 빠르게 한다. EFA는 거기에 OS 우회 통신을 더한다. "HPC, MPI, 노드 간 저지연"이 함께 나오면 EFA다.

@topic ec2/networking/placement-groups

**배치 그룹(placement group)** 은 서로 관련된 인스턴스를 하드웨어 위에 어떻게 놓을지 EC2에 알려 주는 설정이다. 쓰지 않으면 EC2가 알아서 하드웨어에 흩어 놓는다. 만드는 데 요금은 없다.

| 전략 | 놓는 방식 | 맞는 일 |
|---|---|---|
| 클러스터(cluster) | 한 가용 영역 안에서 가깝게 모은다. 같은 고대역 네트워크 구간에 놓인다 | 노드끼리 통신이 많은 HPC, 낮은 지연·높은 처리량 |
| 파티션(partition) | 논리 파티션으로 나누고, 파티션마다 랙(네트워크·전원)을 따로 쓴다 | HDFS, HBase, Cassandra, Kafka 같은 대규모 분산·복제 시스템 |
| 분산(spread) | 인스턴스 하나하나를 서로 다른 랙에 놓는다 | 서로 떨어져 있어야 하는 소수의 중요한 인스턴스 |

**클러스터 배치 그룹.**
- 가용 영역 하나에만 있다. 같은 리전의 피어링된 VPC에 걸칠 수는 있다.
- 단일 흐름 한도가 {{fact:ec2.bw.single-flow.cpg}}로 올라간다. 인터넷과 Direct Connect로 가는 트래픽은 {{fact:ec2.bw.cpg.external}}로 제한된다. 두 인스턴스 사이 속도는 느린 쪽이 정한다.
- 문서 권장: 필요한 수를 **한 번의 시작 요청** 으로, **같은 인스턴스 유형** 으로 띄운다. 나중에 더 넣거나 유형을 섞으면 용량 부족 오류가 날 가능성이 커진다. 향상된 네트워킹을 지원하는 유형을 고른다.
- 용량 부족 오류가 나면 그룹의 인스턴스를 모두 중지 후 시작하고 다시 시도한다. 용량이 있는 하드웨어로 옮겨질 수 있다.
- 용량을 확실히 잡으려면 클러스터 배치 그룹에 온디맨드 용량 예약을 만든다({{ch:ec2/purchasing-options}}). 영역 예약 인스턴스로는 배치 그룹 안 용량을 잡을 수 없다.
- 버스트 가능 유형(T 계열) 등은 지원하지 않는다.

**파티션 배치 그룹.**
- 가용 영역당 최대 {{fact:ec2.pg.partition.per-az}} 파티션이다. 같은 리전의 여러 가용 영역에 걸칠 수 있다. 인스턴스 수는 계정 한도만 따른다.
- 어느 인스턴스가 어느 파티션에 있는지 보여 준다. HDFS·HBase·Cassandra 같은 토폴로지 인식 앱이 이 정보로 복제본을 서로 다른 파티션에 둔다.
- EC2가 고르게 나누려 하지만 보장하지는 않는다. 특정 파티션을 지정해 띄울 수도 있다.
- 전용 인스턴스(Dedicated Instances)를 쓰면 최대 {{fact:ec2.pg.partition.dedicated}} 파티션이다. 용량 예약은 파티션 배치 그룹 안 용량을 잡지 않는다.

**분산 배치 그룹.**
- 리전에서는 **랙 수준** 분산이다. 여러 가용 영역에 걸칠 수 있지만 가용 영역마다 실행 중인 인스턴스는 최대 {{fact:ec2.pg.spread.per-az}}다. 넘으면 시작이 실패한다. 더 필요하면 분산 배치 그룹을 여러 개 쓴다(그룹 사이의 분산은 보장하지 않는다).
- 각자 다른 하드웨어에 놓이므로 유형을 섞거나 시간을 두고 띄워도 괜찮다.
- 호스트 수준 분산은 AWS Outposts에서만 된다. 전용 인스턴스는 지원하지 않는다.

**공통 규칙.**
- 인스턴스는 한 번에 한 배치 그룹에만 속한다. 그룹을 합칠 수 없다. 전용 호스트는 넣을 수 없다.
- 중단 시 중지·최대 절전하도록 설정한 스팟 인스턴스는 배치 그룹에 넣을 수 없다.
- 인스턴스를 다른 그룹으로 옮기려면 중지한 상태에서 바꾼다.
- 분산·파티션은 "한 하드웨어 고장이 여러 인스턴스를 함께 멈추는 것(상관 장애)"을 줄이는 장치다. 가용 영역 장애까지 견디려면 여러 가용 영역에 나눠 둔다({{ch:ec2/overview}}).
- 정밀 시간(precision time) 배치 그룹은 2026년에 추가된 전략이라 시험 범위인지 알 수 없다.
