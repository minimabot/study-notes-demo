@topic ec2/security-access/protection-layers

공동 책임 모델에서 EC2 고객이 맡는 범위는 {{ch:ec2/overview}}에서 정리했다. 이 장은 그중 **인스턴스에 누가, 어떤 길로 들어오는가** 를 다룬다. 문서가 고객 책임으로 꼽는 네 가지를 이 노트의 장과 짝지으면 다음과 같다.

| 고객 책임 | 어디서 다루나 |
|---|---|
| 인스턴스로 오는 네트워크 접근 제어 | VPC·서브넷·보안 그룹: {{ch:vpc/security-groups-nacl}} |
| 인스턴스에 접속할 때 쓰는 자격 증명 관리 | 이 장(키 페어, 접속 방법) |
| 게스트 OS와 소프트웨어의 업데이트·패치 | 아래 |
| 인스턴스에 붙은 IAM 역할과 권한 | {{ch:iam/roles}}, 자격 증명 전달은 {{ch:ec2/metadata}} |

**네트워크 제어의 기본 방향(문서 권장).**
- 보안 그룹을 주된 제어 수단으로 쓰고, 필요한 최소 트래픽만 허용한다. 네트워크 ACL은 특정 트래픽을 막거나 서브넷 단위 안전망을 두는 보조 수단으로 아껴 쓴다.
- 인터넷에서 바로 닿을 필요가 없는 인스턴스는 프라이빗 서브넷에 둔다. 인터넷 게이트웨이로 가는 경로는 꼭 필요한 서브넷에만 준다.
- 관리 트래픽은 별도 보안 그룹이나 별도 네트워크 인터페이스로 일반 트래픽과 나누면 감사와 변경 통제가 쉽다({{ch:ec2/networking}}).
- EC2 API를 VPC 안에서 프라이빗 IP로 부르려면 인터페이스 VPC 엔드포인트를 쓴다({{ch:vpc/endpoints-privatelink}}).

**호스트 격리.** 같은 물리 호스트의 인스턴스끼리도 하이퍼바이저가 CPU·메모리를 격리한다. 인스턴스를 중지하거나 종료하면 메모리는 지워진 뒤 다른 인스턴스에 할당되고, 스토리지 블록도 초기화된다. 인스턴스는 자기에게 배정된 MAC·IP 주소로만 트래픽을 보낼 수 있다.

**패치와 점검.**
- 인스턴스의 OS와 앱을 정기적으로 패치하는 것은 고객 몫이다.
- **Amazon Inspector** 로 EC2 인스턴스의 소프트웨어 취약점과 의도하지 않은 네트워크 노출을 자동으로 찾아 검사하라고 문서가 권한다.
- **AWS Security Hub CSPM** 의 EC2 제어로 보안 모범 사례 준수 여부를 본다.
- 저장 데이터 보호: EBS 볼륨과 스냅샷을 암호화하라고 문서가 권한다({{ch:ec2/ebs}}).

@topic ec2/security-access/key-pairs

**키 페어(key pair)** 는 공개 키와 프라이빗 키 한 쌍이다. 인스턴스에 접속할 때 신원을 증명하는 데 쓴다.

| 항목 | 내용 |
|---|---|
| Linux | 처음 부팅할 때 지정한 공개 키가 기본 사용자의 `~/.ssh/authorized_keys`에 들어간다. SSH로 접속할 때 짝이 되는 프라이빗 키를 쓴다 |
| Windows | 프라이빗 키로 관리자 비밀번호를 복호화하고, 그 비밀번호로 RDP 접속한다 |
| 키 종류 | RSA {{fact:ec2.key.rsa.bits}}(Linux·Windows), ED25519(Linux만). EC2에서 만들거나, 다른 도구로 만든 공개 키를 가져온다(import). DSA 키는 받지 않는다 |
| 보관 | EC2는 공개 키만 보관한다. 프라이빗 키 사본은 없다 |

- 프라이빗 키를 가진 사람은 누구나 그 키 페어를 쓰는 인스턴스에 접속할 수 있다. 안전한 곳에 두고, Linux·macOS에서는 본인만 읽을 수 있게 권한을 좁힌다(`chmod 400`). 권한이 넓으면 SSH 클라이언트가 키를 거부한다.
- 모든 인스턴스에 같은 키를 쓸지 나눌지는 보안 방침에 따라 정한다.

**프라이빗 키를 잃어버렸을 때.** EC2에서 다시 받을 방법은 없다. 루트 볼륨이 EBS인 인스턴스는 이렇게 되살린다.
1. 새 키 페어를 만든다.
2. 원래 인스턴스를 중지하고 루트 볼륨을 뗀다.
3. 임시 인스턴스에 그 볼륨을 데이터 볼륨으로 붙여, `authorized_keys`에 새 공개 키를 넣는다.
4. 볼륨을 원래 인스턴스에 다시 붙이고 시작한 뒤 새 키로 접속한다.

루트 볼륨이 인스턴스 스토어이면 이 방법을 쓸 수 없다. 키 없이 접속하는 다른 길(Session Manager 등)을 미리 마련해 두면 이런 상황에 덜 묶인다.

@topic ec2/security-access/connect-options

접속 방법마다 필요한 것이 다르다. 문서의 비교를 줄이면 다음과 같다.

| 방법 | 인바운드 규칙 | IAM 권한 | 인스턴스 프로파일 | 키 페어 |
|---|---|---|---|---|
| SSH 클라이언트(Linux) | 필요(22번 포트) | 불필요 | 불필요 | 필요 |
| RDP 클라이언트(Windows) | 필요 | 불필요 | 불필요 | 무작위 관리자 비밀번호를 쓰면 필요 |
| EC2 Instance Connect(Linux) | 필요 | 필요 | 불필요 | 불필요 |
| Session Manager(Linux·Windows) | 불필요 | 필요 | 필요 | 불필요 |
| EC2 Instance Connect 엔드포인트(Linux·Windows) | 필요(엔드포인트에서) | 필요 | 불필요 | SSH로 접속하면 필요 |

**SSH 클라이언트.** 인터넷에서 접속하려면 인스턴스에 퍼블릭 주소와 인터넷 경로가 있어야 하고(VPN·Direct Connect로 프라이빗 IP에 접속할 수도 있다), 보안 그룹이 내 IP에서 오는 22번 포트를 허용해야 한다. VPC 기본 보안 그룹은 SSH를 허용하지 않고, 시작 마법사가 만든 보안 그룹은 기본으로 허용한다. `0.0.0.0/0`으로 열지 말고 접속하는 주소 범위로 좁힌다.

**EC2 Instance Connect.** SSH 키를 나눠 주는 대신 IAM 정책으로 SSH 접속을 통제한다.
- 접속하면 EC2 Instance Connect API가 SSH 공개 키를 인스턴스 메타데이터에 넣고, 키는 {{fact:ec2.eic.key.ttl}} 동안만 남는다. 인스턴스의 SSH 데몬이 메타데이터에서 키를 찾아 인증한다.
- 인스턴스에 EC2 Instance Connect 패키지가 있어야 한다(일부 AMI에 미리 설치).
- 콘솔에서 접속하면 브라우저가 리전별 EC2 Instance Connect 서비스를 거친다. 보안 그룹 인바운드 소스에 AWS 관리형 접두사 목록 `com.amazonaws.<리전>.ec2-instance-connect`를 넣어 그 서비스의 22번 포트 접근만 허용한다. 콘솔 접속은 퍼블릭 IPv4나 IPv6 주소가 있어야 한다.
- 모든 연결 요청이 AWS CloudTrail에 기록된다. 추가 요금은 없다.
- 연결은 SSH 세션이 끝날 때까지 이어진다. IAM 자격 증명이 만료돼도 끊기지 않는다.

**Session Manager.** AWS Systems Manager의 기능이다. 브라우저 셸이나 AWS CLI로 세션을 연다.
- 인스턴스가 Systems Manager의 관리형 노드여야 하고, `AmazonSSMManagedInstanceCore` 정책이 있는 IAM 역할(인스턴스 프로파일)을 붙여야 한다. SSM Agent가 필요하다(일부 AMI에 미리 설치).
- **인바운드 포트를 열 필요가 없고 키 페어도 필요 없다.** 그래서 문서가 키 페어의 대안으로 소개한다.
- 사용자에게는 세션을 시작할 IAM 권한이 있어야 한다. 권한이 없으면 `ssm:...` 권한 오류가 난다.
- 설정과 로깅의 자세한 내용은 Systems Manager 사용 설명서에 있다.

@topic ec2/security-access/eice

**EC2 Instance Connect 엔드포인트(EICE, EC2 Instance Connect Endpoint)** 는 퍼블릭 IP도, 인터넷 게이트웨이도, 배스천 호스트도 없이 인터넷에서 프라이빗 서브넷의 인스턴스에 SSH나 RDP로 접속하게 해 준다.

**동작.**
- 서브넷에 엔드포인트를 만들면 그 서브넷에 네트워크 인터페이스가 생긴다. 이것이 VPC 안으로 들어오는 입구다.
- 엔드포인트는 **신원 인식 TCP 프록시(identity-aware TCP proxy)** 다. IAM 자격 증명으로 내 컴퓨터에서 엔드포인트까지 프라이빗 터널을 만들고, 트래픽이 VPC에 닿기 전에 인증·인가한다.
- 라우팅이 허용하면 같은 VPC의 다른 서브넷 인스턴스에도 닿는다.
- 성공·실패한 모든 연결 시도가 CloudTrail에 기록된다.

**보안 그룹.**
- 엔드포인트의 보안 그룹은 대상 인스턴스로 나가는 트래픽을 허용해야 한다.
- 인스턴스 보안 그룹은 관리 포트를 엔드포인트(의 보안 그룹)에서 오는 트래픽만 허용하도록 좁힐 수 있다.
- **클라이언트 IP 보존** 을 끄면(기본) 인스턴스에는 엔드포인트 인터페이스 주소가 출발지로 보이므로 VPC에서 오는 트래픽을 허용한다. 켜면 클라이언트 주소가 보이므로 그 주소를 허용해야 하고, 인스턴스가 엔드포인트와 같은 VPC에 있어야 한다. IPv4 엔드포인트에서만 되고, 전송 게이트웨이를 거치면 안 된다.

**제약과 할당량(모두 조정 불가).**

| 항목 | 값 |
|---|---|
| 계정·리전당 엔드포인트 | {{fact:ec2.eice.per-region}} |
| VPC당, 서브넷당 엔드포인트 | {{fact:ec2.eice.per-vpc}} |
| 엔드포인트당 동시 연결 | {{fact:ec2.eice.conns}} |
| TCP 연결 최대 지속 시간 | {{fact:ec2.eice.tcp.max}}(IAM 정책으로 더 짧게) |

- 관리 트래픽용이다. 대용량 데이터 전송은 제한(throttle)된다.
- 연결 시간은 IAM 자격 증명 수명과 무관하다. 콘솔에서는 최대 터널 시간을 자격 증명 수명보다 짧게 잡는다.
- 자기 키 페어를 쓰면 어떤 Linux AMI든 되고, 아니면 인스턴스에 EC2 Instance Connect가 있어야 한다.
- 엔드포인트 자체 요금은 없다. 다른 가용 영역의 인스턴스에 접속하면 가용 영역 간 데이터 전송 요금이 붙는다.
- 퍼블릭 IPv4 주소에 요금이 붙으므로({{ch:ec2/networking}}), 관리 접속만을 위해 퍼블릭 주소를 두던 인스턴스는 이 방법으로 주소를 없앨 수 있다.
- IPv6·이중 스택 엔드포인트는 2025년에 추가돼 시험 범위인지 알 수 없다.
