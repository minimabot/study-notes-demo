@topic kinesis/overview/what

**Amazon Kinesis Data Streams(KDS)** 는 끊임없이 들어오는 데이터를 받아 두었다가, 여러 애플리케이션이 거의 실시간으로 읽어 처리하게 해 주는 관리형 서비스다. 데이터를 담는 곳을 **데이터 스트림(data stream)** 이라고 하고, 스트림에서 데이터를 읽어 처리하는 프로그램을 **Kinesis Data Streams 애플리케이션** 이라고 부른다.

- 레코드를 넣은 뒤 소비자가 읽을 수 있게 되기까지의 지연(put-to-get 지연)은 {{fact:kinesis.put-to-get.latency}}다. 넣자마자 거의 바로 읽힌다고 보면 된다.
- 들어온 데이터는 읽어도 지워지지 않는다. 보존 기간(retention period)이 지나야 사라진다. 기본은 {{fact:kinesis.retention.default}}다.
- 스트림 하나를 여러 애플리케이션이 **서로 독립적으로, 동시에** 읽는다. 한 애플리케이션이 읽었다고 다른 애플리케이션이 못 읽는 일은 없다.
- 데이터를 받는 파이프라인 서버를 직접 만들고 운영할 필요가 없다. 처리량이 늘면 스트림 용량을 늘린다.

용어는 {{ch:kinesis/key-concepts}}에서 하나씩 정리한다.

@topic kinesis/overview/use-cases

KDS는 "들어오는 즉시 가볍게 처리해야 하는 데이터"에 맞다. 데이터를 서버에 모아 두었다가 한꺼번에 보내는 방식(배치)이 아니라, 생기는 대로 바로 밀어 넣는다. 대표적인 쓰임은 다음과 같다.

| 쓰임 | 예 |
|---|---|
| 로그·데이터 피드 수집 | 서버와 애플리케이션 로그를 바로 스트림에 넣는다. 앞단 서버가 죽어도 이미 넣은 로그는 남는다 |
| 실시간 지표와 보고 | 배치를 기다리지 않고 들어오는 로그로 바로 지표를 계산한다 |
| 실시간 분석 | 웹 클릭스트림을 여러 애플리케이션이 나란히 읽어 각자 분석한다 |
| 복잡한 스트림 처리 | 한 애플리케이션의 출력을 다른 스트림에 넣고, 그것을 또 다른 애플리케이션이 읽는 식으로 단계를 잇는다 |

흔한 구성의 예를 하나 보자. 클릭스트림을 스트림 하나에 넣는다. 애플리케이션 A는 누적 집계를 계산해 DynamoDB 테이블을 갱신하고, 대시보드가 그 테이블을 읽는다. 애플리케이션 B는 같은 데이터를 압축해 Amazon S3에 보관한다. 두 작업은 서로를 기다리지 않는다.

처리는 대개 가볍다. 응답이 실시간으로 이루어져야 하기 때문이다. 무거운 일괄 분석은 집계 결과를 데이터 웨어하우스나 맵리듀스 클러스터에 넣은 뒤 그쪽에서 한다.

@topic kinesis/overview/related

Kinesis 이름이 붙은 서비스는 여럿이다. KDS와 헷갈리기 쉬운 두 가지만 한 줄씩 정리한다.

| 서비스 | 하는 일 |
|---|---|
| Amazon Data Firehose | 스트리밍 데이터를 받아 Amazon S3, Amazon Redshift 같은 대상에 알아서 버퍼링해 전달한다. 소비자 코드를 짜지 않는다. KDS 스트림을 원본으로 쓸 수도 있다 |
| Amazon Managed Service for Apache Flink | Apache Flink 애플리케이션을 관리형으로 실행해 스트림 데이터를 변환·분석한다. KDS 스트림을 읽는 소비자가 될 수 있다 |

정리하면 KDS는 데이터를 **담아 두고 여러 소비자가 읽게 하는 곳**, Firehose는 **대상까지 옮겨 주는 것**, Flink는 **흐르는 데이터를 계산하는 것**이다. 이 밖에 영상용 Kinesis Video Streams도 같은 Kinesis 계열이다.

@topic kinesis/overview/vs-sqs

"생산자와 소비자를 떼어 놓는다"는 점에서는 Amazon SQS도 같다. 차이는 메시지를 다루는 방식이다.

| 질문 | KDS를 고른다 | SQS를 고른다 |
|---|---|---|
| 같은 데이터를 여러 애플리케이션이 읽나 | 예. 각자 자기 위치에서 읽는다 | 아니오. 메시지 하나는 소비자 한 곳이 처리하고 지운다 |
| 지난 데이터를 다시 읽어야 하나 | 예. 보존 기간 안이면 원하는 위치부터 다시 읽는다 | 아니오. 지운 메시지는 다시 못 읽는다 |
| 순서가 필요한가 | 샤드 안에서 순서대로 읽는다 | 표준 대기열은 순서를 보장하지 않는다(FIFO 대기열은 그룹 안 순서) |
| 용량을 직접 다루고 싶나 | 샤드 단위 용량이 있다(온디맨드 모드면 자동) | 표준 대기열은 처리량을 거의 신경 쓰지 않아도 된다 |

메시지 하나하나를 작업으로 보고 처리한 뒤 지우는 "작업 큐"라면 SQS가 단순하다. 메시지마다 따로 지연·재시도·DLQ를 다루기도 쉽다. 반대로 순서 있는 기록을 여러 곳에서 실시간으로 읽고 다시 읽기도 해야 한다면 KDS다. SNS, EventBridge까지 포함한 비교는 {{ch:common/messaging-compare}}에 있다.
