@topic sqs/best-practices/idempotency

SQS는 메시지 사본을 여러 서버에 나눠 저장한다. 드물게 그중 한 서버가 응답하지 않는 순간에 메시지를 받거나 지우면, 그 서버의 사본은 지워지지 않고 남는다. 나중에 그 사본이 다시 전달될 수 있다. Standard 큐가 "적어도 한 번" 전달을 약속하는 이유다.

중복은 큐 안에서만 생기지 않는다. 소비자가 가시성 제한 시간 안에 처리를 끝내지 못하면 메시지가 다시 보이고, 다른 소비자가 같은 메시지를 가져간다. 생산자와 소비자가 여럿인 시스템이라면 큐 종류와 상관없이 이런 일이 생길 수 있다.

그래서 기본 원칙은 하나다. **소비자를 멱등(idempotent)하게 만든다.** 같은 메시지를 두 번 처리해도 결과가 한 번 처리한 것과 같아야 한다.

| 방법 | 예 |
|---|---|
| 처리 기록을 남긴다 | 주문 ID를 처리 완료 테이블에 조건부로 쓰고, 이미 있으면 건너뛴다 |
| 덮어써도 같은 결과가 되게 한다 | "재고에 하나 더하기" 대신 "재고를 이 값으로 정하기" |
| 외부 API에 멱등 키를 넘긴다 | 결제 요청에 주문 ID 기반 키를 붙인다 |

FIFO 큐는 보내는 쪽 중복을 일정 시간 동안 걸러 주지만, 소비자 쪽 재처리까지 막아 주지는 않는다. 중복 제거 ID와 메시지 그룹 ID를 쓰는 자세한 방법은 {{ch:sqs/fifo}}에서 다룬다.

@topic sqs/best-practices/retries

**요청 오류는 백오프와 함께 다시 시도한다.** AWS SDK에는 재시도와 지수 백오프(Exponential Backoff)가 이미 들어 있다. SDK를 쓰면 따로 짤 필요가 없다. SDK의 재시도 기능을 쓰지 않는다면, `ReceiveMessage`가 빈 응답·시간 초과·오류를 돌려줬을 때 바로 다시 부르지 말고 잠시 쉰다. AWS는 처음에 {{fact:sqs.bp.retry.pause.first}}, 같은 결과가 이어지면 {{fact:sqs.bp.retry.pause.next}}처럼 대기를 늘리는 예를 든다.

**처리할 수 없는 메시지는 따로 모은다.** 받을 때마다 실패하는 메시지를 독약 메시지(poison pill)라고 부른다. 그대로 두면 큐에 계속 남아 재시도만 반복한다. 데드레터 큐(DLQ)를 붙이면 정해진 횟수만큼 실패한 메시지가 옮겨진다. 이렇게 하면 원본 큐의 `ApproximateAgeOfOldestMessage` 지표도 독약 메시지 때문에 부풀지 않아, 잘못된 경보가 줄어든다.

**최대 수신 횟수를 1로 두지 않는다.** SQS는 분산 시스템이라, `ReceiveMessage`가 성공으로 끝났는데 소비자 손에 메시지가 닿지 않는 일이 드물게 있다. 이때도 SQS는 한 번 전달한 것으로 센다. 최대 수신 횟수가 1이면 그 메시지는 한 번도 처리되지 못한 채 DLQ로 간다.

재처리 정책, 보관 기간, 리드라이브 같은 DLQ 설정은 {{ch:sqs/dlq}}에서 다룬다.

@topic sqs/best-practices/throughput

SQS는 HTTP 요청-응답으로 쓴다. 그래서 스레드 하나가 연결 하나로 낼 수 있는 처리량은 요청 지연이 정한다. AWS 예시로는 지연이 {{fact:sqs.bp.single-thread.latency-example}}이면 {{fact:sqs.bp.single-thread.tps-example}}이 상한이다. 이 벽을 넘는 방법은 두 가지다.

**1. 수평적 조정(Horizontal scaling).** 생산자와 소비자 수를 늘린다. 클라이언트마다 스레드를 늘리거나, 클라이언트를 더하거나, 둘 다 한다. 클라이언트를 더하면 처리량은 거의 비례해서 는다.

**2. 작업 배치 처리(Action batching).** 요청 하나에 메시지를 여러 개 담는다. 배치 작업은 `SendMessageBatch`, `DeleteMessageBatch`, `ChangeMessageVisibilityBatch`다. 받기는 `ReceiveMessage` 하나로 여러 개를 받을 수 있어서 따로 배치 작업이 없다. 한 번에 최대 {{fact:sqs.batch.max-messages}}까지다.

배치의 이점은 왕복 한 번에 더 많은 일을 한다는 것이다. 같은 처리량을 더 적은 스레드·연결·요청으로 낸다. SQS는 요청 수로 요금을 매기므로 비용도 준다. 코드를 크게 바꾸지 않고 배치를 쓰려면 AWS SDK for Java의 버퍼링 비동기 클라이언트(`AmazonSQSBufferedAsyncClient`)를 쓸 수 있다. 다만 이 클라이언트는 FIFO 큐를 지원하지 않는다.

> **주의:** 배치 요청 전체가 성공으로 돌아와도 그 안의 메시지 일부는 실패했을 수 있다. 응답에서 메시지별 실패 목록을 확인하고, 실패한 것만 다시 보낸다.

배치는 메시지를 모으는 동안 지연이 생길 수 있다. 짧은 시간에 메시지가 많이 생기는 생산자, 그리고 스스로 원할 때 가져가는 소비자에게 잘 맞는다.

@topic sqs/best-practices/timing

**가시성 제한 시간은 처리 시간에 맞춘다.** 너무 길면 소비자가 실패했을 때 재시도까지 오래 기다린다. 너무 짧으면 처리 중에 메시지가 다시 보여 다른 소비자가 같은 일을 한다. 처리 시간을 알면 처리와 삭제에 걸리는 최대 시간으로 둔다. 모르면 하트비트를 쓴다. AWS 예시는 처음 {{fact:sqs.visibility.initial-suggestion}}으로 시작하고, 처리하는 동안 {{fact:sqs.bp.heartbeat.interval}}마다 {{fact:sqs.bp.heartbeat.extend-by}}씩 늘리는 방식이다. 연장해도 {{fact:sqs.visibility.max-from-first-receive}} 한도는 넘을 수 없다. 자세한 내용은 {{ch:sqs/visibility-timeout}}에 있다.

**대부분 긴 폴링(Long polling)을 쓴다.** 긴 폴링은 빈 응답을 줄여 요청 수와 비용을 낮춘다. 대기 시간은 보통 최댓값인 {{fact:sqs.longpoll.wait.max}}로 둔다. 응답을 바로 받아야 하는 애플리케이션만 짧은 폴링을 쓴다. 두 방식의 요금 기준은 같다.

긴 폴링을 쓸 때 지킬 것이 두 가지 더 있다.

- **큐마다 스레드를 따로 둔다.** 스레드 하나로 여러 큐를 돌면, 빈 큐에서 기다리는 동안 다른 큐에 온 메시지를 처리하지 못한다.
- **HTTP 응답 제한 시간을 대기 시간보다 길게 잡는다.** 클라이언트가 먼저 끊으면 HTTP 오류가 난다.

폴링 방식의 차이는 {{ch:sqs/polling}}에서 다룬다.

@topic sqs/best-practices/mistakes

공식 문서로 확인할 수 있는 실수만 모았다.

| 실수 | 생기는 일 |
|---|---|
| 소비자를 멱등하게 만들지 않는다 | 중복 전달 때 결제나 알림이 두 번 일어난다 |
| 가시성 제한 시간이 처리 시간보다 짧다 | 처리 중인 메시지를 다른 소비자가 또 처리한다 |
| DLQ 없이 운영한다 | 독약 메시지가 계속 재시도되고, FIFO 큐에서는 그 메시지 그룹이 멈춘다 |
| DLQ 최대 수신 횟수를 1로 둔다 | 소비자에게 닿지 않은 메시지가 처리 기회 없이 DLQ로 간다 |
| Standard 큐에서 DLQ 보관 기간을 원본보다 짧거나 같게 둔다 | 만료는 처음 큐에 들어간 시각 기준이라, 옮겨진 메시지가 금방 지워진다 |
| 짧은 폴링을 쓴다 | 빈 응답이 늘어 요청 수와 비용이 는다 |
| 배치 응답의 메시지별 실패를 보지 않는다 | 실패한 메시지가 오류 없이 빠진다 |
| Lambda에서 부분 배치 응답을 켜지 않는다 | 한 건 실패로 배치 전체가 다시 처리된다 |
| FIFO 큐에서 메시지 그룹 ID를 하나만 쓴다 | 받아 간 메시지를 지우거나 다시 보이기 전에는 다른 소비자가 다음 메시지를 받지 못해 병렬 처리가 막힌다 |
| HTTP 응답 제한 시간이 긴 폴링 대기 시간보다 짧다 | 메시지를 기다리다 HTTP 오류가 난다 |

Lambda의 부분 배치 응답(`ReportBatchItemFailures`)은 Lambda 개발자 안내서의 SQS 오류 처리 페이지에 있다. 메시지 그룹 설계는 {{ch:sqs/fifo}}에서, 지표와 경보는 {{ch:sqs/monitoring}}에서 다룬다.
