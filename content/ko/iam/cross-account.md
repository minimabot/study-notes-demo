@topic iam/cross-account/two-ways

다른 AWS 계정의 보안 주체에게 내 리소스를 쓰게 하는 방법은 두 가지다. 용어부터 정한다. 보안 주체가 있는 쪽이 **신뢰받는 계정(trusted account)**, 리소스가 있는 쪽이 **신뢰하는 계정(trusting account)** 이다.

| 방법 | 동작 |
|---|---|
| 리소스 기반 정책(resource-based policy) | S3 버킷 정책, SNS 주제 정책, SQS 대기열 정책처럼 리소스에 붙인 정책의 `Principal`에 상대 계정이나 그 역할·사용자를 적는다 |
| 역할 수임(role assumption) | 리소스 계정에 역할을 만들고, 신뢰 정책에 상대 계정을 적는다. 상대는 `AssumeRole`로 임시 자격 증명을 받아 일한다 |

두 방법의 가장 큰 차이는 **원래 권한을 유지하느냐** 다.

- 역할을 수임하면 원래 권한을 내려놓고 역할의 권한만 갖는다. 그래서 내 계정 버킷에서 상대 계정 버킷으로 바로 복사하는 일은 한 세션으로 하기 어렵다.
- 리소스 기반 정책으로 접근하면 보안 주체는 자기 계정에서 일하는 상태 그대로 상대 리소스에도 접근한다. 두 계정 사이에 데이터를 복사할 때 편하다.
- 리소스 기반 정책을 지원하지 않는 서비스라면 역할 수임만 쓸 수 있다. 여러 서비스에 걸친 권한을 한 역할로 모아 관리할 때도 역할이 낫다.

**양쪽이 모두 허용해야 한다.** 다른 계정으로 가는 요청은 두 번 평가된다. 신뢰받는 계정에서는 보안 주체의 자격 증명 기반 정책(그리고 권한 경계 같은 제한 정책)을, 신뢰하는 계정에서는 리소스 기반 정책(그리고 그것을 제한하는 정책)을 본다. 둘 다 `Allow`일 때만 허용된다. 어느 쪽이든 명시적 거부가 있으면 거부다. 같은 계정 안의 평가와 다른 점이고, 자세한 순서는 {{ch:iam/policy-evaluation}}에서 다룬다.

리소스 계정이 상대 계정 전체(`arn:aws:iam::<계정>:root`)를 보안 주체로 적으면, 상대 계정 관리자는 받은 범위 안에서만 자기 사용자·역할에 권한을 나눠 줄 수 있다. 받은 것보다 더 넓게 줄 수는 없다.

역할과 리소스 기반 정책은 **같은 파티션 안에서만** 계정을 건넌다. 예를 들어 `aws` 파티션 계정과 `aws-cn` 파티션 계정 사이에는 쓸 수 없다.

@topic iam/cross-account/role-setup

IAM 자습서의 구성을 따라 순서를 정리한다. 원본 계정(Originating)의 개발자가 대상 계정(Destination)의 S3 버킷을 갱신해야 한다.

1. **대상 계정**: 버킷 접근만 허용하는 권한 정책을 만들고, 그 정책을 붙인 역할(예: `UpdateData`)을 만든다. 신뢰할 엔터티로 원본 계정 ID를 적는다.
2. **원본 계정**: 개발자 쪽 보안 주체에 그 역할 ARN에 대한 `sts:AssumeRole`을 허용한다. 수임하면 안 되는 쪽(자습서의 분석가)이 넓은 권한을 이미 갖고 있다면, 그 역할 ARN에 대한 `sts:AssumeRole`을 명시적으로 거부한다.
3. **사용**: 콘솔에서는 역할 전환(Switch Role)에 계정 ID와 역할 이름을 넣는다. CLI·SDK는 `AssumeRole`로 받은 임시 자격 증명을 쓴다. 수임이 됐는지는 `GetCallerIdentity`로 확인한다({{ch:iam/temporary-credentials}}).

신뢰 정책에 계정 전체를 적어도, 그 계정 안에서 실제로 수임할 수 있는 것은 자기 정책에서 `sts:AssumeRole`을 허용받은 보안 주체뿐이다. 이것도 양쪽 허용 규칙의 한 예다.

주의할 점은 다음과 같다.

- 루트 사용자로 로그인한 상태에서는 역할을 전환할 수 없다.
- 콘솔 역할 전환은 `ExternalId`를 요구하지 않는 역할에만 된다. 외부 ID를 요구하는 역할은 API나 CLI로만 수임한다.
- 역할을 수임한 세션은 다시 다른 역할을 수임할 수 있지만(역할 체인), 이때 세션 기간이 짧게 묶인다.
- 내 역할을 조직이나 계정 밖의 누가 수임할 수 있는지는 IAM Access Analyzer로 찾는다({{ch:iam/access-analysis}}).

@topic iam/cross-account/third-party

모니터링·비용 분석 같은 **제3자 서비스** 에 내 계정 접근을 줄 때도 역할을 쓴다. IAM 사용자와 장기 액세스 키를 건네지 않는다. 제3자에게서 받을 것은 세 가지다.

| 받을 것 | 쓰는 곳 |
|---|---|
| 제3자의 AWS 계정 ID | 역할 신뢰 정책의 `Principal` |
| **외부 ID(external ID)** | 신뢰 정책의 `sts:ExternalId` 조건 |
| 필요한 권한 목록 | 역할의 권한 정책. 제3자가 쓰는 비용은 내 계정에 청구되므로 필요한 만큼만 준다 |

**혼동된 대리자 문제(confused deputy problem)** 가 외부 ID를 쓰는 이유다. 제3자 Example Corp는 여러 고객의 역할을 수임한다. 역할 ARN은 비밀이 아니다. 다른 고객이 내 역할 ARN을 알아내 자기 것인 양 Example Corp에 등록하면, Example Corp는 그 고객의 요청으로 내 계정에 들어오게 된다. 권한 없는 쪽이 권한 있는 쪽(대리자)을 속여 일을 시키는 구조다.

외부 ID는 이렇게 막는다.

1. Example Corp가 고객마다 **고유한** 외부 ID를 만들어 준다. 고객이 정하지 않는다. 고객이 정하면 고유성을 보장할 수 없기 때문이다.
2. 고객은 신뢰 정책에 그 값을 조건으로 넣는다.
3. Example Corp는 수임할 때 요청한 고객의 외부 ID를 항상 넣는다. 다른 고객이 내 ARN을 등록해도 Example Corp는 그 고객의 외부 ID를 넣으므로 수임이 실패한다.

```json
{ "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::999988887777:root" },
  "Action": "sts:AssumeRole",
  "Condition": { "StringEquals": { "sts:ExternalId": "제3자가-발급한-고객-ID" } } }
```

외부 ID는 **비밀이 아니다.** 역할을 볼 권한이 있으면 누구나 볼 수 있다. 추측하기 어려운 값이면 되고, 제3자의 고객 번호처럼 이미 있는 고유 식별자로 충분하다. 제3자 쪽은 고객이 준 ARN을 외부 ID 없이도 수임할 수 있는지 시험하고, 된다면 고객이 신뢰 정책을 고칠 때까지 등록하지 않는 것이 권장 절차다.

@topic iam/cross-account/service-org

**서비스 간 혼동된 대리자.** CloudTrail처럼 AWS 서비스가 자기 서비스 보안 주체(`cloudtrail.amazonaws.com`)로 다른 계정의 S3 버킷에 쓰는 경우가 있다. 버킷 정책이 서비스 보안 주체만 허용하면, 버킷 이름을 아는 다른 계정도 자기 추적을 그 버킷으로 보낼 수 있다. AWS는 서비스 보안 주체에 권한을 주는 리소스 정책에 다음 전역 조건 키를 넣으라고 권장한다.

| 조건 키 | 확인하는 것 |
|---|---|
| `aws:SourceArn` | 서비스가 어느 리소스(예: 특정 추적)를 대신해 왔는가 |
| `aws:SourceAccount` | 어느 계정을 대신해 왔는가 |
| `aws:SourceOrgID`, `aws:SourceOrgPaths` | 어느 조직·조직 경로를 대신해 왔는가 |

이 키들은 **AWS 서비스 보안 주체가 보낸 요청** 에 들어온다. 제3자 회사가 자기 계정의 역할로 내 역할을 수임하는 경우의 대책은 외부 ID다. 서비스별로 따로 있는 보호 장치(예: KMS의 암호화 컨텍스트)와 조건 키 지원 여부는 각 서비스 문서에서 확인한다.

**Organizations 정책과 계정 간 접근.** 계정 간 요청에서도 조직 정책이 함께 평가된다.

- **SCP(서비스 제어 정책)** 는 조직 구성원 계정의 IAM 사용자·역할(루트 사용자 포함)이 가질 수 있는 최대 권한을 정한다. 내 계정 보안 주체가 다른 계정 역할을 수임하거나 다른 계정 리소스를 쓰는 것도 이 범위 안에서만 된다. 권한을 주지는 않는다.
- **RCP(리소스 제어 정책)** 는 구성원 계정 리소스의 최대 권한을 정한다. 보안 주체가 내 조직 소속이든 아니든 적용된다. 그래서 서비스 간 혼동된 대리자 통제(`aws:SourceOrgID` 등)를 버킷 정책마다 넣지 않고 조직 전체에 한 번에 걸 수 있다. 이때도 버킷 정책에 대응하는 허용은 따로 있어야 한다.

SCP·RCP와 다른 정책이 합쳐지는 순서는 {{ch:iam/policy-evaluation}}에서 다룬다.
