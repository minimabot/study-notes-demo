@topic iam/identities/root-user

AWS 계정을 처음 만들면 로그인 자격 증명이 하나 생긴다. **AWS 계정 루트 사용자(root user)** 다. 계정을 만들 때 쓴 이메일 주소와 암호로 로그인하고, 계정 안의 모든 서비스와 리소스에 완전한 권한을 갖는다. 관리자 권한을 받은 IAM 사용자와도 다르다. 루트 사용자는 IAM 정책으로 권한을 깎을 수 있는 대상이 아니다.

그래서 AWS는 **일상 작업에, 관리 작업에도 루트 사용자를 쓰지 말라** 고 강하게 권한다. 평소에는 IAM Identity Center의 관리 사용자 등 다른 자격 증명을 쓰고, 루트는 루트만 할 수 있는 일에만 쓴다.

**루트 사용자만 할 수 있는 대표 작업**

| 분류 | 작업 |
|---|---|
| 계정 | 독립 계정의 이메일 주소·루트 암호·루트 액세스 키 변경, 독립 계정 해지와 재개 |
| 복구 | 유일한 IAM 관리자가 실수로 자기 권한을 없앴을 때 정책을 고쳐 되살리기 |
| 결제 | 결제 및 비용 관리 콘솔에 IAM 접근 켜기, 일부 결제·세금 송장 작업 |
| S3 | 버킷에 MFA 삭제(MFA Delete) 켜기, 모든 위탁자를 거부하게 잘못 쓴 버킷 정책 고치기·지우기 |
| SQS | 모든 위탁자를 거부하게 잘못 쓴 큐 정책 고치기·지우기 |
| 기타 | EC2 예약 인스턴스 마켓플레이스 판매자 등록, AWS GovCloud(US) 가입 |

Organizations에 속한 계정은 관리 계정이나 위임된 관리자 계정의 권한 있는 IAM 사용자·역할이 멤버 계정의 이메일 변경, 해지 등을 대신할 수 있다.

**루트 사용자 보호 수칙(AWS 권장)**

- 강한 암호를 쓰고 MFA로 로그인을 보호한다. 루트 사용자에게는 모든 계정 유형에서 MFA가 강제된다. 계정을 만들 때나 로그인 중 안내가 나올 때 MFA를 직접 등록해야 한다.
- 루트 사용자의 액세스 키를 만들지 않는다. 이미 있으면 지운다.
- 루트 이메일은 개인 주소 대신 그룹 메일 주소를 쓰고, 계정 복구 수단(이메일, 전화번호)에 대한 접근을 관리한다.
- 루트 사용 활동을 모니터링한다.

**중앙 루트 액세스 관리(centralized root access).** Organizations를 쓰면 관리 계정이나 IAM 위임된 관리자가 멤버 계정의 루트 자격 증명(암호, 액세스 키, 서명 인증서, MFA)을 지울 수 있다. 이 기능을 켠 뒤 새로 만드는 멤버 계정은 처음부터 루트 자격 증명이 없다. 루트가 필요한 일부 작업, 예를 들어 잘못된 S3 버킷 정책·SQS 큐 정책 삭제나 루트 암호 복구 허용은 `sts:AssumeRoot`로 여는 짧은 **권한 있는 세션(privileged session)** 에서 한다. 이 세션은 작업 범위가 AWS 관리형 정책으로 좁혀진다. 루트 자격 증명으로는 `sts:AssumeRoot`를 부를 수 없고, 전역 STS 엔드포인트가 아닌 리전 엔드포인트로 보내야 한다.

@topic iam/identities/users-credentials

**IAM 사용자(IAM user)** 는 계정 안에 만드는 엔터티다. 사람이나 워크로드 하나를 나타내고, 이름과 자격 증명으로 이루어진다. IAM 사용자는 별도 계정이 아니라 한 계정에만 속하며, 그 활동 요금은 계정이 낸다.

새 IAM 사용자는 **아무 권한도 없다.** 정책을 붙여야 무엇이든 한다. API·CLI로 만들면 자격 증명도 하나 없이 시작한다(콘솔에서 만들 때는 콘솔 암호나 액세스 키 중 하나 이상을 골라야 한다).

| 자격 증명 | 쓰임 |
|---|---|
| 콘솔 암호 | AWS Management Console 로그인. 끄면 콘솔 로그인만 막히고 권한은 그대로다 |
| 액세스 키 | API·CLI·SDK 호출 서명. 액세스 키 ID와 비밀 액세스 키 한 쌍 |
| SSH 키, 서비스별 자격 증명 | CodeCommit, Amazon Keyspaces 인증 |
| 서버 인증서 | 일부 서비스의 HTTPS. AWS는 ACM을 쓰고, ACM이 없는 리전에서만 IAM을 쓰라고 권한다 |

**액세스 키.** 장기 자격 증명이다. 사용자 하나에 {{fact:iam.access-keys.per-user}}까지 만들 수 있다. 비밀 액세스 키는 만들 때만 볼 수 있으므로, 잃어버리면 그 키를 지우고 새로 만든다. 키가 둘까지 허용되므로 새 키를 만들어 바꿔 끼운 뒤 옛 키를 비활성화·삭제하는 순서로 교체할 수 있다. AWS의 경고는 분명하다.

- 액세스 키보다 역할 같은 임시 자격 증명을 먼저 검토한다.
- 루트 사용자로 액세스 키를 만들지 않는다.
- 키를 애플리케이션 코드나 프로젝트 파일에 넣지 않는다. SDK·CLI가 정해진 위치에서 읽게 하거나, 더 낫게는 역할을 쓴다. 공유 자격 증명 파일에 저장된 키는 평문이다.
- CloudTrail로 키 사용을 감시하고, 쓰지 않는 키와 암호는 지운다. 자격 증명 보고서(credential report)로 계정의 모든 사용자의 암호·액세스 키·MFA 상태와 마지막 사용 시점을 한 번에 본다.

**암호 정책(password policy).** 계정 단위로 IAM 사용자 암호 규칙을 정한다. 따로 정하지 않으면 기본 정책이 적용된다. 기본 정책은 길이 {{fact:iam.password.default.min-length}} 이상 {{fact:iam.password.max-length}} 이하, 대문자·소문자·숫자·기호 가운데 세 종류 이상, 계정 이름이나 이메일과 다를 것, 만료 없음이다. 사용자 지정 정책으로는 최소 길이({{fact:iam.password.custom.min-length-floor}}부터), 문자 종류, 만료 기간(최대 {{fact:iam.password.max-age.max}}), 재사용 방지(최대 {{fact:iam.password.reuse.max}}의 이전 암호), 사용자 스스로 암호 변경 허용 등을 정한다.

- 암호 정책은 루트 사용자 암호와 액세스 키에는 적용되지 않는다. 암호가 만료돼 콘솔에 못 들어가도 액세스 키는 계속 동작한다.
- 길이·문자 규칙을 바꾸면 다음 암호 변경 때부터 적용된다. 만료 기간은 즉시 적용되어, 이미 기간을 넘긴 암호는 다음 로그인 때 바꿔야 한다.
- 로그인 실패 횟수로 잠그는 정책은 만들 수 없다. 대신 MFA와 함께 쓴다.
- 잊은 암호는 IAM에서 꺼내 볼 수 없다. 새로 설정한다.

**다중 인증(MFA).** 자격 증명에 더해 두 번째 증거를 요구한다. AWS는 모든 IAM 사용자에게 MFA를 요구하라고 권한다. 루트 사용자와 IAM 사용자는 각각 유형과 관계없이 MFA 디바이스를 {{fact:iam.mfa.devices.max}}까지 등록할 수 있고, 로그인에는 그중 하나만 있으면 된다. 루트 사용자의 MFA는 루트에만 걸린다. IAM 사용자는 저마다 따로 MFA를 설정한다.

| 유형 | 특징 |
|---|---|
| 패스키·보안 키(FIDO) | 공개 키 암호 기반으로 피싱에 강하다. AWS가 가장 먼저 권하는 방식이다. 보안 키 하나를 여러 사용자가 쓸 수 있다. 콘솔에서만 등록한다 |
| 가상 인증 앱 | 휴대폰 앱이 시간 기반 일회용 암호(TOTP)를 만든다. 보안 키를 준비하기 전의 임시 수단으로 권한다 |
| 하드웨어 TOTP 토큰 | AWS와 시드를 공유한 전용 토큰만 쓴다. 물리 장치가 필요하면 보안 키를 대신 권한다 |

SMS 문자 MFA는 새로 켤 수 없다. 쓰고 있는 사용자는 다른 방식으로 옮긴다. API 호출에도 MFA를 요구하려면 정책 조건으로 MFA 인증 여부를 검사한다({{ch:iam/conditions-abac}}).

@topic iam/identities/groups

**IAM 사용자 그룹(user group)** 은 IAM 사용자의 모음이다. 그룹에 자격 증명 기반 정책을 붙이면 그룹의 모든 사용자가 그 권한을 받는다. 사람이 부서를 옮기면 정책을 고치지 않고 그룹만 바꾸면 된다. 사용자는 여전히 자기 자격 증명을 따로 갖는다.

그룹의 성질은 다음과 같다.

- 그룹 하나에 사용자 여럿, 사용자 하나가 여러 그룹에 속할 수 있다. 권한은 붙은 정책을 모두 합친 것이다.
- **그룹은 중첩되지 않는다.** 그룹 안에는 사용자만 들어가고 다른 그룹은 넣을 수 없다.
- **모든 사용자가 자동으로 속하는 기본 그룹은 없다.** 필요하면 직접 만들고 새 사용자를 넣는다.
- **그룹은 위탁자가 아니다.** 권한을 묶는 수단일 뿐 인증되는 대상이 아니므로, 리소스 기반 정책의 `Principal`에 그룹을 쓸 수 없다. 그룹으로 역할을 수임하거나 로그인할 수도 없다.
- 계정당 그룹 수 기본 할당량은 {{fact:iam.quota.groups}}, 그룹 하나에 붙이는 관리형 정책은 {{fact:iam.quota.managed-per-group}}다.

같은 경로(path)를 준다고 사용자가 그룹에 들어가지는 않는다. 경로는 이름을 정리하는 용도일 뿐 권한 경계가 아니다.

@topic iam/identities/users-vs-roles

AWS 문서의 기본 방향은 **사람도 워크로드도 임시 자격 증명을 쓰게 한다** 는 것이다. IAM 사용자의 장기 자격 증명은 다른 방법이 없을 때만 쓴다.

| 누가 | 권하는 방법 |
|---|---|
| 사람(직원, 운영자) | IAM Identity Center 사용자, 또는 IdP 페더레이션으로 역할 수임. 계정 하나만 쓰는 독립 계정이면 역할을 만들어 수임하게 한다 |
| AWS 안의 워크로드(EC2, Lambda, ECS 등) | 서비스가 수임하는 IAM 역할({{ch:iam/roles}}) |
| AWS 밖의 워크로드 | 역할 기반 방식(예: IAM Roles Anywhere)을 먼저 검토한다 |
| 모바일·웹 앱의 최종 사용자 | OIDC 페더레이션. AWS는 Amazon Cognito를 권한다 |

IAM 사용자가 맞는 경우로 문서가 드는 예는 다음과 같다.

- 역할을 쓸 수 없는 워크로드(예: WordPress 플러그인)
- IAM Identity Center를 지원하지 않는 서드파티 AWS 클라이언트
- CodeCommit SSH 키·Git 자격 증명, Amazon Keyspaces 서비스별 자격 증명
- **비상 접근(emergency access)**: IdP에 접근할 수 없을 때를 대비한 사용자. 자격 증명을 엄격히 관리하고 MFA로 보호한다

장기 액세스 키를 꼭 써야 하면 필요할 때 키를 교체하고, 쓰지 않는 키는 지운다. Identity Center 사용자도 AWS 액세스 포털에서 단기 액세스 키를 받아 CLI를 쓸 수 있으므로, 단지 "CLI를 써야 해서"는 IAM 사용자를 만들 이유가 되지 않는다.

@topic iam/identities/identifiers

IAM은 리소스를 세 가지 방식으로 가리킨다.

**표시 이름(friendly name)과 경로(path).** `Bob`, `Developers` 같은 이름이다. 계정 안에서 사용자·그룹·역할·정책 이름은 겹칠 수 없다. 사용자 이름은 로그인할 때는 대소문자를 가리지 않지만, 정책과 ARN 안에서는 가린다. API·CLI로 만들 때 `/division_abc/engineering/` 같은 경로를 붙일 수 있다(콘솔에서는 못 붙인다).

**ARN(Amazon Resource Name).** 정책에서 리소스를 지정할 때 쓴다. 형식은 `arn:파티션:서비스:리전:계정:리소스`다. IAM은 전역이라 리전 자리가 비어 있다.

| 대상 | ARN 모양 |
|---|---|
| 계정(루트) | `arn:aws:iam::<계정>:root` |
| 사용자·그룹·역할 | `arn:aws:iam::<계정>:user/<경로/이름>` (`group/`, `role/`) |
| 서비스 연결 역할 | `arn:aws:iam::<계정>:role/aws-service-role/<서비스>/<이름>` |
| 인스턴스 프로파일 | `arn:aws:iam::<계정>:instance-profile/<이름>` |
| 역할 세션 | `arn:aws:sts::<계정>:assumed-role/<역할>/<세션 이름>` |

역할 세션의 ARN은 서비스 자리가 `sts`다. 파티션은 일반 리전이 `aws`, 중국 리전은 `aws-cn`처럼 다르고, 파티션이 다른 계정 사이에는 접근을 위임할 수 없다.

**고유 ID(unique ID).** IAM은 사용자·그룹·역할·정책·인스턴스 프로파일·서버 인증서마다 고유 ID를 준다. 접두어로 종류를 알 수 있다.

| 접두어 | 종류 |
|---|---|
| `AIDA` | IAM 사용자 |
| `AGPA` | 사용자 그룹 |
| `AROA` | 역할 |
| `AIPA` | 인스턴스 프로파일 |
| `ANPA` | 관리형 정책 |
| `AKIA` | 장기 액세스 키 |
| `ASIA` | STS 임시 액세스 키 |

고유 ID가 필요한 이유는 이름 재사용이다. 이름은 계정 안에서 한 번에 하나만 쓸 수 있을 뿐, 지운 뒤 다시 쓸 수 있다. 예를 들어 버킷 정책의 `Principal`을 `*`로 두고 `aws:PrincipalArn` 조건으로 `build-bot` 역할 ARN을 허용했다면, 그 역할을 지우고 같은 이름으로 다시 만들 때 조건이 새 역할에도 맞는다. 반면 `Principal`에 역할 ARN을 직접 적으면 저장할 때 고유 ID로 바뀌므로, 다시 만든 역할에는 그대로 적용되지 않는다. 고유 ID는 같은 이름으로 다시 만들어도 달라지므로, 리소스 기반 정책의 `Principal`이나 `aws:userid` 조건에 고유 ID를 쓰면 이런 사고를 줄인다. 고유 ID는 API·CLI로만 볼 수 있고 콘솔에는 나오지 않는다. 그 밖에는 AWS도 ARN 사용을 기본으로 권한다.
