@topic iam/policy-evaluation/basics

보안 주체가 콘솔·API·CLI로 요청을 보내면 AWS는 세 단계를 거친다. 먼저 보안 주체를 **인증** 한다(S3처럼 익명 요청을 받는 일부 서비스는 예외). 다음으로 요청 정보를 모아 **요청 컨텍스트(request context)** 를 만든다. 누가(보안 주체), 무엇을(작업), 어디에(리소스), 어떤 상황에서(IP, 시간, MFA 여부, 태그 등) 요청했는지가 담긴다. 마지막으로 이 요청에 걸리는 정책을 모두 모아 **평가** 한다.

평가의 기본 원칙은 셋이다.

- **기본은 거부다.** 어떤 정책도 허용하지 않으면 거부된다. 이를 **묵시적 거부(implicit deny)** 라고 한다. 예외는 계정 루트 사용자로, 기본적으로 모든 권한을 갖는다.
- **허용은 명시해야 한다.** 요청이 통과하려면 평가 규칙에 따라 정책이 `Allow`로 허용해야 한다.
- **명시적 거부가 이긴다.** 적용되는 정책 어디에든 맞는 `Deny` 문이 하나라도 있으면 **명시적 거부(explicit deny)** 이고, 다른 정책의 `Allow`와 상관없이 거부된다.

| 상황 | 결과 |
|---|---|
| 맞는 `Deny` 문이 있다 | 명시적 거부. 무엇으로도 뒤집을 수 없다 |
| `Deny`도 `Allow`도 없다 | 묵시적 거부. 다른 정책의 `Allow`로 허용될 수 있다 |
| 필요한 정책이 모두 `Allow`, `Deny` 없음 | 허용 |

두 거부의 차이가 설계에서 중요하다. 묵시적 거부는 "아직 허용하지 않았다"는 뜻이라 다른 정책이 허용하면 풀린다. 명시적 거부는 어떤 경우에도 허용되면 안 되는 작업에만 쓴다. 문서도 넓게 허용하고 위험한 작업만 `Deny`로 막는 방식이 예상치 못한 결과를 낼 수 있으니, 명시적 거부는 허용할 상황이 전혀 없을 때만 쓰라고 권한다.

정책 종류끼리 합치는 방식은 두 가지다.

- **합집합(OR):** 같은 계정 안에서 자격 증명 기반 정책과 리소스 기반 정책은 어느 한쪽만 허용해도 된다.
- **교집합(AND):** 권한 경계, SCP, RCP, 세션 정책은 "상한"이라서, 자격 증명 기반 정책의 허용과 **모두** 겹쳐야 남는다.

@topic iam/policy-evaluation/order

AWS 문서의 평가 흐름도는 아래 순서로 진행한다. 어느 단계에서든 거부가 나오면 그 자리에서 끝난다.

1. **명시적 거부 확인.** SCP, RCP, 리소스 기반 정책, 자격 증명 기반 정책, 권한 경계, 세션 정책을 모두 훑어 맞는 `Deny` 문을 찾는다. 하나라도 있으면 **거부**.
2. **RCP.** 리소스가 있는 계정에 적용된다. 맞는 `Allow`가 없으면 거부. RCP를 켜면 `RCPFullAWSAccess`라는 AWS 관리형 정책이 조직 루트, 모든 OU, 모든 계정에 자동으로 붙고 떼어 낼 수 없으므로, 따로 제한하지 않았다면 이 단계는 통과한다.
3. **SCP.** 보안 주체가 속한 계정에 적용된다. 맞는 `Allow`가 없으면 거부.
4. **리소스 기반 정책.** 같은 계정이고 이 정책이 보안 주체를 허용하면, 보안 주체 종류에 따라 여기서 바로 **허용** 될 수 있다(다음 절).
5. **자격 증명 기반 정책.** 허용하는 문이 없으면 묵시적 거부로 **거부**.
6. **권한 경계.** 경계가 있는데 이 작업을 허용하지 않으면 **거부**. 경계가 없으면 통과.
7. **세션 정책.** 세션 보안 주체(역할 세션, 페더레이션 사용자 세션)가 아니면 **허용**. 세션 정책을 넘기지 않았다면 **허용**. 세션 정책이 있는데 이 작업을 허용하지 않으면 **거부**.

몇 가지 함정이 있다.

- **SCP는 권한을 주지 않는다.** SCP가 `s3:*`를 허용해도 자격 증명 기반 정책이 허용하지 않으면 거부다. 반대로 관리자 정책을 받은 사용자도 SCP가 허용하지 않는 작업은 못 한다. 멤버 계정의 루트 사용자도 마찬가지다.
- **권한 경계를 붙이면 권한이 줄 수 있고, 떼면 늘 수 있다.** 실제 권한은 자격 증명 기반 정책과 경계의 교집합이다.
- **세션 정책도 상한이다.** 역할을 맡을 때 세션 정책을 넘기면 그 세션은 역할의 권한 정책과 세션 정책이 겹치는 만큼만 할 수 있다.

@topic iam/policy-evaluation/resource-based

같은 계정 안에서 리소스 기반 정책은 다른 정책과 조금 다르게 작동한다. **리소스 기반 정책이 보안 주체를 직접 허용하면, 자격 증명 기반 정책이 없어도 허용될 수 있다.** 다만 그 정책의 `Principal`에 무엇을 적었는지에 따라 권한 경계·세션 정책의 영향이 달라진다.

| `Principal`에 적은 것 | 묵시적 거부의 영향 |
|---|---|
| IAM 사용자 ARN | 자격 증명 기반 정책·권한 경계의 묵시적 거부와 상관없이 허용 |
| 역할 세션 ARN (`assumed-role/...`) | 세션에 직접 준 권한이다. 자격 증명 기반 정책·권한 경계·세션 정책의 묵시적 거부와 상관없이 허용 |
| IAM 역할 ARN (`role/...`) | 자격 증명 기반 정책은 없어도 되지만, 권한 경계·세션 정책의 묵시적 거부에는 막힌다 |
| 페더레이션 사용자 ARN (`federated-user/...`) | 세션에 직접 준 권한이다. 묵시적 거부와 상관없이 허용 |

- 역할을 맡아 요청하면 요청하는 보안 주체는 **역할 자체가 아니라 역할 세션** 이다. 그래서 역할 ARN에 준 권한과 역할 세션 ARN에 준 권한이 다르게 취급된다.
- **명시적 거부는 예외 없이 이긴다.** 리소스 기반 정책이 허용해도 권한 경계나 자격 증명 기반 정책에 `Deny`가 있으면 거부다. 문서의 예에서 경계로 `logs` 버킷을 거부당한 사용자는 버킷 정책이 허용해도 들어가지 못한다. 반면 경계가 언급하지 않은(묵시적 거부일 뿐인) Secrets Manager 비밀은, 비밀의 리소스 기반 정책이 허용하면 읽을 수 있다.
- **예외: 역할 신뢰 정책과 KMS 키 정책.** 이 둘은 같은 계정이라도 보안 주체를 명시적으로 허용해야 한다. 그 밖의 서비스에서도 같은 계정 안에서 리소스 기반 정책의 명시적 허용을 요구하는 경우가 있으니 서비스 문서를 확인한다.

@topic iam/policy-evaluation/cross-account

계정 A의 보안 주체가 계정 B의 리소스를 쓰는 것을 **교차 계정 액세스(cross-account access)** 라고 한다. A는 **신뢰받는 계정(trusted account)**, B는 **신뢰하는 계정(trusting account)** 이다.

교차 계정 요청은 **두 번 평가** 한다.

- **A(보안 주체 쪽):** 자격 증명 기반 정책이 B의 그 리소스를 허용해야 한다. 권한 경계, SCP 같은 제한 정책도 함께 본다.
- **B(리소스 쪽):** 리소스 기반 정책이 A의 그 보안 주체(또는 A 계정 전체)를 허용해야 한다. RCP 같은 제한 정책도 함께 본다.
- **두 평가가 모두 허용일 때만 허용** 한다. 한쪽이라도 거부(명시적이든 묵시적이든)면 거부다.

같은 계정이었다면 리소스 기반 정책 하나로 충분했을 요청도, 교차 계정에서는 A의 자격 증명 기반 정책이 따로 필요하다. 버킷 정책에 A 계정 전체(`arn:aws:iam::<A 계정 ID>:root`)를 적으면 A 계정을 신뢰한다는 뜻일 뿐이고, A 안의 개별 사용자·역할에게는 A의 관리자가 다시 권한을 줘야 한다.

**역할을 맡는 방식과 비교.** 리소스 기반 정책을 지원하지 않는 서비스라면 B에 역할을 만들고 A의 보안 주체가 그 역할을 맡게 한다. 역할을 맡은 뒤에는 B 계정의 보안 주체로 요청하므로, 요청은 B 안의 단일 계정 평가가 된다. 이 방식은 {{ch:iam/cross-account}}에서 더 다룬다.

아래 실험에서 계정 관계, 보안 주체 종류, 각 정책을 바꿔 가며 어느 단계가 판정을 내는지 확인해 보자. 같은 계정에서 자격 증명 기반 정책을 "해당 문 없음"으로 두고 버킷 정책만 허용해 보면, 보안 주체 종류와 권한 경계에 따라 결과가 갈린다. 교차 계정으로 바꾸면 같은 설정이 거부된다.

@topic iam/policy-evaluation/boundaries-delegation

권한 경계의 대표 용도는 **권한 관리 위임** 이다. 중앙 관리자가 다른 사람에게 사용자·역할을 만드는 일을 맡기되, 맡은 사람이 자기 권한보다 큰 권한을 가진 자격 증명을 만들지 못하게 한다.

문서의 예를 줄이면 이렇다. 관리자 María가 Zhang에게 사용자 생성을 맡긴다.

1. **새 사용자용 경계 정책** (`XCompanyBoundaries`)을 만든다. 새 사용자가 가질 수 있는 최대 권한이다. 자기 비밀번호·액세스 키 관리 외의 IAM 작업은 빠져 있다.
2. **Zhang의 권한 경계** (`DelegatedUserBoundary`)를 만든다. 사용자 생성·정책 연결은 `iam:PermissionsBoundary` 조건 키로 "새 사용자에 `XCompanyBoundaries`를 경계로 지정할 때만" 허용한다. 경계 정책 자체를 고치는 작업(`iam:CreatePolicyVersion`, `iam:SetDefaultPolicyVersion`, `iam:DeletePolicy` 등)과 경계를 떼는 작업(`iam:DeleteUserPermissionsBoundary`)은 명시적으로 거부한다.
3. **Zhang의 권한 정책** 을 붙인다. 경계는 권한을 주지 않으므로 실제 권한은 따로 줘야 한다.

```json
{
  "Sid": "CreateOrChangeOnlyWithBoundary",
  "Effect": "Allow",
  "Action": ["iam:CreateUser", "iam:AttachUserPolicy", "iam:PutUserPolicy",
             "iam:DetachUserPolicy", "iam:DeleteUserPolicy", "iam:PutUserPermissionsBoundary"],
  "Resource": "*",
  "Condition": { "StringEquals": {
    "iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/XCompanyBoundaries" } }
}
```

Zhang이 경계를 지정하지 않고 사용자를 만들면 요청이 거부된다. 경계를 지정하면 만들어지고, 새 사용자에게 `IAMFullAccess`를 붙여도 실제 IAM 권한은 경계 안으로 좁혀진다. 문서는 주의할 점도 적는다. Zhang은 자기가 못 쓰는 S3 권한을 가진 사용자를 만들 수 있으므로, 이렇게 위임하는 것은 사실상 Zhang에게 그만큼을 믿고 맡기는 일이다.

역할도 같은 원리다. 역할 생성을 맡길 때는 `iam:CreateRole`·`iam:PutRolePolicy`·`iam:AttachRolePolicy` 등에 같은 조건을 걸고, `iam:DeleteRolePermissionsBoundary`를 거부한다. 아래 설계 과제에서 직접 골라 보자.

**주의.** 권한 경계가 붙은 사용자·역할이 있는 곳에서는 리소스 기반 정책에 `Deny` + `NotPrincipal`을 쓰지 않는다. 경계가 붙은 보안 주체는 `NotPrincipal` 값과 상관없이 항상 거부된다. 대신 `ArnNotEquals` 조건 연산자와 `aws:PrincipalArn`을 쓴다.
