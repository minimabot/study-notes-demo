@topic iam/overview/what-is-iam

**AWS Identity and Access Management(IAM)** 는 AWS 리소스에 누가 접근하는지를 통제하는 웹 서비스다. IAM이 맡는 일은 두 가지로 나뉜다.

| 일 | 묻는 질문 |
|---|---|
| 인증(authentication) | 요청을 보낸 쪽이 누구인가. 로그인했는가 |
| 권한 부여(authorization) | 그 대상이 이 작업을 해도 되는가 |

콘솔에 로그인하든, CLI·SDK로 API를 부르든 AWS를 쓸 때는 매번 IAM을 거친다. 따로 켜는 기능이 아니라 계정의 바탕에 깔린 서비스다.

알아 둘 성질은 다음과 같다.

- **전역 서비스다.** 사용자·그룹·역할·정책 같은 IAM 리소스는 특정 리전에 속하지 않는다. 그래서 IAM 리소스의 ARN은 리전 자리가 비어 있다(`arn:aws:iam::<계정 ID>:user/...`). 한 번 만든 역할은 어느 리전의 서비스에서든 쓴다.
- **최종 일관성(eventual consistency)을 따른다.** IAM은 데이터를 전 세계 여러 서버에 복제해 가용성을 얻는다. 사용자를 만들거나 정책을 고치는 변경은 바로 저장되지만, 모든 곳에 퍼지기까지 시간이 걸린다. AWS는 IAM 변경을 애플리케이션의 핵심 경로에 넣지 말고, 드물게 도는 초기화·설정 단계에서 하라고 권한다. 변경이 퍼졌는지 확인한 뒤 운영 작업이 거기에 기대게 한다.
- **추가 요금이 없다.** IAM, IAM Identity Center, AWS STS(Security Token Service)는 계정 기능으로 무료다. IAM 사용자나 임시 자격 증명으로 다른 서비스를 쓸 때 그 서비스 요금만 낸다. IAM Access Analyzer는 기능에 따라 요금이 붙는 것이 있다({{ch:iam/access-analysis}}).

@topic iam/overview/request-flow

IAM이 요청 하나를 처리하는 흐름을 따라가 본다.

**1. 요청(request).** 사람이나 애플리케이션이 콘솔·API·CLI를 쓰면 AWS로 요청이 간다. 요청에는 다음이 담긴다.

| 요소 | 내용 |
|---|---|
| 작업(action) | 하려는 일. 예: `s3:GetObject`, `iam:CreateUser` |
| 리소스(resource) | 작업 대상. 예: S3 버킷, IAM 사용자 |
| 위탁자(principal) | 요청을 보낸 사람·애플리케이션. 그 위탁자에 붙은 정책 정보도 함께 간다 |
| 환경 데이터 | 출발지 IP 주소, 사용자 에이전트, SSL 사용 여부, 시각 |
| 리소스 데이터 | DynamoDB 테이블 이름, EC2 인스턴스 태그처럼 대상에 관한 값 |

AWS는 이 값들을 모아 **요청 컨텍스트(request context)** 를 만든다. 정책의 조건(`Condition`)은 이 컨텍스트의 값을 보고 판단한다.

**2. 인증.** 위탁자는 자격 증명으로 자신을 증명한다. 누구냐에 따라 방법이 다르다.

- 루트 사용자: 계정을 만들 때 쓴 이메일 주소와 암호
- IAM 사용자: 계정 ID(또는 별칭), 사용자 이름, 암호. 프로그램에서는 역할을 수임해 받은 임시 자격 증명이나 액세스 키
- 페더레이션 위탁자(federated principal): 외부 ID 공급자(IdP)가 인증하고 결과를 AWS에 넘긴다. AWS에 직접 로그인하지 않는다
- IAM Identity Center 디렉터리 사용자: AWS 액세스 포털에서 사용자 이름과 암호로 로그인

S3·STS의 일부 요청처럼 익명 요청을 받는 예외가 있지만, 대부분의 요청은 인증을 거친다. AWS는 모든 사용자에게 다중 인증(MFA)을 쓰라고 권한다({{ch:iam/identities}}).

**3. 권한 부여.** IAM은 요청 컨텍스트로 이 요청에 걸리는 정책을 찾고 허용·거부를 정한다. 같은 계정 안에서의 기본 규칙은 이렇다.

1. 처음에는 모든 요청이 거부된다(묵시적 거부).
2. 자격 증명 기반 정책이나 리소스 기반 정책에 명시적 허용이 있으면 기본 거부를 뒤집는다.
3. SCP·RCP가 있으면 이 작업을 허용해야 한다. 권한 경계와 세션 정책도 대개 허용해야 한다. 단, 같은 계정의 리소스 기반 정책이 요청한 IAM 사용자나 역할 세션의 ARN을 직접 허용하면, 권한 경계·세션 정책에 허용 문이 없다는 이유로는 거부되지 않는다. 리소스 기반 정책의 `Principal`에 역할 ARN을 지정한 허용은 이 예외에 들지 않아 경계·세션 정책의 묵시적 거부에 막힌다. 반면 `Principal`을 `*`로 두고 `aws:PrincipalArn` 조건에 역할 ARN을 쓴 허용은 경계·세션 정책으로 제한되지 않는 별도 예외다. 어느 경우든 명시적 거부와 SCP·RCP의 제한은 그대로 적용된다({{ch:iam/policy-evaluation}}).
4. 어느 정책에든 명시적 거부가 있으면 다른 허용을 모두 이긴다.

다른 계정의 리소스에 접근할 때는 상대 계정의 정책이 허용하고, 내 쪽 자격 증명 기반 정책도 허용해야 한다. 평가 순서는 {{ch:iam/policy-evaluation}}에서 자세히 다룬다.

**4. 작업 수행.** 허용되면 위탁자는 리소스에 작업을 한다. 서비스마다 지원하는 작업·리소스·조건 키 목록이 정해져 있고, 정책은 이 목록 안에서 쓴다. 역할을 지울 권한이 있어도 그룹을 지울 권한이 없으면 그룹 삭제는 실패한다. 작업 하나하나를 따로 허용해야 한다.

@topic iam/overview/identities-and-access

IAM 문서는 비슷한 말을 구분해 쓴다. 헷갈리기 쉬우므로 정리해 둔다.

| 용어 | 포함하는 것 |
|---|---|
| IAM 리소스 | IAM이 저장하는 것. 사용자, 그룹, 역할, 정책, ID 공급자 객체 |
| IAM 엔터티(entity) | AWS가 인증에 쓰는 IAM 리소스. 사용자와 역할 |
| IAM 자격 증명(identity) | 정책으로 권한을 받는 대상. 사용자, 그룹, 역할 |
| 위탁자(principal) | 요청을 보낼 수 있는 대상. 루트 사용자, IAM 사용자, 역할(을 수임한 세션), 페더레이션 위탁자 |

그룹은 자격 증명이지만 엔터티도 위탁자도 아니다. 그룹으로 로그인하거나 요청을 보낼 수 없다. 루트 사용자는 위탁자이지만 IAM 엔터티가 아니다.

자격 증명마다 받는 자격 증명 종류도 다르다. IAM 사용자와 루트 사용자는 **장기 자격 증명**(암호, 액세스 키)을, 역할은 **임시 자격 증명**을 받는다. AWS는 사람과 워크로드 모두 임시 자격 증명으로 접근하게 하라고 권한다.

**접근 관리 = 정책.** 권한은 정책(policy)으로 준다. 대부분 JSON 문서다. 크게 두 종류로 시작한다.

- **자격 증명 기반 정책(identity-based policy)**: 사용자·그룹·역할에 붙인다. "이 자격 증명이 어떤 리소스에 무엇을 할 수 있는가"를 적는다. 여러 곳에 붙이는 관리형 정책(AWS 관리형, 고객 관리형)과 한 곳에만 박아 넣는 인라인 정책이 있다. 처음에는 AWS 관리형 정책으로 시작하고, 인라인 정책은 대부분의 경우 권하지 않는다.
- **리소스 기반 정책(resource-based policy)**: S3 버킷 같은 리소스에 붙인다. "어떤 위탁자가 이 리소스에 무엇을 할 수 있는가"를 적고, 다른 계정의 위탁자를 지정할 수 있다. 언제나 인라인이다.

역할은 둘 다 갖는다. 역할은 자격 증명이면서 리소스이기도 해서, 누가 수임할지 정하는 **신뢰 정책**(리소스 기반 정책의 한 종류)과 수임한 뒤 무엇을 할지 정하는 권한 정책이 함께 붙는다({{ch:iam/roles}}). 정책 종류 전체는 {{ch:iam/policies}}에서 다룬다.

@topic iam/overview/identity-center-organizations

IAM은 계정 하나 안의 접근을 다룬다. 계정이 여럿이 되면 다음 두 서비스와 함께 쓴다.

**IAM Identity Center.** 사람(워크포스 사용자)이 여러 AWS 계정과 클라우드 애플리케이션에 들어가는 입구를 한곳에 모은다. 사용자를 Identity Center 디렉터리에 직접 만들거나, Okta·Microsoft Entra·Active Directory 같은 기존 IdP와 연결한다. 관리자가 **권한 세트(permission set)** 를 사용자·그룹에 할당하면 Identity Center가 각 계정에 그에 맞는 IAM 역할을 만들고 정책을 붙인다. 사용자는 로그인할 때 그 역할을 자동으로 수임하므로 언제나 임시 자격 증명을 쓴다. 반면 IAM 사용자가 역할을 쓰려면 수임 권한을 받은 뒤 직접 역할을 전환해야 한다. AWS는 여러 계정의 접근을 중앙에서 관리할 때 Identity Center를 권장한다. 페더레이션 방식은 {{ch:iam/federation}}에서 다룬다.

**AWS Organizations.** 여러 계정을 조직 하나로 묶어 관리한다. 계정마다 정책을 따로 관리하기 어려우므로, AWS는 계정을 여럿 가진 경우 Organizations로 권한을 관리하라고 권한다. 접근 통제와 관련된 쓰임은 두 가지다.

- **서비스 제어 정책(SCP)과 리소스 제어 정책(RCP)**: 조직 안 계정에서 허용될 수 있는 최대 권한을 정한다. 권한을 주지는 않고, IAM 정책이 허용한 것 가운데 SCP·RCP도 허용하는 것만 통과한다.
- **중앙 루트 액세스 관리**: 멤버 계정의 루트 사용자 자격 증명을 지우고, 루트가 필요한 일부 작업을 관리 계정에서 대신한다({{ch:iam/identities}}).

계정 사이에서 역할로 접근을 위임하는 방법은 {{ch:iam/cross-account}}에서 다룬다.
