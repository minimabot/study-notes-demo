@topic iam/best-practices/overview

IAM 사용 설명서는 **보안 모범 사례(security best practices)** 를 한 페이지에 모아 둔다. 항목이 많지만 네 갈래로 묶으면 기억하기 쉽다. 각 항목의 자세한 내용은 이미 다룬 장에 있으므로 여기서는 지도처럼 쓴다.

| 갈래 | AWS가 권하는 것 |
|---|---|
| 자격 증명 | 사람은 IdP 페더레이션으로 임시 자격 증명을 쓴다({{ch:iam/federation}}). 워크로드는 역할을 쓴다({{ch:iam/roles}}). IAM 사용자·루트 사용자에는 MFA를 요구한다. 장기 액세스 키가 꼭 필요하면 필요할 때 교체한다. 루트 자격 증명을 보호한다 |
| 권한 | 최소 권한을 준다. AWS 관리형 정책으로 시작해 고객 관리형 정책으로 좁힌다. 조건으로 더 제한한다({{ch:iam/conditions-abac}}). 쓰지 않는 사용자·역할·권한·자격 증명을 정기적으로 지운다 |
| 검증 | IAM Access Analyzer로 활동 기반 정책을 만들고, 정책을 검사하고, 퍼블릭·교차 계정 액세스를 확인한다({{ch:iam/access-analysis}}) |
| 여러 계정과 위임 | Organizations의 SCP·RCP로 가드레일을 둔다. 계정 안에서 권한 관리를 남에게 맡길 때는 권한 경계로 상한을 정한다({{ch:iam/policy-evaluation}}) |

몇 가지는 자주 헷갈린다.

- **SCP와 RCP는 권한을 주지 않는다.** 줄 수 있는 최대치를 정할 뿐이다. 실제 허용은 자격 증명 기반 정책이나 리소스 기반 정책이 한다.
- **권한 경계도 그 자체로는 권한을 주지 않는다.** 예를 들어 개발자가 자기 워크로드용 역할을 만들게 허용하면서, 만들 수 있는 역할의 권한 상한을 권한 경계로 묶는다.
- **장기 자격 증명은 예외다.** 문서가 IAM 사용자가 필요한 경우로 드는 것은 역할을 쓸 수 없는 워크로드, Identity Center를 지원하지 않는 서드파티 클라이언트, CodeCommit·Amazon Keyspaces 자격 증명, 비상 접근 정도다({{ch:iam/identities}}).
- **AWS 밖의 워크로드도 임시 자격 증명을 쓸 수 있다.** IAM Roles Anywhere(X.509 인증서), `AssumeRoleWithSAML`, `AssumeRoleWithWebIdentity`, IoT Core의 상호 TLS, ECS Anywhere, EKS 하이브리드 노드, Systems Manager 하이브리드 활성화가 그 방법이다.

@topic iam/best-practices/root-user

루트 사용자가 무엇이고 루트만 할 수 있는 작업이 무엇인지는 {{ch:iam/identities}}에서 다뤘다. 여기서는 **루트 자격 증명을 지키는 운영 절차** 를 정리한다. 원칙은 하나다. 루트는 루트가 꼭 필요한 작업에만 쓰고, 평소에는 관리 사용자를 따로 만들어 쓴다.

**로그인 보호**

- 강하고 고유한 암호를 쓴다. 암호 관리자로 생성하는 방법을 권한다. 루트 암호의 길이·문자 규칙은 IAM 기본 암호 정책과 같다.
- MFA를 등록한다. 독립 계정, 관리 계정, 멤버 계정 모두 루트 MFA가 필수다. MFA가 없으면 첫 콘솔 로그인 시도부터 {{fact:iam.root.mfa.grace-period}} 안에 등록해야 하고, 지나면 등록해야 콘솔에 들어간다.
- MFA를 **여러 개** 등록해 둔다. 하나를 잃어도 다른 MFA로 로그인할 수 있다. 등록 한도는 {{fact:iam.mfa.devices.max}}다.
- 루트 액세스 키는 만들지 않는다. 루트 작업은 드물기 때문에 콘솔에서 한다.

**사람과 경로 나누기**

- **다중 승인(multi-person approval).** 한 사람이 루트 암호와 MFA를 모두 갖지 않게 한다. 암호를 가진 관리자 그룹과 MFA를 가진 관리자 그룹을 나누고, 두 그룹에서 한 명씩 모여야 로그인할 수 있게 한다.
- **그룹 메일 주소.** 루트 이메일은 회사가 관리하고 여러 사람에게 전달되는 주소로 한다. 담당자가 휴가 중이거나 퇴사해도 AWS의 연락을 놓치지 않는다. 다른 용도로 쓰지 않는다.
- **복구 수단 분리.** 루트 암호 복구에는 이메일과 전화번호가 쓰인다. 두 경로를 한 사람이 모두 갖지 않게 서로 다른 그룹이 관리한다. MFA를 모두 잃으면 등록된 이메일과 전화번호가 둘 다 살아 있어야 복구할 수 있으므로 연락처를 최신으로 유지한다.
- 루트 암호를 그 계정에 의존하는 도구(같은 계정의 AWS 서비스로 돌아가는 비밀 저장소 등)에 두지 않는다. 암호를 잃으면 그 도구에도 들어갈 수 없다. 보관 장소 접근은 두 사람 이상이 승인하게 하고 기록·감시한다.

**Organizations 환경**

- 관리 계정 루트에도 MFA가 필수다.
- 멤버 계정은 두 전략 가운데 고른다. 중앙 루트 액세스 관리로 멤버 계정의 루트 자격 증명을 아예 지우거나(문서가 권하는 쪽), 남겨 두되 MFA로 보호한다.
- 멤버 계정 루트 자격 증명을 남겨 둔다면, 루트 전용 작업 일부를 빼고 루트의 모든 작업을 거부하는 SCP를 붙여 예방 통제를 둔다.

**감시.** 루트 로그인과 사용을 기존 감시 체계로 추적하고 경보를 보낸다. 루트 활동은 CloudTrail에 남는다({{ch:iam/access-analysis}}).

CLI에서 루트 작업이 꼭 필요하면 문서는 루트 액세스 키 대신 루트 자격 증명으로 `aws login` 명령을 써서 자동으로 바뀌는 임시 자격 증명을 받으라고 한다. 최근 추가된 방식이라 시험 반영 여부는 알 수 없다.

@topic iam/best-practices/credentials

IAM 사용자를 둘 수밖에 없는 계정에서 자격 증명을 다루는 방법이다. 각 기능의 세부 규칙은 {{ch:iam/identities}}에 있다.

**MFA 고르기.** AWS는 피싱에 강한 MFA, 곧 패스키와 보안 키(FIDO)를 가능한 곳마다 쓰라고 권한다. 가상 인증 앱은 보안 키를 준비하기 전의 수단, 하드웨어 TOTP 토큰은 꼭 물리 장치가 필요할 때의 수단으로 본다. Identity Center를 쓰면 IAM이 아니라 Identity Center의 MFA 기능을 쓴다(자격 증명 소스가 Identity Center 디렉터리, AWS Managed Microsoft AD, AD Connector일 때).

**암호 정책.** 계정 암호 정책은 IAM 사용자의 콘솔 암호에만 걸린다. 루트 암호와 액세스 키에는 걸리지 않는다. 그래서 암호 정책만으로 "장기 자격 증명 관리"가 끝나지 않는다. 액세스 키는 따로 교체·삭제해야 한다.

**액세스 키 교체(update) 순서.** 사용자 하나에 키를 {{fact:iam.access-keys.per-user}}까지 둘 수 있다는 점을 이용해 서비스 중단 없이 바꾼다.

1. 기존 키를 살려 둔 채 새 키를 만든다. 새 키는 만들자마자 활성이다. 비밀 액세스 키는 이때만 볼 수 있다.
2. 모든 애플리케이션과 도구를 새 키로 바꾼다.
3. 옛 키의 **마지막 사용(last used)** 정보를 확인한다(`GetAccessKeyLastUsed`). 며칠 기다렸다가 다시 보는 방법도 있다.
4. 쓰지 않는 것 같아도 바로 지우지 말고 먼저 **비활성(Inactive)** 으로 바꾼다(`UpdateAccessKey`).
5. 새 키로만 정상 동작하는지 확인한다. 멈춘 도구가 있으면 옛 키를 다시 활성화하고 2단계로 돌아간다.
6. 충분히 기다린 뒤 옛 키를 지운다(`DeleteAccessKey`).

교체할 키를 찾을 때는 IAM 콘솔 사용자 목록의 **액세스 키 사용 기간(Access key age)** 열이나 자격 증명 보고서를 본다. 직원이 회사를 떠날 때처럼 필요할 때 교체한다. 비밀 액세스 키를 잃어버렸다면 되찾을 방법이 없으니 그 키를 지우고 새로 만든다.

@topic iam/best-practices/least-privilege

**최소 권한(least privilege)** 은 작업에 필요한 권한만 주고 그 이상은 주지 않는 것이다. 어떤 작업을, 어떤 리소스에, 어떤 조건에서 할 수 있는지를 정책으로 정한다. 처음부터 완벽하게 정하기는 어렵기 때문에 문서는 넓게 시작해 줄여 가는 흐름을 권한다.

| 단계 | 할 일 |
|---|---|
| 시작 | 직무용 AWS 관리형 정책(job function)으로 권한을 준다. Identity Center라면 권한 세트, 아니면 IAM 역할에 붙인다 |
| 관찰 | 정해 둔 기간(예: {{raw:90일}}) 동안 실제로 쓰는 서비스와 작업을 지켜본다 |
| 분석 | 마지막 액세스 정보로 쓰지 않은 서비스를 찾고, IAM Access Analyzer로 CloudTrail 활동 기반 정책을 생성한다 |
| 교체 | 쓴 것만 담은 고객 관리형 정책을 만들어 붙이고, AWS 관리형 정책을 뗀다. 배포 전 정책 검사로 확인한다 |
| 반복 | 쓰지 않는 사용자·역할·권한·자격 증명을 정기적으로 찾아 지운다 |

AWS 관리형 정책으로 끝내면 안 되는 이유는 그것이 모든 고객을 위해 만든 정책이라 내 사용 사례에 최소 권한이 아닐 수 있기 때문이다. 분석 도구의 사용법과 한계는 {{ch:iam/access-analysis}}에서 다룬다.

관리자 사용자, 루트, 비상 접근 사용자는 일상 작업에 필요 없는 큰 권한을 갖는다. 그래서 문서는 AWS를 배우거나 시험해 볼 때도 권한이 작은 사용자를 하나 더 만들어 그것으로 일하라고 권한다.

조건은 최소 권한을 더 좁히는 도구다. 예를 들어 TLS로 보낸 요청만 허용하거나, CloudFormation 같은 특정 서비스를 거친 호출만 허용할 수 있다({{ch:iam/conditions-abac}}).
