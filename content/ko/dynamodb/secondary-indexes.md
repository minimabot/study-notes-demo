@topic dynamodb/secondary-indexes/basics

테이블은 기본 키(Primary Key)로 찾을 때 가장 빠르다. 그런데 앱은 다른 속성으로도 찾고 싶어 한다. "고객별 주문"은 기본 키로 되지만 "배송 대기 중인 주문"은 기본 키로 안 된다. 그때마다 테이블 전체를 `Scan`하면 테이블이 커질수록 느려지고 용량도 많이 쓴다.

**보조 인덱스(Secondary Index)** 는 같은 데이터를 다른 키로 다시 정리해 둔 사본이다.

- 인덱스는 테이블 하나에만 속한다. 이 테이블을 **기본 테이블(Base Table)** 이라고 한다.
- 인덱스를 만들 때 대체 키와, 인덱스로 복사할 속성(**프로젝션(Projection)**)을 정한다. 기본 테이블의 기본 키 속성은 항상 함께 복사된다.
- 앱은 인덱스에 직접 쓰지 않는다. 기본 테이블에 쓰면 DynamoDB가 인덱스를 알아서 고친다.
- 인덱스는 `Query`나 `Scan`으로 읽는다. 글로벌 보조 인덱스에는 `GetItem`, `BatchGetItem`을 쓸 수 없다.
- 인덱스 키 값은 유일하지 않아도 된다. 같은 키 값을 가진 항목이 여러 개 있으면 모두 돌려준다.
- 인덱스 키 속성은 최상위 String, Number, Binary 속성이어야 한다. 맵·리스트·세트는 키가 될 수 없다.

인덱스는 두 종류다. **글로벌 보조 인덱스(GSI, Global Secondary Index)** 와 **로컬 보조 인덱스(LSI, Local Secondary Index)** 다. 테이블 하나에 GSI는 기본 한도 {{fact:dynamodb.gsi.default-quota}}, LSI는 최대 {{fact:dynamodb.lsi.max}}까지 만들 수 있다.

@topic dynamodb/secondary-indexes/gsi-vs-lsi

| 항목 | GSI | LSI |
|---|---|---|
| 파티션 키 | 기본 테이블과 달라도 된다 | 기본 테이블과 같아야 한다 |
| 정렬 키 | 선택. 아무 스칼라 속성 | 필수. 기본 테이블과 다른 속성 |
| 만드는 시점 | 언제든 추가·삭제 | 테이블 만들 때만. 나중에 추가·삭제 불가 |
| 조회 범위 | 테이블 전체 (모든 파티션) | 파티션 키 값 하나 안 |
| 읽기 일관성 | 최종 일관성만 | 최종 일관성 또는 강력한 일관성 |
| 용량 | 인덱스 자기 용량을 쓴다 | 기본 테이블 용량을 쓴다 |
| 크기 제한 | 없다 | 파티션 키 값 하나당 {{fact:dynamodb.lsi.item-collection.max}} |
| 프로젝션 밖 속성 | 읽을 수 없다 | 기본 테이블에서 자동으로 가져온다 (추가 비용) |

고르는 기준을 정리하면 이렇다.

- **다른 파티션 키로 찾아야 한다** → GSI밖에 없다. 예: 주문 테이블을 상태(`status`)로 찾기.
- **같은 파티션 키 안에서 다른 순서로 정렬하고, 강력한 일관성 읽기가 꼭 필요하다** → LSI. 다만 테이블을 만들 때 미리 정해야 한다.
- **나중에 생길 접근 패턴** → GSI. LSI는 운영 중인 테이블에 붙일 수 없다.

AWS 모범 사례 문서도 대개 GSI가 LSI보다 쓸모가 많다고 적는다.

LSI가 있는 테이블에는 **항목 컬렉션(Item Collection)** 제한이 생긴다. 항목 컬렉션은 같은 파티션 키 값을 가진 기본 테이블 항목과 그 LSI 항목을 모두 합친 것이다. 이 합이 {{fact:dynamodb.lsi.item-collection.max}}를 넘으면 그 파티션 키 값으로는 더 쓸 수 없다. 쓰기 요청에 `ReturnItemCollectionMetrics`를 켜서 크기를 지켜본다.

GSI는 기본 테이블과 **비동기로** 맞춰진다. 보통은 순식간에 반영되지만, 방금 쓴 항목이 GSI 조회에 아직 안 나올 수 있다. 앱은 이 경우를 견디도록 짜야 한다.

@topic dynamodb/secondary-indexes/projections

프로젝션은 인덱스에 복사할 속성의 범위다. 세 가지가 있다.

| 유형 | 인덱스에 들어가는 것 |
|---|---|
| `KEYS_ONLY` | 기본 테이블 키 + 인덱스 키만. 가장 작다 |
| `INCLUDE` | `KEYS_ONLY` + 지정한 비키 속성 |
| `ALL` | 기본 테이블의 모든 속성. 가장 크다 |

프로젝션이 크면 조회는 편하지만 저장 비용과 쓰기 비용이 늘어난다. 인덱스 항목마다 키와 속성 크기에 더해 {{fact:dynamodb.gsi.index-item-overhead}}의 오버헤드가 붙는다. `ALL`은 데이터를 통째로 한 벌 더 두는 셈이라 저장·쓰기 비용이 대개 두 배 가까이 된다.

프로젝션에 없는 속성을 요청하면 두 인덱스가 다르게 반응한다.

- **GSI:** 기본 테이블에서 가져오지 않는다. 그 속성은 결과에 없다. 필요하면 기본 테이블을 따로 읽어야 한다.
- **LSI:** 기본 테이블에서 자동으로 가져온다. 이를 **페치(Fetch)** 라고 한다. 앱 코드는 그대로지만 항목 전체를 다시 읽으므로 지연과 읽기 용량이 늘어난다.

기준은 이렇다.

- 자주 읽는 속성은 프로젝션에 넣어 페치나 추가 조회를 없앤다.
- 거의 읽지 않는 속성은 넣지 않는다. 프로젝션된 속성을 고칠 때마다 인덱스 쓰기도 일어난다.
- 쓰기가 많고 조회는 드물면 `KEYS_ONLY`를 고려한다.
- 인덱스 항목이 작으면 속성을 몇 개 더 넣어도 쓰기 비용은 같다. 쓰기 단위가 {{fact:dynamodb.wcu.item-size}} 단위로 올림되기 때문이다.

GSI 쓰기 비용은 변경 내용에 따라 다르다. 인덱스 키 값이 바뀌면 옛 항목 삭제와 새 항목 추가로 인덱스 쓰기가 두 번 든다. 인덱스 키도 프로젝션 속성도 아닌 속성만 바꾸면 인덱스 쓰기는 없다.

@topic dynamodb/secondary-indexes/sparse

DynamoDB는 **인덱스 키 속성이 있는 항목만** 인덱스에 넣는다. 정렬 키가 있는 GSI라면 파티션 키와 정렬 키가 둘 다 있어야 들어간다. 그래서 일부 항목만 들어간 인덱스가 생긴다. 이를 **희소 인덱스(Sparse Index)** 라고 한다.

이 성질을 일부러 쓸 수 있다.

- 주문 테이블에서 아직 배송하지 않은 주문에만 `OpenDate` 속성을 넣고, 배송하면 지운다.
- `OpenDate`를 정렬 키로 하는 GSI를 만들면, 인덱스에는 미배송 주문만 날짜순으로 남는다.
- 주문이 수백만 건이어도 인덱스는 작다. 조회가 빠르고, GSI에 기본 테이블보다 적은 쓰기 용량을 줘도 된다.

한 걸음 더 나가면 **GSI 오버로딩(Overloading)** 이 있다. 여러 종류의 항목이 한 테이블에 있을 때, 공통 속성(예: `Data`) 하나에 항목 종류마다 다른 의미의 값을 넣는다. 그러면 GSI 하나로 여러 접근 패턴을 처리할 수 있다. 자세한 모델링은 {{ch:dynamodb/data-modeling}}에서 다룬다.

@topic dynamodb/secondary-indexes/gsi-throttling

GSI는 자기 용량과 자기 파티션을 따로 가진다. 그래서 **GSI가 막히면 기본 테이블 쓰기가 막힌다.** 이를 **GSI 백 프레셔(Back Pressure)** 라고 한다.

- 테이블에 쓰기가 성공하려면 테이블과 그 쓰기에 영향을 받는 모든 GSI에 쓰기 용량이 충분해야 한다.
- 어느 GSI 하나라도 모자라면 기본 테이블 쓰기가 스로틀링된다. 기본 테이블 용량이 넉넉해도 그렇다.
- 오류는 GSI를 가리키지만, 실제로 거절된 것은 기본 테이블 쓰기다. 그래서 원인을 헷갈리기 쉽다.

흔한 원인 두 가지다.

1. **GSI 쓰기 용량 부족(프로비저닝 모드).** AWS는 GSI의 쓰기 용량을 기본 테이블 쓰기 용량 이상으로 두라고 안내한다. 쓰기가 테이블과 인덱스 양쪽에 일어나기 때문이다.
2. **GSI 핫 파티션.** GSI는 GSI 파티션 키로 데이터를 나눈다. 기본 테이블이 `customerId`로 고르게 퍼져 있어도, GSI 파티션 키가 `status`면 값이 몇 개뿐이라 특정 상태 값에 쓰기가 몰린다. 전체 용량이 남아도 파티션 하나의 한도({{fact:dynamodb.partition.write.max}})에 걸린다. 파티션 이야기는 {{ch:dynamodb/partitions}}에 있다.

예외의 이유 코드로 원인을 구분한다.

| 이유 코드 | 뜻 |
|---|---|
| `IndexWriteProvisionedThroughputExceeded` | GSI 프로비저닝 쓰기 용량 부족 |
| `IndexWriteKeyRangeThroughputExceeded` | GSI 파티션 하나에 쓰기가 몰림 |
| `IndexWriteMaxOnDemandThroughputExceeded` | 온디맨드 GSI에 정한 최대 처리량 초과 |
| `IndexWriteAccountLimitExceeded` | 계정 수준 테이블별 한도 초과 |

카디널리티가 낮은 속성을 GSI 파티션 키로 쓸 때는 쓰기 집중을 먼저 의심한다.
