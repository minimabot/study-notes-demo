@topic dynamodb/data-modeling/access-patterns

관계형 데이터베이스(RDBMS)에서는 먼저 데이터를 정규화해 표로 나누고, 질문은 나중에 SQL과 `JOIN`으로 만든다. 질의는 유연하지만, 조인할수록 일이 늘어 트래픽이 커지면 성능이 일정하지 않다.

DynamoDB는 순서가 반대다. **조인이 없다.** 그 대신 자주 쓰는 질문이 요청 한 번, 키 하나로 끝나도록 데이터를 미리 그 모양으로 저장한다. 그래서 질문을 모르면 설계를 시작할 수 없다. AWS도 애플리케이션이 답해야 할 **접근 패턴(Access pattern)** 을 먼저 정리한 뒤 스키마를 설계하라고 안내한다.

접근 패턴을 정리할 때 세 가지를 함께 본다.

| 성질 | 묻는 것 |
|---|---|
| 데이터 크기 | 얼마나 저장하고, 한 번에 얼마나 읽는가 |
| 데이터 모양 | 화면 하나가 어떤 항목들을 함께 원하는가 |
| 데이터 속도 | 최대 부하가 어디에, 얼마나 몰리는가 |

그다음 원칙은 네 가지다.

1. **관련 데이터는 함께 둔다.** 같이 읽는 항목은 같은 파티션 키 아래에 모은다.
2. **정렬 순서를 쓴다.** 정렬 키를 잘 짜면 관련 항목이 붙어서 저장되고 범위로 읽힌다.
3. **요청을 퍼뜨린다.** 한 키에 몰리지 않게 한다({{ch:dynamodb/partitions}}).
4. **GSI로 다른 질문을 받는다.** 기본 키로 안 되는 패턴은 인덱스로 처리한다({{ch:dynamodb/secondary-indexes}}).

**테이블은 몇 개로 둘까.** AWS 문서는 두 가지 기초 설계를 함께 소개한다.

| 설계 | 모양 |
|---|---|
| 단일 테이블 설계(Single table design) | 여러 종류(엔터티)의 항목을 한 테이블에 둔다. 정렬 키로 종류를 구분한다 |
| 다중 테이블 설계(Multiple table design) | 엔터티 종류마다 테이블을 하나씩 둔다. 관계형에 가까운 모양이다 |

단일 테이블의 장점은 이렇다.

- 여러 종류의 항목을 `Query` 한 번으로 읽는다. 따로 두 번 읽으면 요청마다 읽기 단위가 올림되므로, 한 번에 읽을 때보다 비용과 지연이 늘어난다.
- 관리할 테이블, IAM 정책, 경보, 암호화 키가 줄어든다.
- 여러 사용 패턴이 섞여 전체 트래픽이 고르게 되어, 프로비저닝 용량을 높은 사용률로 쓰기 쉽다.

다중 테이블이 나은 경우도 문서에 적혀 있다.

- 엔터티마다 요구가 다를 때. 백업은 테이블 단위이고, 암호화 키와 테이블 클래스(Standard-IA)도 테이블 단위다.
- 테이블마다 스트림이 따로 있어, 항목 종류별로 Lambda 함수를 나눌 수 있다.
- GraphQL 리졸버나 고수준 SDK 매퍼처럼 테이블 하나에 엔터티 하나를 가정하는 도구를 쓸 때.
- 여러 엔터티를 함께 읽는 접근 패턴이 없을 때. 이때는 다중 테이블로 충분하다고 AWS는 쓴다.

AWS의 일반 원칙은 "테이블 수를 가능한 한 적게, 대부분은 단일 테이블을 고려"다. 다만 이것은 함께 읽는 데이터가 있을 때의 이야기이고, 대량 시계열이나 접근 패턴이 아주 다른 데이터는 예외로 든다. 단일 테이블이 늘 정답이라는 뜻이 아니다. 단일 테이블은 관계형에 익숙한 사람에게 학습 곡선이 가파르다는 단점도 함께 적혀 있다.

테이블 수에는 한도도 있다. 계정·리전당 초기 할당량은 {{fact:dynamodb.tables.per-region.default}}이고, 늘려도 {{fact:dynamodb.tables.per-region.max}}가 끝이다. 그 이상이 필요하면 계정을 나눈다. 테넌트마다 테이블을 만드는 설계라면 이 한도를 먼저 따진다.

@topic dynamodb/data-modeling/sort-keys

**항목 컬렉션(Item collection)** 은 파티션 키 값이 같은 항목의 묶음이다. 복합 기본 키를 쓰는 테이블이나 인덱스에만 생긴다. DynamoDB에서 **일대다 관계**를 나타내는 기본 수단이 항목 컬렉션이다. 한 사용자의 프로필, 장바구니, 주소를 같은 파티션 키 아래에 두면 다음 세 가지를 모두 할 수 있다.

- 그 사용자의 항목 전부 읽기 (파티션 키만 준 `Query`)
- 항목 하나만 읽기 (`GetItem`)
- 특정 종류만 읽기 (정렬 키 조건을 준 `Query`)

**계층형 정렬 키(Composite sort key).** 계층의 단계를 `#` 같은 구분자로 이어 정렬 키를 만든다.

| PK | SK |
|---|---|
| `USER#u1` | `CART#ACTIVE#apple` |
| `USER#u1` | `CART#SAVED#pear` |
| `USER#u1` | `WISH#veggies#carrot` |

파티션 키는 늘 정확한 값이어야 하지만, 정렬 키는 **왼쪽부터 일부만** 조건으로 줄 수 있다. `begins_with(SK, "CART#")`는 장바구니 전체를, `begins_with(SK, "CART#ACTIVE#")`는 결제할 항목만 읽는다. 위시리스트는 키 조건에서 빠지므로 읽지도 않고 읽기 용량도 쓰지 않는다. 필터 표현식으로 거르는 것과 다르다({{ch:dynamodb/query-scan}}). 지역 데이터라면 `국가#지역#도시#동네`처럼 두어 어느 단계에서든 범위로 읽을 수 있다.

날짜·시각은 `2026-10-03T09:00`처럼 문자열 순서와 시간 순서가 같은 형식으로 넣는다. 그래야 `BETWEEN`, `>`로 기간을 읽고 `ScanIndexForward=false`로 최신 순으로 읽을 수 있다.

**버전 항목(Version control).** 변경 이력을 남기면서 최신 값을 빨리 읽고 싶을 때 쓰는 패턴이다.

1. 처음 쓸 때 사본 두 개를 만든다. 정렬 키 접두어가 `v0_`인 것과 `v1_`인 것이다.
2. 고칠 때마다 다음 번호(`v2_`, `v3_`…)로 새 항목을 쓰고, 같은 내용을 `v0_` 항목에도 덮어쓴다.
3. 최신 값은 `v0_` 항목 하나를 읽으면 된다. 전체 이력은 파티션 키로 `Query`하고 `v0_`를 빼면 된다.

두 항목을 함께 바꿔야 하므로 트랜잭션으로 묶으면 둘이 어긋나지 않는다({{ch:dynamodb/transactions}}).

**수직 분할(Vertical partitioning).** 큰 JSON 문서 하나를 항목 하나에 통째로 넣으면, 일부만 고쳐도 문서 전체 크기만큼 쓰기 단위를 쓰고, 키 조건으로 일부만 읽을 수도 없다. AWS는 문서를 같은 파티션 키 아래, 정렬 키 접두어(`PROFILE`, `ADDR#default`, `CART#…`)로 구분한 작은 항목들로 나누라고 권장한다. 쓰기는 {{fact:dynamodb.wcu.item-size}} 단위로 매겨지므로, 나눈 항목이 그보다 작으면 하나를 고칠 때 쓰기 단위 하나로 끝난다. 항목 하나의 최대 크기 {{fact:dynamodb.item.max-size}}를 피하는 방법이기도 하다.

> **주의:** 테이블에 LSI가 있으면 항목 컬렉션 하나가 {{fact:dynamodb.lsi.item-collection.max}}를 넘을 수 없다. 컬렉션이 끝없이 자라는 설계라면 LSI 대신 GSI를 쓴다.

@topic dynamodb/data-modeling/relationships

**다대다 관계: 인접 목록(Adjacency list).** 송장(invoice)과 청구서(bill)처럼, 송장 하나에 청구서 여러 개가 들어가고 청구서 하나가 여러 송장에 들어가는 관계다. 그래프로 보면 엔터티가 노드, 관계가 간선이다.

- 노드마다 파티션 키를 하나씩 쓴다.
- 노드 자신의 속성은 그 파티션 안의 항목 하나로 둔다.
- 관계(간선)는 같은 파티션 안에 **정렬 키 = 상대 노드 ID** 인 항목으로 둔다.

| PK | SK | 뜻 |
|---|---|---|
| `INV#1` | `INV#1` | 송장 자체의 속성 |
| `INV#1` | `BILL#7` | 송장 1에 청구서 7이 들어 있다 |
| `INV#2` | `BILL#7` | 송장 2에도 청구서 7이 들어 있다 |
| `BILL#7` | `BILL#7` | 청구서 자체의 속성 |

송장 하나의 청구서 목록은 기본 테이블 `Query`로 읽는다. 반대 방향("청구서 7이 든 송장들")은 **기본 테이블의 정렬 키를 파티션 키로 하는 GSI** 를 만들어 읽는다. PK와 SK를 뒤집은 이 인덱스를 흔히 역 인덱스(inverted index)라 부른다. 데이터 중복이 적고 양방향 질의가 단순해지는 것이 장점이다.

관계마다 자주 함께 보여 줄 속성(예: 가입일, 역할)은 간선 항목에 넣는다. 상대 노드의 이름처럼 잘 바뀌지 않는 값을 간선에 복사해 두는 **비정규화(Denormalization)** 도 흔하다. 대신 원본이 바뀌면 사본도 고쳐야 한다.

여러 단계를 건너는 그래프 탐색을 실시간으로 해야 한다면, AWS는 그래프 데이터베이스인 Amazon Neptune을 검토하라고 안내한다. DynamoDB의 인접 목록은 "한 단계 이웃 찾기"에 맞다.

**GSI 오버로딩(Overloading).** 단일 테이블에는 종류가 다른 항목이 섞여 있다. 그래서 같은 이름의 속성(예: `Data`)에 항목 종류마다 다른 값을 넣을 수 있다. 직원 항목에는 이름, 창고 소속 항목에는 창고 ID, 인사 항목에는 입사일을 넣는다. 테이블의 정렬 키를 파티션 키로, `Data`를 정렬 키로 하는 GSI 하나를 만들면 "이름으로 직원 찾기", "창고별 직원", "최근 입사자"를 모두 그 인덱스로 처리한다. 테이블당 GSI 기본 한도는 {{fact:dynamodb.gsi.default-quota}}이지만, 이렇게 하면 그보다 훨씬 많은 필드를 인덱싱할 수 있다.

**희소 인덱스(Sparse index).** GSI에는 인덱스 키 속성이 있는 항목만 들어간다. 드물게 생기는 상태(예: 수리 기사에게 넘긴 장애 보고)에만 `EscalatedTo` 속성을 붙이고, 그 속성을 파티션 키로 하는 GSI를 만들면 인덱스에는 그 항목만 남는다. 전체를 훑지 않고 드문 항목을 바로 찾고, 인덱스의 쓰기·저장 비용도 해당 항목만큼만 든다. 자세한 동작은 {{ch:dynamodb/secondary-indexes}}에서 다뤘다.

> **주의:** 오버로딩한 GSI의 파티션 키가 `Employee_Name`처럼 값 종류가 적으면 그 값에 쓰기가 몰린다. GSI가 막히면 기본 테이블 쓰기도 막히므로, 필요하면 GSI 파티션 키에도 쓰기 샤딩을 적용한다.

@topic dynamodb/data-modeling/time-series-large

**시계열 데이터(Time series data).** 센서 이벤트처럼 쓰기는 모두 "지금" 시각에 몰리고, 읽기는 오늘 데이터가 가장 많고 오래될수록 줄어드는 데이터다. AWS는 테이블을 적게 쓰라는 일반 원칙의 예외로, 이런 데이터에 **기간마다 테이블을 하나씩** 두는 패턴을 소개한다.

1. 기간(예: 월)마다 테이블을 만든다. 테이블 이름에 기간을 넣는다.
2. 기간이 끝나기 전에 다음 기간 테이블을 미리 만들어 두고, 기간이 바뀌는 순간 쓰기를 새 테이블로 돌린다.
3. 더 쓰지 않는 테이블은 쓰기 용량을 아주 낮추고, 읽기 용량도 오래될수록 줄인다.
4. 거의 읽지 않는 옛 테이블은 보관(아카이브)하거나 삭제한다.

이 패턴은 테이블 클래스와 잘 맞는다. 쓰기·읽기가 몰리는 현재 테이블은 처리량이 싼 **Standard** 로 두고, 데이터는 보관해야 하지만 거의 읽지 않는 지난 테이블은 저장 비용이 싼 **Standard-IA** 로 바꾼다. 테이블 클래스는 나중에 바꿀 수 있다. 현재 테이블 안에서도 한 키에 쓰기가 몰리면 쓰기 샤딩을 함께 쓴다({{ch:dynamodb/partitions}}).

**TTL(Time to Live)로 오래된 항목 지우기.** 테이블을 나누지 않는다면 항목마다 만료 시각(에포크 초, Number 타입)을 넣고 TTL을 켠다. TTL 삭제는 쓰기 용량을 쓰지 않아 무료이고, 저장 요금과 읽을 데이터 양을 함께 줄인다. 다만 비동기로 지워져 만료 뒤 보통 며칠 안에 사라진다. 그래서 잠금 항목처럼 제때 지워져야 하는 데이터를 TTL에 맡기면 안 되고, 조회에서는 필터 표현식으로 만료 항목을 걸러 낸다. TTL 삭제도 스트림에 남으므로, Lambda가 TTL이 지운 레코드만 골라 S3 같은 저렴한 저장소로 옮기는 아카이브 구성도 쓴다. 자세한 설정은 {{ch:dynamodb/streams-ttl}}에서 다룬다.

**큰 항목.** 항목 하나는 {{fact:dynamodb.item.max-size}}를 넘을 수 없다. 넘으면 쓰기가 `ValidationException`으로 실패한다. 방법은 세 가지다.

| 방법 | 주의할 점 |
|---|---|
| 큰 속성 압축 (GZIP 등 → Binary 속성) | 압축한 값으로는 필터링할 수 없다 |
| 여러 항목으로 나누기 (수직 분할) | 같은 파티션 키, 정렬 키로 조각을 구분한다 |
| S3에 객체로 두고 항목에는 객체 키만 | S3와 DynamoDB를 묶는 트랜잭션이 없다. 실패 시 남는 고아 객체를 앱이 치운다 |

S3 방식을 쓸 때는 S3 객체 메타데이터에 DynamoDB 항목의 기본 키를 적어 두면 거꾸로 찾아가기 쉽다. 또 AWS는 쓰기 요청에 `ReturnConsumedCapacity`를 써서 최대 크기에 가까워지는 항목을 미리 감시하라고 권장한다.

@topic dynamodb/data-modeling/order-example

고객·주문·주문 품목이 있는 쇼핑몰을 단일 테이블로 설계해 본다. 순서는 늘 같다. **접근 패턴 → 키 → 인덱스.**

**1단계: 접근 패턴을 적는다.**

| 번호 | 접근 패턴 |
|---|---|
| ① | 고객 ID로 고객 정보 보기 |
| ② | 고객의 주문 목록을 최신 순으로 보기 |
| ③ | 주문 하나와 그 품목 전부를 한 번에 보기 |
| ④ | 주문 ID만으로 주문 찾기 (고객 센터) |
| ⑤ | 창고별로 출고 대기 중인 주문을 오래된 순으로 보기 |

**2단계: 기본 테이블 키를 정한다.** 주문과 품목은 늘 함께 읽으므로(③) 주문 ID를 파티션 키로 한 항목 컬렉션에 모은다.

| PK | SK | 내용 |
|---|---|---|
| `CUST#c1` | `PROFILE` | 이름, 이메일 |
| `ORDER#o7` | `INFO` | 고객 ID, 주문일, 상태, 합계 |
| `ORDER#o7` | `ITEM#01` | 상품 ID, 상품명, 수량, 주문 당시 단가 |
| `ORDER#o7` | `ITEM#02` | 같은 형식 |

품목에는 상품명과 **주문 당시 단가**를 복사해 둔다. 상품 테이블을 다시 읽지 않아도 되고, 나중에 가격이 바뀌어도 주문 기록은 그대로다.

**3단계: 기본 키로 안 되는 패턴에 인덱스를 붙인다.** ②는 고객 ID로 묶어야 하는데 주문의 파티션 키는 주문 ID다. 그래서 주문 `INFO` 항목에 `GSI1PK`, `GSI1SK` 속성을 넣고 GSI1을 만든다. 고객 `PROFILE` 항목에도 같은 속성을 넣으면 인덱스 하나가 고객 정보와 주문 목록을 함께 담는다(오버로딩).

| GSI1PK | GSI1SK | 항목 |
|---|---|---|
| `CUST#c1` | `ORDER#2026-10-21#o9` | 주문 o9 |
| `CUST#c1` | `ORDER#2026-10-03#o7` | 주문 o7 |
| `CUST#c1` | `PROFILE` | 고객 c1 |

⑤는 희소 인덱스로 받는다. 출고 대기 주문에만 `pendingWh`(창고 ID)와 `pendingSince`(대기 시작 시각)를 넣고, 출고되면 두 속성을 지운다. 이 둘을 키로 하는 GSI2에는 대기 중인 주문만 남는다. 상태 값(`PENDING`) 하나를 파티션 키로 쓰면 쓰기가 한 값에 몰리므로, 창고 ID처럼 값이 여럿인 속성을 쓴다.

**4단계: 패턴마다 실제 요청을 확인한다.**

| 패턴 | 요청 |
|---|---|
| ① | `GetItem` PK=`CUST#c1`, SK=`PROFILE` |
| ② | GSI1 `Query` GSI1PK=`CUST#c1`, `begins_with(GSI1SK, "ORDER#")`, `ScanIndexForward=false` |
| ③ | `Query` PK=`ORDER#o7` (주문 정보와 품목이 함께 온다) |
| ④ | `GetItem` PK=`ORDER#o7`, SK=`INFO` |
| ⑤ | GSI2 `Query` pendingWh=`WH#seoul`, pendingSince 오름차순 |

모든 패턴이 `Scan` 없이 키로 끝난다. 주문 `INFO`와 품목을 처음 쓸 때는 `TransactWriteItems`로 묶어 일부만 저장되는 일을 막는다. 한 트랜잭션에는 항목 {{fact:dynamodb.txn.max-items}}까지 들어가므로, 품목 수가 그보다 많을 수 있는 업무라면 다른 방법을 정해 둔다({{ch:dynamodb/transactions}}). GSI는 비동기로 반영되므로 ②, ⑤는 방금 쓴 주문이 잠깐 안 보일 수 있다.

새 접근 패턴이 생기면 같은 순서를 반복한다. GSI는 운영 중에도 추가할 수 있지만, 기본 테이블 키는 나중에 바꿀 수 없다. 그래서 1단계를 꼼꼼히 하는 것이 가장 싸다. 키 설계는 NoSQL Workbench에서 표 모양으로 미리 그려 볼 수 있다.
